# Quick start

You will start Odudu on your own machine, sign in to its console as the first administrator, and then sign a person in to an app. You need nothing installed except Docker and `curl`.

This stack is for trying Odudu out on your own machine. Odudu itself can run on a server other people reach, but this is not that deployment: it serves plain http on loopback only, and its database password is fixed and public. A server that others can reach needs a real database password, TLS and your own encryption key, which the Operating section covers.

## Before you start

You need Docker with Compose v2: Docker Desktop on macOS or Windows, or Docker Engine with the Compose plugin on Linux. Check with `docker compose version`. The command has a space in it; the older `docker-compose` is not Compose v2.

You also need `curl`, which macOS, Linux and current Windows ship. Postgres and the one-time setup step come in the stack. The stack publishes these ports on loopback only:

| Port | What                                                   | Change it with    |
| ---- | ------------------------------------------------------ | ----------------- |
| 3000 | The server and the console                             | `ODUDU_PORT`      |
| 8025 | The mail catcher's inbox, only with the `mail` profile | `ODUDU_MAIL_PORT` |

## 1. Start Odudu

One command downloads the file that describes the stack and starts it. The first start pulls the images, so it is slower than the starts after it.

```text
curl -fsSLO https://github.com/wizzywit/odudu/releases/download/v0.1.0-rc.6/compose.yaml && docker compose up -d
```

In Windows PowerShell, `curl` is another command and `&&` is not available. Use `curl.exe`, and start Compose on a second line so it does not run after a failed download:

```text
curl.exe -fsSLO https://github.com/wizzywit/odudu/releases/download/v0.1.0-rc.6/compose.yaml
docker compose up -d
```

This is a release candidate; once 0.1.0 is out, the command uses `latest`.

The file starts three things: Postgres, a one-time setup step that creates the database roles and the first administrator, and the server.

### If port 3000 is taken

Compose will say the port is already allocated. Choose another one with `ODUDU_PORT` and start again. In bash and zsh:

```text
ODUDU_PORT=3100 docker compose up -d
```

In PowerShell:

```text
$env:ODUDU_PORT = '3100'; docker compose up -d
```

Use that port wherever the rest of this page says 3000. Pick it before the first start: the address is saved then, so to change the port later run `docker compose down -v` and start again, which erases what you made. Use `localhost`, not `127.0.0.1`, in your app's settings: the issuer always names `localhost`.

## 2. Copy the first password

The setup step prints the console address, the administrator's email and a generated password, once.

```sh {run expect="Odudu is ready"}
docker compose logs setup
```

You will see something like this, each line led by the container name that `docker compose logs` adds. Your password is different.

```text
Odudu is ready.

 console:  http://localhost:3000/console/
 email:    admin@odudu.local
 password: yjNimKOX…

The password is shown once and must be changed at first sign-in.
To remove it from the setup container log afterwards, run:

  docker compose rm -f setup
```

Want your own email? Set `ODUDU_ADMIN_EMAIL` before the first start, the same way as `ODUDU_PORT` above. Want to be asked for a password instead of being given one? Run `docker compose run --rm setup` from a terminal before you start the server.

Copy the password somewhere safe. The generated one stays readable in the setup container's log until the container is removed, so remove it now.

```sh {run}
docker compose rm -f setup
```

## 3. Sign in to the console

Open the console address from the banner, `http://localhost:3000/console/`. It first asks which tenant you administer. Type `system`, the tenant that holds the first administrator, and choose **Continue to sign-in**.

## 4. Set up an app

An app asks Odudu to sign a person in. Odudu keeps people in a tenant, so you make a tenant, register your app as a client of it, and make a person. Each step has two routes to the same result: the console, or the command line. Pick one; your choice sticks to every step on this page.

### Make a tenant

The tenant is the home of its own people, apps and keys. Call it `demo`.

<Tabs groupId="route" defaultValue="console">
<TabItem value="console" label="Console">

1. In the rail, under **SYSTEM**, choose **Tenants**.
2. Choose **Create a tenant**.
3. Type `demo` in **Name**. The issuer under it becomes `http://localhost:3000/tenants/demo`.
4. Choose **Create tenant**. The tenant exists now. The page goes on to ask for its first administrator, which this page does not need, so leave it there.

<ConsoleShot
  name="new-tenant"
  alt="The Create a tenant form with the name demo typed in and its issuer, http://localhost:3000/tenants/demo, shown beneath."
  caption="A tenant needs only a name. The issuer follows from it."
/>

</TabItem>
<TabItem value="cli" label="Command line">

Every command on this page talks to the server at one address. Set it once; if you moved the port, set it to that address instead.

```sh {run}
export ODUDU_BASE="${ODUDU_BASE:-http://localhost:3000}"
```

```sh {run expect="tenantId"}
docker compose exec odudu odudu seed tenant --name demo
```

</TabItem>
</Tabs>

### Register the app

Call it `my-app`. It is a single-page app, which cannot keep a secret, so it is a public client. The redirect address is where Odudu sends the person after they sign in.

<Tabs groupId="route" defaultValue="console">
<TabItem value="console" label="Console">

1. Open the `demo` tenant: in **Tenants**, choose **Enter demo**. Then, in the rail under **APPLICATIONS**, choose **Clients**.
2. Choose **Create a client**.
3. Type `my-app` in **Client ID**.
4. In **Kind**, choose **Public application**.
5. Type `http://localhost:8080/callback` in the first row of **Redirect URIs**.
6. Choose **Create client**. A public client has no secret, so nothing is shown once.

<ConsoleShot
  name="new-client"
  alt="The Create a client form with client ID my-app, the kind Public application and one redirect URI."
  caption="A public client, with the address Odudu sends the browser back to."
/>

The tenant's client list now shows it.

<ConsoleShot
  name="clients"
  alt="The demo tenant's Clients list: the built-in odudu-admin client and my-app, with a Create a client button."
  caption="The demo tenant lists my-app beside its built-in administration client."
/>

</TabItem>
<TabItem value="cli" label="Command line">

```sh {run expect="clientDbId"}
docker compose exec odudu odudu seed client --tenant demo --client-id my-app --public --redirect-uri http://localhost:8080/callback
```

</TabItem>
</Tabs>

### Make a person

Call them `ada`.

<Tabs groupId="route" defaultValue="console">
<TabItem value="console" label="Console">

1. In the rail under **IDENTITY**, choose **Subjects**.
2. Choose **Create a subject**.
3. Type `ada` in **Username**.
4. Choose **Create subject**.
5. Open the **Credentials** tab and choose **Issue a one-time password**, then **Issue password**. The console shows the password once. Copy it: the person changes it at their first sign-in.

<ConsoleShot
  name="new-subject"
  alt="The Create a subject form with the username ada typed in."
  caption="A person needs only a username. There is no password field."
/>

The subject list shows the new person.

<ConsoleShot

  alt="The demo tenant's Subjects list, with the person ada and a Create a subject button."
  caption="The demo tenant now lists the person."
/>

<ConsoleShot

The console never lets you choose someone's password, so there is no field for one. The command-line route does, and the guides sign `ada` in with that route's password, so use the Command line tab here if you mean to follow them.

</TabItem>
<TabItem value="cli" label="Command line">

The guides sign `ada` in with the password shown here, so keep it for now and choose your own for real users.

```sh {run expect="userSubjectId"}
docker compose exec odudu odudu seed user --tenant demo --username ada --password 'a long and unremarkable passphrase'
```

</TabItem>
</Tabs>

### Sign in to the app

Now ask the tenant to sign `ada` in to `my-app`. This is the address your app sends the browser to. The `code_challenge` is part of PKCE, which every client uses, and the guides explain it.

<Tabs groupId="route" defaultValue="console">
<TabItem value="console" label="Console">

Open this address in your browser. If you moved the port, use it in place of 3000.

```text
http://localhost:3000/tenants/demo/protocol/openid-connect/auth?response_type=code&client_id=my-app&redirect_uri=http%3A%2F%2Flocalhost%3A8080%2Fcallback&scope=openid&state=abc123&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256
```

</TabItem>
<TabItem value="cli" label="Command line">

```sh {run}
SIGN_IN="$ODUDU_BASE/tenants/demo/protocol/openid-connect/auth?response_type=code&client_id=my-app&redirect_uri=http%3A%2F%2Flocalhost%3A8080%2Fcallback&scope=openid&state=abc123&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256" && echo "$SIGN_IN"
```

Open that address in your browser. To check without a browser, ask for the page:

```sh {run expect="200"}
curl -sS -o /dev/null -w '%{http_code}\n' "$SIGN_IN"
```

</TabItem>
</Tabs>

You see Odudu's sign-in page, named for `my-app` and the `demo` tenant. Sign in as `ada`; if you issued a one-time password, Odudu asks for a new one first. The browser then tries to open `http://localhost:8080/callback?code=...`, and because nothing listens there yet it shows a connection error. That is the end of the quick start: the address in the bar holds the one-time code your app would swap for tokens.

## Where to next

This stack runs over plain http on your own machine, so its cookies are the local kind, without `Secure`. A real deployment sits behind TLS and sets `ODUDU_TLS=true`; [Deploying](../operating/deploying.md) shows how.

Pick the guide for what you are building. Each one signs a person in, or a service, all the way to tokens.

- [A web app with a server](../guides/web-app.md), which keeps a secret.
- [A single-page app](../guides/single-page-app.md), which cannot.
- [An API](../guides/api.md) that receives tokens and decides whether to trust them.
- [A service calling a service](../guides/machine-to-machine.md), where no person signs in.

When you want to know what a tenant, a client and a token are, read [Concepts](../concepts/index.md).
