# Email in the console

Odudu sends a little mail: a link to verify an address, a link to reset a password. A tenant needs somewhere to send it from. By default there is nowhere, and the mail is only written to the server's log, which is fine for trying things out and no use to a person waiting for a link. This page connects a tenant to a mail server and shows how its mail is doing. It needs the `manage-tenant` capability; the menu entry is **Email** under **TENANT**.

## 1. Read where the mail goes

The status line at the top says one of three things. **not sent** means nothing sends this tenant's mail and it is only logged. **deployment sender** means the tenant has no relay of its own, so its mail goes through the one the deployment was started with. **own relay** means the tenant sends through the relay set below.

## 2. Set the relay

Under **Mail relay**, fill in the mail server the tenant should use.

1. Enter the **Host** and the **Port**, a whole number from 1 to 65535. Port 587 is the usual one for a relay that takes mail from an application.
2. Enter the **Sender address**, which is what the From line of each message says.
3. If the server asks you to log in, enter the **Username** and a **New password**. Leave both empty if it does not.
4. Leave **Require TLS (STARTTLS)** on. It is required while a username or password is set, so they are never sent in the clear.
5. Save the section. It replaces the whole relay, so every field you want to keep must be filled in.

The password is stored, never shown again. To remove it, turn on **Remove the stored password** and save.

## 3. Send a test message

Under **Test message**, enter an address in **Send to** and choose **Send test message**. The console sends one message through the saved relay and tells you what the server answered. It uses the saved relay, so save first.

The message wears the tenant’s published theme (its logo and colours) and its own wording, as a verification mail does. Under **Send as client** the console starts on the client you signed in with, `odudu-admin`, when you may read the tenant’s clients and the list holds it, and the message then wears that client’s theme over the tenant’s; a client with no theme of its own, or a disabled one, shows the tenant’s look. The list is searched a page at a time, so `odudu-admin` is preselected only when it is on the page already loaded; otherwise the tenant’s own look is sent, the line under the picker says so, and you can search for the client. Pick another client of the tenant to send as it, or choose **Use the tenant’s own look** to send no client. Without the manage-clients capability the choice is closed and the tenant’s own look is sent. Choosing a client needs manage-clients as well as manage-tenant.

## 4. Watch the delivery

The **Delivery** list shows the latest mail the tenant sent or tried to send, newest first. Use **Show** to look at only **Queued**, **Retrying**, **Failed** or **Sent** messages, and **Refresh** to read it again. A message is failed once every attempt is spent. The list never shows a message's body, because it carries a link that signs somebody in.

## 5. Know how the mail looks

Mail wears the tenant's published theme, as the tenant's pages do: its light and dark colours, and its logo and dark logo. The tenant's theme is the default: a mail takes a client's logo and colours, piece by piece over the tenant's, only when the flow began inside that client's sign-in (a registration or a reset asked for from it). It never takes a client's stylesheet or templates, and wording is always the tenant's. A tenant with no published theme, or with a palette and no logo, sends Odudu's own look; a logo that fails to load shows its alt text, and the tenant's name is always written beside it. Many mail apps hold back remote images until the reader allows them, so the name and the alt text carry the brand on their own.

The look is fixed when the mail is queued. A theme published afterwards shows in the next mail and not in one already waiting, and a mail opened after the tenant replaces its logo shows the old one as alt text, because the server serves a logo only while a published version names it. The language of a mail is the recipient's own language if the tenant offers it, else the tenant's default language, else English; the preview here still lets you choose any language Odudu ships. A tenant's message overrides change pages and mail alike: every mail message can be overridden except the attribution lines.

## Things that cannot be undone

**Remove the relay** deletes the tenant's own relay, and with it the stored password. The tenant then falls back to the deployment's sender, or to logging only. You confirm first, and you can save a relay again at any time, though you will need the password again.

## Do the same through the API

The calls are in the [smtp](../reference/generated/admin-api/smtp/index.md) and [mail](../reference/generated/admin-api/mail/index.md) areas of the admin API: the first reads, sets and removes the relay and sends the test, the second lists the delivery. The deployment-wide sender is set with the `ODUDU_SMTP_*` variables in the [configuration reference](../reference/generated/configuration.md).
