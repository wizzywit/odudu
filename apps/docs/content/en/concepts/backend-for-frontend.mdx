# Backend for frontend

You build a page that signs people in. When the sign-in finishes, something has to hold the tokens. If the page holds them, any script that runs in the page can read them and send them away. If a server you run holds them, the page holds nothing worth stealing.

_In words: The browser page holds one HttpOnly cookie with an opaque id. It talks to a backend for frontend, which keeps the tokens, signs in with Odudu and calls your API with the access token. The API never sees the cookie and the page never sees a token._

## What it is

A backend for frontend (BFF) is a small server that sits beside your page and is the OAuth client. It is the pattern RFC 10017, also called BCP 212, recommends for browser apps. The server signs the person in, keeps the tokens, and gives the browser a cookie holding a random identifier and nothing else. Odudu provides it as [`@odudu-io/bff`](../sdks/bff.md).

## What the browser holds

One cookie, `__Host-odudu`. It is `HttpOnly`, so a script cannot read it, `Secure`, so it travels only over https, and `SameSite=Lax`. Its value is a random 256-bit identifier. Every cookie it sets has the attributes the `__Host-` prefix demands: `Secure`, `Path=/` and no `Domain`. The BFF refuses to start with a cookie name that lacks the prefix.

`Lax` and not `Strict` because the person comes back from Odudu by a navigation from another site, and that return has to carry the cookie that started the sign-in.

## The routes

A BFF gives the page four routes and a proxy:

- `login` sends the browser to Odudu. A second cookie, valid for 10 minutes, ties the sign-in to the browser that started it.
- `callback` finishes the sign-in, makes the session with a new identifier and sends the browser back to your app.
- `session` answers who is signed in, as claims, never as a token.
- `logout` ends the session and answers the address of Odudu's end-session page. The address carries the client and the registered return address and no `id_token_hint`, because the ID token never leaves the server. Odudu asks the person to confirm on its own page.
- The proxy calls your API with the session's access token. You list the servers it may call and the path prefixes under each, and it calls nothing else. The browser's cookie and its own `Authorization` header never reach the API. Bodies are limited to 10 MiB by default.

## Protecting the routes

A request that changes something needs the header `X-Odudu-BFF`, with any value, and an `Origin` you allowed. A script in your page can add the header; a page from another site cannot without a preflight the BFF never approves. The `session` route and every proxied call need the header too. `login` and `callback` are plain navigations, which cannot add a header, so they are exempt.

## Keeping the session alive

When a session holds a refresh token and its access token is within 30 seconds of expiry, the BFF renews it, with one request however many calls arrive together at one instance. A refresh token Odudu no longer accepts (`invalid_grant`) ends the session: the answer is `401` with the header `X-Odudu-Session: ended`, which tells a client it was the BFF and not your API. Any other failure, such as an unreachable Odudu, keeps the session and answers `503`. A session without a refresh token ends when its access token does. By default no session lasts longer than seven days.

## Where the sessions live

The default store is memory: at most 10,000 sessions, each dropped after 30 minutes idle, all lost on restart. That fits one process.

More than one instance needs a store they share, with a `lock`. Odudu treats a refresh token used twice as a replay and revokes the grant. Without a lock, two instances can both refresh the same session, and that session ends with `401`. The lock is kept under `lock:` followed by the session identifier and lapses after 120 seconds. Without one, run a single instance or send each session to one instance.

## What it does not do

- It does not give the page a token. To call your API, the page goes through the proxy.
- It does not stop a script that runs in your page from acting as the person while the page is open. It stops that script from taking the tokens away.
- Without a client secret it is not the architecture the RFC describes. Give it one.
- It ships no shared store. You write one over your own database or cache.

## When to choose it

Choose a BFF when you have a server, or can run one: the tokens stay out of the browser. It costs a server hop on each proxied call, and a store to keep.

Choose the browser mode of `@odudu-io/react`, or [the core on its own](../sdks/core-without-react.md), when there is no server, as with a static site or a demonstration. The tokens then live in the page's memory, where a script can read them.

## Deploying one

- Serve the app over https. The cookie is `Secure`; Chrome accepts it on `localhost`, and Safari may not.
- Serve the page and the BFF from one origin, as the React example does, so the cookie is first-party.
