# Sessions

You sign in to one app, then open another that uses the same Odudu. It does not ask for your password again. That is a session: a record that you proved who you are.

## What a session is

When a person signs in, Odudu records a session and sets a cookie in their browser. The cookie says which session is theirs, and with `ODUDU_TLS` on it is `Secure` and prefixed `__Host-` ([the names](../operating/configuration.md#cookie-names)). The next time any app in the tenant sends the person to Odudu, the cookie is found and they are sent straight back signed in.

While the sign-in page is open, a short-lived cookie remembers which sign-in this browser started. It signs nobody in. A link mailed during the sign-in, such as a password reset, brings that browser, and no other, back to it. Anyone on the same browser profile can continue that sign-in until the HttpOnly cookie expires with the login lifetime.

Each sign-in also sets a long-lived device cookie that names no one. Sessions store its digest, shown as `device` in the session lists, which group by it. The cap below counts a person's sessions on that device too, so it is exact once the browser holds the cookie; a first sign-in, or simultaneous ones, can still leave a session the browser no longer names.

A session belongs to a tenant, to a person and to a browser. It remembers which clients it signed in, so signing out reaches them all. The cookie is per host, so people sign in again after a switch of address ([Custom domains](../operating/custom-domains.md)).

## How long it lasts

Two limits apply, and the earlier one ends the session:

- The **idle limit** ends a session nobody has used. It is 30 minutes by default and set with `sso_session_idle_seconds`.
- The **absolute limit** ends a session however busy it is. It is 10 hours by default and set with `sso_session_max_seconds`.

The idle limit cannot be longer than the absolute one. A tenant with `remember_me_allowed` offers a "stay signed in" box with its own pair of limits, `remember_me_idle_seconds` and `remember_me_max_seconds`.

One browser can hold several sessions. The tenant's `max_sessions_per_browser` caps them at 25 sessions by default; a new one past the cap ends the one used longest ago.

## How a session ends

- **By itself**, when a limit is reached.
- **On purpose**, when an app sends the person to the tenant's end-session address. The person is asked to confirm unless the operator turned that off and the request carries the app's ID token for this session. [Refresh and end a session](../guides/refresh-and-end-a-session.md) shows it.
- **By an administrator**, who can end one person's sessions, or call `DELETE /admin/tenants/{tenant}/sessions` to end a tenant's live sessions a few hundred at a time.
- **By a password change**, when the person leaves "End my other sessions" checked: all but the session in use end.

Ending a session ends the refresh tokens bound to it, which is what a browser sign-in produces. A grant made with `offline_access` has no session, so ending sessions leaves it alone. Its refresh tokens work until they expire or an administrator revokes them: `GET /admin/tenants/{tenant}/subjects/{id}/grants` lists what a person holds, with `offline` set on those grants, and `DELETE /admin/tenants/{tenant}/subjects/{id}/grants/{clientId}` revokes every grant through one client, offline ones included. An API that checks only a signature accepts an access token until it expires, which is why they are short; one that asks the introspection endpoint is told at once.

## Recovery codes

Lose the phone that holds the authenticator app and the second factor is gone. Recovery codes are the way back in.

Each person who has set up an authenticator app is given **one set of ten recovery codes**, or 8 to 16 where the tenant sets another size. Making a new set replaces the old one.

A few rules are worth knowing:

1. **Each code works once.** A code that has been used is refused if it is tried again.
2. **A code stands in for an authenticator code, and only that.** It is accepted only on the step that asks for an authenticator code, never after a passkey assertion that included user verification, which already proves two things. After one that lacked it, a code can stand in. Without an authenticator app, held codes are not accepted.
3. **Removing the last authenticator app removes the whole set**, used codes included, and writes an entry to the audit trail with the action `subject.recovery_codes_revoke`. Otherwise a code that outlived its authenticator would work again with the next one.
4. **An administrator can revoke a set**, with `DELETE /admin/tenants/{tenant}/subjects/{id}/recovery-codes`. If the person still has an authenticator, the next sign-in asks them to make a new set, unless the call says `require_new_set=false`. With none, nothing is asked.
5. **A wrong code counts** towards the lockout that follows too many wrong second-factor attempts.

The person is told by email when their set is revoked, by an administrator or because the last authenticator went.

## Working with sessions

1. Choose the two limits, shorter for sensitive tenants.
2. Decide whether to offer "stay signed in", and set its limits.
3. Make each app end the session at its own sign-out.
4. When somebody loses a phone, remove the authenticator, end their sessions, revoke their grants, and let them enrol a new one.
