# Consent and audit

Consent answers what a person let an app see; the audit trail answers what happened, and who did it.

_In words: A client asks, the person decides and a grant is recorded, so the person is asked again only when a client wants more. Separately, the audit trail records sign-ins and refusals, sessions, tokens and administrator changes. Both are kept for each tenant, and audit events are kept 90 days by default._

## Consent

When a client asks for scopes, Odudu can show the person a **consent screen** listing what it wants, in the words you wrote for each scope. Denying sends them back with `access_denied`.

An allow is **recorded**: one grant for this person and this client, holding the scopes they ticked. The screen appears again only if the client asks for more than was recorded.

### When the screen appears

Odudu decides in this order:

1. If the request says `prompt=consent`, ask, whatever the client is set to. A request that would be granted `mcp:write` is asked at every sign-in, whatever is recorded, and `prompt=none` refuses it.
2. If the client registered itself, or arrived as a metadata document, and this person has no grant recorded for this exact client, ask. The client's own setting does not matter here, and `prompt=none` refuses with `consent_required`.
3. If the client does not require consent, carry on without the screen.
4. If everything it asks for is already recorded, carry on.
5. If something is missing and the request says `prompt=none`, refuse with `consent_required`, because `none` means the person must not be shown anything.
6. Otherwise, ask.

`consent_required` is a setting on each client. An administrator's clients leave it off by default; a client that registered itself has it on. An approval belongs to that client's id alone: allowing one app never allows another with the same name.

### Looking at and removing grants

An administrator can list a person's grants with `GET /admin/tenants/{tenant}/subjects/{id}/consents` and remove one with `DELETE /admin/tenants/{tenant}/subjects/{id}/consents/{clientId}`, and the person is asked again.

### A client that names itself

A tenant can let an app identify itself with an https address (`cimd_enabled`) or let an agent register itself (`client_registration_policy` set to `mcp`). Anyone can claim a name, so such a client meets step 2. The screen shows where the client says it came from: the host of the document and every redirect address, or, for a self-registered agent, where this request sends the person and its other origins. Neither kind is ever offered `mcp:write`. The [Settings page](../admin-console/settings.mdx#client-registration) has the details, and the [registration transcript](../reference/transcripts/request-paths/bootstrap.md#the-mcp-policy) shows each refusal.

## Audit

Every tenant keeps an **audit trail**. Each entry says what happened, who or what did it, to what, the outcome, when, and from where. It never holds a secret.

It records:

- **sign-ins**, including failures and lockouts;
- **sessions** that were started or ended;
- **tokens** that were issued, refreshed or revoked, and families revoked for reuse;
- **credentials** that were created or changed, and recovery codes issued or revoked;
- **changes an administrator made**, through the admin API or the console.

Read it with `GET /admin/tenants/{tenant}/audit`, filtered or exported. The [audit events reference](../reference/generated/events.md) lists every event, action and reason.

### Refusals are bounded

Anybody can cause a refusal, so one is recorded only where something limits how many a caller can cause. A registered client gets up to 20 refusals a minute. The last says the budget ran out, and later ones go to the server's log. A failed client login naming a client nobody registered writes no row. A sign-up with an address that already has an account writes one row, limited by the form's budget per address.

### An agent in the trail

When an AI agent acts through the MCP endpoint, each tool call, reads included, is an `agent.tool_call` event, refused calls too. The actor is the person who signed in and the actor client is the agent's client. The details name the tool and the admin route, never the arguments. A change made with `mcp:write` is also the console's event for that change. Access-changing, credential and destructive operations are not available to an agent yet ([classes](../guides/protect-an-mcp-server.md#what-an-agent-can-and-cannot-do-and-why)). A message override and the display name go live the moment they are saved, with nothing checking them for links, so a manipulated agent could publish text it read elsewhere. Review what an agent reads; overrides are audited, and one tool clears them.

### The console assistant in the trail

In Act mode the assistant only proposes a change, and only the administrator whose conversation it is can approve it, from their own console sign-in. Deciding is an `assistant.approval` event that never holds the change or any message text, and the change is an `agent.tool_call` event. A system administrator using the assistant in another tenant leaves the tool calls in that tenant's trail and the conversation in the system tenant's. Carrying a conversation on after a new sign-in is an `assistant.reattached` event. [The operating page](../operating/assistant-budget.md#what-the-audit-trail-records-of-a-turn) has the limits.

### How long it is kept

Only the retention pass below deletes an event. Events are not signed or chained, so whoever holds the database owner's login could change them: export what you must keep somewhere that person cannot reach.

Events are kept 90 days by default, set per tenant with `audit_retention_days`. `odudu reap` removes older ones on a schedule ([configuration](../reference/generated/configuration.md), [command](../reference/generated/cli.md)).

## Working with consent and audit

1. Write a clear `consent_text` for every scope a person might be asked about.
2. Turn `consent_required` on for any client you do not run yourself.
3. Choose a retention that matches your rules, and export what you must keep longer.
