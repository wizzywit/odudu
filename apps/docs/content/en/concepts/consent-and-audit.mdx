# Consent and audit

Two questions come up afterwards. A person asks: what did I let that app see? An administrator asks: what happened on Tuesday, and who did it? Consent answers the first. The audit trail answers the second.

_In words: A client asks, the person decides and a grant is recorded, so the person is asked again only when a client wants more. Separately, the audit trail records sign-ins and refusals, sessions, tokens and administrator changes. Both are kept for each tenant, and audit events are kept 90 days by default._

## Consent

When a client asks for scopes, Odudu can stop and show the person a **consent screen**. It lists what the client wants, in the words you wrote for each scope. The person allows or denies. Denying sends them back with `access_denied`.

An allow is **recorded**: one grant for this person and this client, holding the scopes they ticked. The next time the same client asks for the same things, there is no screen. It appears again only if the client asks for more than was recorded.

### When the screen appears

Odudu decides in this order:

1. If the request says `prompt=consent`, ask, whatever the client is set to. A request that would be granted `mcp:write` is asked at every sign-in, whatever is recorded, and `prompt=none` refuses it.
2. If the client registered itself, or arrived as a metadata document, and this person has no grant recorded for this exact client, ask. The client's own setting does not matter here, and `prompt=none` refuses with `consent_required`.
3. If the client does not require consent, carry on without the screen.
4. If everything it asks for is already recorded, carry on.
5. If something is missing and the request says `prompt=none`, refuse with `consent_required`, because `none` means the person must not be shown anything.
6. Otherwise, ask.

`consent_required` is a setting on each client. An administrator's clients leave it off by default; a client that registered itself has it on. `odudu seed client --consent-required` creates one that asks.

A client nobody at the tenant vetted is held to step 2 until the person approves it. The approval belongs to that client's id alone: allowing one app never allows another with the same name.

### Looking at and removing grants

An administrator can list a person's grants with `GET /admin/tenants/{tenant}/subjects/{id}/consents` and remove one with `DELETE /admin/tenants/{tenant}/subjects/{id}/consents/{clientId}`, and the person is asked again.

### A client that names itself

A tenant can let an app identify itself with an https address (`cimd_enabled`) or let an agent register itself (`client_registration_policy` set to `mcp`). Anyone can claim a name, so such a client is held to step 2. For an app that identifies itself with an https address, the screen shows the host the document came from and every redirect address. An agent that registers itself says so and lists its redirect origins. Neither kind is ever offered `mcp:write`, and a request that names it is answered without it. The [Settings page](../admin-console/settings.mdx#client-registration) has the details, and the [registration transcript](../reference/transcripts/request-paths/bootstrap.md#the-mcp-policy) shows each refusal.

## Audit

Every tenant keeps an **audit trail**. Each entry says what kind of event it was, what happened, who or what did it, to what, the outcome, when, and from where. It never holds a secret.

It records:

- **sign-ins**, including failures and lockouts;
- **sessions** that were started or ended;
- **tokens** that were issued, refreshed or revoked, and families revoked for reuse;
- **credentials** that were created or changed, and recovery codes issued or revoked;
- **changes an administrator made**, through the admin API or the console.

Read it with `GET /admin/tenants/{tenant}/audit`, filtered or exported. The [audit events reference](../reference/generated/events.md) lists every event, action and reason.

### Refusals are bounded

Anybody can cause a refusal as often as they like, and each is a row, so one is recorded only where something limits how many a caller can cause. A registered client gets up to 20 refusal rows a minute. The last says the budget ran out, and later ones go to the server's log. A failed client login naming a client nobody registered writes no row. A sign-up with an address that already has an account writes one row naming that account, limited by the sign-up form's budget per address.

### An agent in the trail

When an AI agent acts through the MCP endpoint, each tool call, reads included, is an `agent.tool_call` event. The actor is the person who signed in and the actor client is the agent's client. The details name the tool and the admin route, never the arguments. A refused call is recorded too. A change made with `mcp:write` is also a `client.amend` or `scope.amend` event naming the agent's client and the person, with the text before and after.

### How long it is kept

Nothing in the server or the admin API edits or deletes an event, apart from the retention pass below. Events are not signed or chained, so whoever holds the database owner's login could change them: export what you must keep somewhere that person cannot reach.

Events are kept 90 days by default, set per tenant with `audit_retention_days`. `odudu reap` removes older ones on a schedule ([configuration](../reference/generated/configuration.md), [command](../reference/generated/cli.md)).

## Working with consent and audit

1. Write a clear `consent_text` for every scope a person might be asked about.
2. Turn `consent_required` on for any client you do not run yourself.
3. Choose a retention that matches your rules, and export what you must keep longer.
4. Find something odd in the trail by who, what and when.
