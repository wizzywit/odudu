# Consent and audit

Two questions come up afterwards: what did I let that app see, and what happened on Tuesday, and who did it? Consent answers the first, the audit trail the second.

_In words: A client asks, the person decides and a grant is recorded, so the person is asked again only when a client wants more. Separately, the audit trail records sign-ins and refusals, sessions, tokens and administrator changes. Both are kept for each tenant, and audit events are kept 90 days by default._

## Consent

When a client asks for scopes, Odudu can stop and show the person a **consent screen**. It lists what the client wants, in the words you wrote for each scope. The person allows or denies. Denying sends them back with `access_denied`.

An allow is **recorded**: one grant for this person and this client, holding the scopes they ticked. The screen appears again only if the client asks for more than was recorded.

### When the screen appears

Odudu decides in this order:

1. If the request says `prompt=consent`, ask, whatever the client is set to. A request that would be granted `mcp:write` is asked at every sign-in, whatever is recorded, and `prompt=none` refuses it.
2. If the client registered itself, or arrived as a metadata document, and this person has no grant recorded for this exact client, ask. The client's own setting does not matter here, and `prompt=none` refuses with `consent_required`.
3. If the client does not require consent, carry on without the screen.
4. If everything it asks for is already recorded, carry on.
5. If something is missing and the request says `prompt=none`, refuse with `consent_required`, because `none` means the person must not be shown anything.
6. Otherwise, ask.

`consent_required` is a setting on each client. An administrator's clients leave it off by default; a client that registered itself has it on.

A client nobody at the tenant vetted is held to step 2 until the person approves it. The approval belongs to that client's id alone: allowing one app never allows another with the same name.

### Looking at and removing grants

An administrator can list a person's grants with `GET /admin/tenants/{tenant}/subjects/{id}/consents` and remove one with `DELETE /admin/tenants/{tenant}/subjects/{id}/consents/{clientId}`, and the person is asked again.

### A client that names itself

A tenant can let an app identify itself with an https address (`cimd_enabled`) or let an agent register itself (`client_registration_policy` set to `mcp`). Anyone can claim a name, so such a client meets step 2. For an app that identifies itself with an https address, the screen shows the host the document came from and every redirect address. An agent that registers itself says so, names where this request sends the person, and lists the other origins it registered. Neither kind is ever offered `mcp:write`. The [Settings page](../admin-console/settings.mdx#client-registration) has the details, and the [registration transcript](../reference/transcripts/request-paths/bootstrap.md#the-mcp-policy) shows each refusal.

## Audit

Every tenant keeps an **audit trail**. Each entry says what kind of event it was, what happened, who or what did it, to what, the outcome, when, and from where. It never holds a secret.

It records:

- **sign-ins**, including failures and lockouts;
- **sessions** that were started or ended;
- **tokens** that were issued, refreshed or revoked, and families revoked for reuse;
- **credentials** that were created or changed, and recovery codes issued or revoked;
- **changes an administrator made**, through the admin API or the console.

Read it with `GET /admin/tenants/{tenant}/audit`, filtered or exported. The [audit events reference](../reference/generated/events.md) lists every event, action and reason.

### Refusals are bounded

Anybody can cause a refusal, and each is a row, so one is recorded only where something limits how many a caller can cause. A registered client gets up to 20 refusals a minute. The last says the budget ran out, and later ones go to the server's log. A failed client login naming a client nobody registered writes no row. A sign-up with an address that already has an account writes one row naming that account, limited by the sign-up form's budget per address.

### An agent in the trail

When an AI agent acts through the MCP endpoint, each tool call, reads included, is an `agent.tool_call` event. The actor is the person who signed in and the actor client is the agent's client. The details name the tool and the admin route, never the arguments. A refused call is recorded too. A change made with `mcp:write` is also the console's event for that change. Access-changing, credential and destructive operations are not available to an agent yet ([classes](../guides/protect-an-mcp-server.md#what-an-agent-can-and-cannot-do-and-why)). A message override and the display name are live on sign-in pages and mail the moment they are saved, with nothing checking them for links. A manipulated agent could publish text it read elsewhere. Review what an agent reads; overrides are audited with their text, and one tool clears them.

### A change the console assistant proposes

The console assistant changes nothing by itself. In Act mode a change it proposes is stored as an approval for the administrator whose conversation it is, with a card the server writes from the call and from the state it read, and the assistant waits. Only that administrator, from their own console sign-in, can approve it: no token the assistant or any agent holds can, and no other administrator. Approving lets that one change run once, exactly as the card shows it, under a grant made for it alone that ends when it returns. A change whose value would not fit the card whole, a long stylesheet or template for one, is not proposed at all: the assistant says so and the person makes that edit in the console. At most five changes wait in one conversation and ten for one person, so one answer cannot use up the allowance other agents ask for. An approval the person never answered, because they went on, can be spent only until it expires and never after the tool call it was for was closed. A sign-in can have at most 20 approved assistant writes in all, because they draw on the same allowance as any agent's writes under that sign-in. The deciding is an `assistant.approval` event naming the person, the conversation, the approval, the tool and the state, and never the change or any message text. The change itself is an `agent.tool_call` event, like any other tool call, and the console's own event for what it changed.

### What the audit trail holds of an assistant turn

Each turn of the console assistant is two `assistant.turn` events, `started` and `ended`, naming the person, the conversation, the turn, the profile, the mode and the model slot; the `ended` event adds the tokens by slot, the steps and why the turn stopped, and a turn that hit a token limit is `refused` and one that failed is `failed`. Neither holds message text, tool output or the name of anything in your tenant: the trace, which has an owner and a retention of its own, is where a conversation is read. The audit fails closed. A turn does not begin when its first event cannot be written, so the model is not called and nothing is reserved, and a tool call whose `agent.tool_call` event cannot be written does not return its data to the assistant; that event names the conversation and the turn it was made in. The `ended` event is written after the turn has settled, and a failure to write it is logged without changing the answer the person saw.

### How long it is kept

Nothing in the server or the admin API edits or deletes an event, apart from the retention pass below. Events are not signed or chained, so whoever holds the database owner's login could change them: export what you must keep somewhere that person cannot reach.

Events are kept 90 days by default, set per tenant with `audit_retention_days`. `odudu reap` removes older ones on a schedule ([configuration](../reference/generated/configuration.md), [command](../reference/generated/cli.md)).

## Working with consent and audit

1. Write a clear `consent_text` for every scope a person might be asked about.
2. Turn `consent_required` on for any client you do not run yourself.
3. Choose a retention that matches your rules, and export what you must keep longer.
4. Find something odd in the trail by who, what and when.
