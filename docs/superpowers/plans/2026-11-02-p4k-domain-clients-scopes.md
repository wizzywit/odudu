# P4k domain 5: client and scope entities, two features, pages/clients and pages/scopes

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development. Steps use checkbox syntax.

**Goal:** what other slices read of a client or a scope lives in `entities/client` and `entities/scope`; the scope-to-client assignment journey and the role-mapping editor are features with two consumers each; the capability rules each have one owner; `features/clients` and `features/scopes` become `pages/clients` and `pages/scopes`, with no behaviour changed.

**Spec:** `docs/superpowers/specs/2026-11-02-p4k-frontend-architecture-design.md`. Parent: `2026-11-02-p4k-frontend-architecture.md`, tasks D-A to D-G. Model: `2026-11-02-p4k-domain-roles-groups.md`.

## Global constraints

Those of the domain-4 plan apply unchanged: layer order `app > pages > widgets > features > entities > shared`; a feature imports no page, no other feature and, unless it is a waiting slice, no widget; entities and shared import no upper layer, an entity imports no entity, shared imports no entity; an index exports only `ui|use-cases|services`, type-only free; a repository or adapter function other slices call goes through a thin use-case re-export (precedents `entities/subject/use-cases/subjectCalls.ts`, `entities/tenant`); adapters never in an index; use-cases reach adapters only through the repository segment; a service imports an entity index for types only (`entities/area`, `entities/administrator` excepted) and any slice's `types/`, so a rule that needs an entity value takes it as an argument; migrated views import no service or repository; files named for concepts, under 300 lines; a new file under `shared/` adds an inventory entry the ratchet refuses, so shared files only grow in the sense that nothing domain-named is added. Every task ends with `pnpm format:check && pnpm lint && pnpm typecheck && pnpm boundaries && pnpm test:unit` plus `pnpm --filter @odudu/docs test`. Inventories and the baseline shrink in the commit that resolves them. Dispatches quote the comment rules and the heavy-slot lock. This domain starts after domain 4 is merged: it edits `pages/groups` (Task 6).

## Rulings

- **Entity `client`** = `Client` type (wire field names kept; `ClientRecord` and the rest of the 45 contract imports stay page types), address (`clientsHref`, `newClientHref`, `clientHref`, `clientsTrail`; the `'Clients'` label is a literal, a page test asserts it equals `areaAt('clients').label`, precedent `'Subjects'`), `ClientPicker` + `useClientPicker` (use-case `clientPicker.ts`). Consumers beyond the slice: audit, branding, email, scopes. **Entity `scope`** = `Scope` type, address, `useScopePicker` (moved from `clients/repository/useClientScopes.ts`), and the two assignment calls `assignScope`/`unassignScope` with their adapter test (from `shared/adapter/scopeAssignment`), exposed as `use-cases/scopeCalls.ts`. Consumers: audit, clients (picker, calls), scopes. Alternative rejected: one `entities/assignment` (an entity imports no entity, and the call is a write on a scope, path `scopes/:id/clients/:id`).
- **`features/scope-assignment`** = `useAssignmentFlow`, `AssignmentControls`, the wording (`ASSIGNMENTS`, `ASSIGNMENT_RULE`, `assignmentOf`, `assignedText`, `unassignedText`). Two consumers, both pages, each side reading a different list and rebasing a different cache (`useScopeChanges`, `useClientAssignment`), so the two page hooks stay and the feature holds the one-change-in-flight state, the controls and the words. It imports no entity (`Counterpart` is `{id,name}`). `AssignmentControls` takes its `choices` and the rule text from the page's view model, so its view imports no service. Alternative rejected: put the flow in `entities/scope` (a journey with toast and refusal reporting is not what a scope is).
- **`features/role-mapping`** = `RoleMapping` view (`SaveSection` + `MappedRoles` + `RolePicker` + the kept-roles note, with `description`, `empty` and `children` for what only one side adds) and `useRoleMapping` (the `role_ids` field, `choose`, `mapped`, `kept`, `offered`; takes `unavailableOf` and `saveRoles`). `pages/groups` keeps its loss gate and dialog around the returned `save`; `pages/scopes` adds its pointer line as a child. Placed here by the domain-4 plan, "when scopes migrates and there are two consumers". Alternative rejected: leave both (verified identical behaviour, 60 duplicated lines per side, two tests of one rule).
- **No `entities/capability`, no ceiling feature** (domain 4's evidence stands). **`Reach` is not an instance of `Ceiling<Ready>`:** it judges one client's service account (`free` when none exists), carries no caller and cannot fail (the record's own `ReadGate` handles that). It stays as one type in the page, named `ServiceAccountReach`, pointing at `Ceiling` in a one-line comment. Variants kept: `reachLine` says "…so you cannot change {name}." where `beyondText` says "…cannot change what {name} holds."; pinned by `ceiling.test.ts` and `ClientRecordPage.test.tsx`.
- **Order.** Entities (Task 5), features (Task 6), then `git mv` (Task 7): audit imports `clientHref` and `scopeHref` and must be repointed to the entities first.
- **Placed out, by name.** The 3 `clients -> features/branding` imports: after the move a page importing a feature is legal and the sideways rule is blind to it (domain-3 finding); domain 7 (`branding`) extracts `clientScope`/`useScopeEdits`/the client-branding editor as a feature. `SCOPES_PAGE` "show N, N more" (`clients/services/scopes.ts:12`) and `listCount` vs `byteSizeReading` (`lists.ts:12`, `format.ts:128`): audit A rows 250/253 have 4 and 2 other copies, 3 of them in branding, so domain 7 owns one `shown` helper and one `limitReading`. camelCase of `Client`/`Scope` fields and the contracts-only-in-adapter sweep: the close, after domain 5, as in domain 4.
