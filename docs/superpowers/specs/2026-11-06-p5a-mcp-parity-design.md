## 1. Goal and the owner's decisions

When P5a closes, an agent holding `mcp:read` can read everything the admin console can read that is not a
secret, personal data or credential metadata, and an agent holding `mcp:write` can make every change the console
offers that is **content**: it changes what a person reads, not who may do what. Everything that changes who can
access what, returns a secret, or cannot be put back by a call waits for P5b, with a human-confirmation step.

Decisions the owner has made (2026-11-06):

1. Reads and reversible writes reach parity with the console in this phase, drawn at **access-changing**, not at
   reversible (section 2 says why).
2. Access-changing writes (W2), credential and secret-returning operations (C) and destructive operations (D)
   are accepted as a **later phase, P5b, on the condition that it is documented there so no later session misses
   it**. Section 8 and the plan's Increment 19 place it in seven named places, each pinned by a test.

Anti-goals, unchanged from the P5a design: no tool is the control (the admin door and the owner's capabilities
are); no token is forwarded; nothing here widens what an `mcp:read` token may do.

## 2. The classification model

One class per route. A route whose body mixes classes is served only by a tool whose fields are exactly its W1
fields (the admin door admits a write by field); section 4 classes every field of each mixed route.

| Class | Meaning                                                                                                                                                                                                      | This phase                                                                   |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| R     | read; no secret, no personal data beyond the subject record, no credential metadata                                                                                                                          | a tool                                                                       |
| RS    | sensitive read: personal data, credential metadata, secrets, whole-tenant or byte downloads                                                                                                                  | stays refused at the tool layer and at the admin door (`AGENT_DENIED_READS`) |
| W1    | content write: wording, descriptions, drafts, structure that grants nothing                                                                                                                                  | a tool, behind `mcp:write`, admitted by field                                |
| W2    | access-changing write, reversible by another call: grants, mappings, redirect and grant settings, security settings, identity fields, anything that goes live on a credential page, anything that sends mail | P5b, with human confirmation                                                 |
| C     | returns or sets a credential or secret: passwords, client secrets, registration tokens, key material, relay credentials, imports that carry secrets                                                          | P5b, with human confirmation                                                 |
| D     | destructive: deletes, ends sessions, clears locks, changes signing keys, discards drafts                                                                                                                     | P5b, with human confirmation                                                 |
| I     | instance-level read (no `:tenant`): the tenant list and its count; creating a tenant is W2 and importing one is C                                                                                            | the two reads                                                                |
| N     | not data: HTML rendered for a browser frame                                                                                                                                                                  | never a tool; the console frames it by address                               |

**Why the line is access, not reversibility.** "Reversible" is a property of the data: a redirect URI or a role
grant is reversible too, after the damage. What matters for an injected agent is whether one wrong call changes who
can get in or what a token carries. W1 cannot: its worst case is wrong text a person reads, the class of harm the
shipped client name on the consent screen already carries. W1 also includes **additive** creates (a role, group or
scope with no grants): the agent cannot delete what it creates, so an injected agent can only add clutter, bounded
by the budget in section 5.

## 5. Safety design for expanding writes

The door and the owner's capability stay the control; nothing below is a tool-side promise.

1. **Per-route allowlist, by method and field.** `AGENT_WRITE_ROUTES` is typed `method: 'PATCH'` today
   (`agent-scope.ts` line 5); it widens to `'PATCH' | 'POST' | 'PUT' | 'DELETE'` and each entry carries a
   `body: 'fields' | 'whole'` mode. `fields` is the shipped check; `whole` (the theme draft PUT, whose body is
   the draft) admits the draft's own members and nothing else. A route with no entry is refused, so the 79
   remaining routes stay refused by default.
2. **Idempotency-Key on every POST a tool makes.** The admin API takes the key as an optional header
   (`answerRoute` runs without one). The caller sends one on each POST, and a create tool requires an
   `idempotency_key` argument (a pattern-checked token) that the client supplies and keeps the same across its
   retries. The key is never derived from the MCP request id: a retry is a new JSON-RPC request with a new id, so
   a derived key would let the retry create a second role. A create without a key is refused before any call. `noIdempotency` routes (domains verify, smtp test)
   are not W1, so none is affected.
3. **Preconditions.** `If-Match` is required by every tool that amends an existing resource (`if_match`, as the
   two shipped tools); the theme tools take the draft's etag from their own read and send it, answering the
   admin API's `428` for a first draft by sending none.
4. **Read-merge-write for the theme.** The draft PUT replaces the whole draft ("a part left out is absent"), and an
   agent reads text cut at 1,000 characters, so a tool that sent back what the agent read would destroy the
   draft. The tool takes only the parts it changes, reads the current draft in full inside the tool, merges and
   PUTs with `If-Match`; a draft over what the caller may send is refused with a plain problem ("use the console").
   `REQUEST_BODY_CAP_BYTES` (65,536) is per-tool configurable, 512 KiB for the two theme tools (assumption: the
   caller's 1 MiB read cap and `THEME_BODY_LIMIT` of 4 MiB leave room; Increment 18 measures).
5. **Write budget.** The limiter has a request budget (60 a minute a principal). A write token lives at most 600 s
   and is never refreshed, so a per-token budget of **20 mutating calls and 10 creates** (a create spends both) is
   two counters on the token's grant, `token_grants.agent_writes` and `agent_creates`, spent before the call runs by
   one `UPDATE ... WHERE agent_writes < 20 [AND agent_creates < 10]`, which the row lock makes atomic: of any number
   of calls made at once no more than the limit are admitted, in this process or another. A call the admin API
   answers with a 4xx changed nothing and gives its place back; a timeout, an unreachable admin API or an answer too
   large to read keeps it, since the change may have been made. A count of `agent.tool_call` rows was the first
   draft and cannot do this: a row is written after the call, so calls made at once would all pass the count
   before any row existed. Over budget: `429` `mcp:write_budget`, and a `refused` row with the reason
   `write_budget`. The count applies only to calls made through the MCP endpoint: a principal that reaches the admin
   API directly (`odudu mcp` over stdio, which keeps a budget in memory per process) is held by the field gate alone.
   An allowlist entry that creates something is therefore restricted to principals that came through the endpoint
   (`viaEndpoint`): the door admits every entry that is not a `PATCH` (a `POST` creates a row, a `PUT` of a message override
   can create one, a `DELETE` removes one) to a token the endpoint signed and to no other agent token, and refuses one whose
   owner is a service account (`agentWriteNeedsEndpoint`), by the method, so a later entry is held without a flag. A
   `PATCH` changes fields of what exists and neither adds nor removes a row, so it stays open to every
   agent token, the settings amendment included. A token issued to an agent that calls the admin API itself, which is
   what `odudu mcp` over stdio does for a person's sign-in and for a service account's key, may amend a description, a
   name, the display name and the languages, and may not create, set or clear: the command does not list those tools and
   the door refuses one sent by hand. Counting at the door instead would have set a second counter beside the endpoint's and
   the command's in-memory one.
6. **Audit.** Each write already records `agent.tool_call` and the mutation's own event with before and after
   (`redactedDiff`). The mutation actions exist (verified: `git grep -n "message_override.set\|theme.draft_saved\|role.create"
-- packages/domain-audit/src/service/admin-mutation-actions.ts`); the scope amendment once wrote no `detail`, so
   each increment checks that its action's row carries the diff of the W1 fields and no other, and fixes a gap in
   the admin API, which owns it.
7. **Injection suite, extended per write class.** `apps/server/tests/mcp-prompt-injection.int.test.ts` gains one
   scenario for each class of write shipped (structure, localisation text, settings text, theme drafts): the
   scripted agent obeys instructions planted in that class's reads (a role's description, a message override, the
   stylesheet, `list_tenants` display names). Required result for every scenario: against `mcp:read`, zero rows
   change; against `mcp:write` with an owner lacking the capability, zero rows change and each refusal is a
   `capability.refused` row; against a fully capable owner, only W1 fields change, and a body naming any W2 field
   sent past the tool is refused by the door (six refusals per route, as for clients today). A fixture asserts
   that the table of section 3 and the allowlist agree, so a W2 field cannot be added to an allowlist by accident.
8. **Consent and lifetime.** `mcp:write` is asked about at every sign-in and lasts at most 600 s with no refresh
   token (`decideConsent`, `capLifetimeForScope`), unchanged and sufficient for W1.
9. **One scope or two?** Recommendation: **no `mcp:admin` in this phase.** W1 as drawn contains no personal data,
   no access and no secret, so a second scope would ask the person the same question twice and cost three more
   places (scope definition and backfill, `holdsMcpScope` and `scopeAdmits`, the consent wording lint
   `mcp-scope-wording.test.ts`). User attributes, the area that would justify a second scope, are W2 here. P5b's
   human-confirmation step is the right second factor for everything riskier, not a broader standing scope.

Cost of the budget in 5 is one single-row `UPDATE` by primary key per mutating call: no hot path.

## 6. Instance-level reads: `list_tenants` and `count_tenants`

What `crossTenant` means: `whoami` reports `principal.issuerTenantId !== targetTenantId`
(`packages/protocol-admin/src/view/routes/whoami.ts` line 35), and `authorizeAdmin` demands `manage-tenants`
whenever it is true. A route with no `:tenant` in its pattern targets the **system tenant**
(`targetTenantNameFor`, `router.ts` line 107), so for a holder of `manage-tenants`, who lives in the system tenant,
a call to `GET /admin/tenants` is not cross-tenant; for anyone else it is, and is refused.

verified: `sed -n 107,114p packages/protocol-admin/src/view/routes/router.ts`; `sed -n 44,62p
packages/protocol-admin/src/usecase/authorize-admin.ts`; `expandPattern` (`packages/mcp/src/service/admin-path.ts`)
fills `:tenant` from the token and so leaves a pattern without one untouched, assumption: confirmed by a unit
test in Increment 12.

The allowance, and nothing wider:

1. Two entries leave `AGENT_DENIED_READS` and `NOT_TOOLS` and become tools `list_tenants` and `count_tenants`
   (capability `manage-tenants`, `valueTool`/`pageTool` over `listTenantsQuerySchema`, `countTenantsQuerySchema`).
2. `scopeAdmits` gains a rule: these two routes admit an agent only when the token's tenant is the system tenant
   (`isSystemTenantId`), so a tenant-local owner's agent is refused by the door before capability is judged.
   The `tenant` argument stays refused (`expandPattern`): no tool reads another tenant's data in this phase, so
   a system administrator's agent sees the list and cannot open one tenant's clients (section 10 decision 3).
3. `toolVisible` already lists a tool only when the owner holds its capability; `manage-tenants` is not in
   `TENANT_CAPABILITIES`, so Increment 12 checks that `whoami`'s capability set reaches the visibility filter.
4. Output carries other tenants' `display_name`, free text written by those tenants' administrators: `data` label
   and `cleanData` as for every read; the injection suite has a scenario with a hostile display name. The
   worst an obeyed instruction can do is a W1 write in the system tenant.
5. Volume: 10,000 tenants, listed by cursor under `MAX_LIMIT`; the route is served by its existing name index
   (assumption: the `query-plans` job, `.github/workflows/verify.yml` line 346, already has an entry for the tenant
   list; Increment 12 greps the plan inventory for it and adds one if absent).

Volume of the structure creates (Increment 16): a tenant defines at most `ROLE_LIMIT` = 1,000 roles (a client's own
among them) and `GROUP_LIMIT` = 10,000 groups, as it defines at most `SCOPE_LIMIT` = 1,000 scopes. `createRole` and
`createGroup` take the tenant row's lock, count no further than the limit and refuse the create `409`
(`a tenant defines at most N roles`), for every caller; a tenant that holds more keeps what it has. The constants are
in `@odudu/contracts` and are meant to be retuned in that one place. The count is a bounded `select count(*)` over a
`limit` subquery, held by the query-plans job as the scope count is.

## 9. Size and where the risk sits

Estimate: **19 new tools** (17 reads, `list_tenants`, `count_tenants`) and **10 new write tools** plus one extended,
across **8 increments** (12 to 19), roughly 28 to 38 hours of implementer work, plus review loops.

Risk concentration, highest first:

1. **W1 text that goes live to people:** `set_message_override` (sign-in page wording), `update_tenant_text_settings`
   (`display_name` on pages and mail), and the shipped client name. Mitigations: consent every grant, 600 s,
   audited before and after, put back by the same call.
2. **Theme draft tools:** stylesheet and template text is the largest agent-authored surface; drafts never go
   live, so a human reviews in the console and publishes. The risk is moved, not removed, to that person's attention.
3. **Reads of text others authored:** theme markup, message overrides, other tenants' display names. These feed an
   injected agent; the damage is bounded by section 5's field gate.
4. **Additive creates:** clutter, bounded by the budget.

Not a risk class in this phase: personal data, credentials, grants, redirects, settings that change security.

## 10. Decisions

The owner accepted every recommendation below on 2026-11-06 ("go with recommendation"). Decision 2 carries a
residual risk the documents must say plainly: a message override or the tenant display name is live wording
on credential pages, so an agent that read hostile text and held `mcp:write` could mislead a person at the
point where they type a password. It is reversible, audited with before and after, bounded by the write
budget and by the owner's own capability, and P5b re-examines it once a human-confirmation step exists.

1. **The line at access-changing** (section 2) rather than at reversible. Recommend: as drawn.
2. **Message overrides and the tenant display name as W1**, although they appear on credential pages. Recommend: W1,
   consistent with the shipped client name on the consent screen; the alternative is W2 and costs the localisation
   half of console parity.
3. **No `tenant` argument for a system administrator's agent**, so no tool reads another tenant. Recommend: none
   in this phase; revisit in P5b with confirmation.
4. **A second scope.** Recommend: none (section 5.9).
5. **User attributes (subject profile) as W2**, not W1. Recommend: W2: the claims reach relying parties, the
   read is RS, and the verification flags are trusted by them.
6. **Theme image upload** is W1 in kind but needs a binary payload and returns nothing the agent can see.
   Recommend: P5b, with the other uploads, rather than a base64 path in this phase.
7. **Mail previews** (N): rendered HTML for a frame. Recommend: never a tool; the draft's `get_theme_preview_info`
   covers what an agent needs.
8. **Per-token write budget** of 20 mutating calls and 10 creates (section 5.5). Recommend: as stated.
9. **Long text in reads:** raise the 1,000-character cut to 128 KiB for the theme's stylesheet and templates only
   (the cut makes a theme unreadable; every other field keeps it). Recommend: yes, by a named field list.
10. **`POST /subjects/bulk`:** never offered to an agent, even in P5b (wide blast, no console screen).
