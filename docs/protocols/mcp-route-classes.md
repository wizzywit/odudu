# MCP route classes

Which class each admin API route is in, and so whether an AI agent holding an MCP token may reach it. The
admin door (`AGENT_WRITE_ROUTES`, `AGENT_DENIED_READS` in `packages/protocol-admin/src/service/agent-scope.ts`) and the
owner's own capabilities are the control; the tool catalogue (`packages/mcp/src/service/catalogue.ts`) is what an
agent is offered, and this page is what both are judged against. `tests/docs/mcp-route-classes.test.ts` holds the
table to `ADMIN_ROUTES` and to the catalogue in both directions, so a new route, or a route that moves to a tool,
fails the build until its row says so.

An agent holding `mcp:read` can read every route of class R, and the two reads of class I when it signs in to the
system tenant. An agent holding `mcp:write` can today make twelve writes of class W1, through twelve tools: `update_client_metadata`
(a client's name and description), `update_scope_metadata` (a scope's description and display order),
`update_role_description` and `update_group_description`, `create_role`, `create_group` and `create_scope`, which
add a role, a group or a scope that grants nothing, and, for the wording people read on the sign-in pages,
`update_tenant_text_settings` (the display name and the languages), `set_message_override` and
`clear_message_override`, and, for what the sign-in pages look like, `update_theme_draft` and
`update_client_theme_draft`, which save a draft that nothing shows until a person publishes it. The door admits no
field of a route it has no allowlist entry for. Everything else waits for P5b, which adds a step the agent cannot
answer for itself.

## The classes

One class for each route. A route whose body mixes classes is served only by a tool whose fields are exactly its W1
fields, and the admin door admits the write by field, so a body that names anything else is refused
`403 insufficient_scope` whatever a tool says; the field table below classes every field of each such route.

| Class | Meaning                                                                                                                                                                                                      | Placement                                                                    |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| R     | read; no secret, no personal data beyond the subject record, no credential metadata                                                                                                                          | a tool                                                                       |
| RS    | sensitive read: personal data, credential metadata, secrets, whole-tenant or byte downloads                                                                                                                  | refused at the tool layer and at the admin door (`AGENT_DENIED_READS`)       |
| W1    | content write: wording, descriptions, drafts, structure that grants nothing                                                                                                                                  | a tool, behind `mcp:write`, admitted by field                                |
| W2    | access-changing write, reversible by another call: grants, mappings, redirect and grant settings, security settings, identity fields, anything that goes live on a credential page, anything that sends mail | P5b, with human confirmation                                                 |
| C     | returns or sets a credential or secret: passwords, client secrets, registration tokens, key material, relay credentials, imports that carry secrets                                                          | P5b, with human confirmation                                                 |
| D     | destructive: deletes, ends sessions, clears locks, changes signing keys, discards drafts                                                                                                                     | P5b, with human confirmation                                                 |
| I     | instance-level read (no `:tenant`): the tenant list and its count; creating a tenant is W2 and importing one is C                                                                                            | a tool, for an agent of the system tenant whose owner holds `manage-tenants` |
| N     | not data: HTML rendered for a browser frame                                                                                                                                                                  | never a tool; the console frames it by address                               |

**Why the line is access, not reversibility.** "Reversible" is a property of the data: a redirect URI or a role
grant is reversible too, after the damage. What matters for an injected agent is whether one wrong call changes who
can get in or what a token carries. W1 cannot: its worst case is wrong text a person reads, the class of harm the
client name on the consent screen already carries. W1 also includes additive creates (a role, group or scope with no
grants): the agent cannot delete what it creates, so an injected agent can only add clutter, and the write budget of
20 changing calls and 10 creates for each token bounds that.

**Who may add or remove.** A write that is not an amendment adds a row or removes one: a POST creates, a PUT of a
message override or of a first theme draft can create one, a DELETE removes one. The budget that bounds them is spent by the MCP endpoint, and only
the endpoint spends it, so the door admits every allowlist entry whose method is not PATCH to a token the endpoint signed
(`viaEndpoint`) and to no other agent token, and refuses one whose owner is a service account
(`agentWriteNeedsEndpoint` in `agent-scope.ts`, derived from the method, so a later entry is held with no flag). Nothing
bounds an amendment that way, because it changes fields of what exists and cannot make or remove a
row, so the PATCH entries, the settings one included, stay open to every agent token. An agent that calls the admin API
with a token issued to it, which is what `odudu mcp` over standard input and output does, whether the person signs in or
a service account does, may amend (a description, a name, the display name and the languages) but cannot create, set or
clear: that command does not list `create_role`, `create_group`, `create_scope`, `set_message_override`,
`clear_message_override`, `update_theme_draft` or `update_client_theme_draft`, answers one called by name as an unknown tool, and the door answers `403 insufficient_scope`,
and records the refusal, to one sent by hand. A service account that reaches the endpoint has no person whose sign-in
the endpoint counts, so it is refused them too and is not offered them. The alternative was to count at the door, which
would have meant a second count beside the endpoint's own and the command's in-memory one; a refusal keeps one place
where they are counted. Over the endpoint each grant is held to 10 creates and 20 changing calls in all, and the admin
API's own bounds apply to each (a scope past `SCOPE_LIMIT`, a role past `ROLE_LIMIT`, a group past `GROUP_LIMIT` and a
tenant's 501st message override are refused `409`).

The kinds in `NOT_TOOLS` are the same classes by another name, and `NOT_TOOL_KINDS` maps them: `denied` and
`sensitive` are RS, `not-useful` is N, `content` is W1 (a write no tool serves yet), `access-changing` is W2,
`credential` is C and `destructive` is D. The reason of an `access-changing`, `credential` or `destructive` entry
begins with its class and says why, and names no phase.

## How many

All **152 routes** are in exactly one class.

| Class | Routes |
| ----- | ------ |
| R     | 59     |
| RS    | 8      |
| W1    | 13     |
| W2    | 32     |
| C     | 7      |
| D     | 27     |
| I     | 2      |
| N     | 4      |

Of the 13 W1 routes, 12 are meant for a tool and **12 of them have a tool today**; the thirteenth, the theme image upload, needs a binary payload and
answers nothing an agent can read, so a person uploads images in the console.

## Changing a class

A route's class is changed here, in the same commit as the catalogue entry or the allowlist entry that moves it, and
never to make a test pass: a route whose tool is added without its row changing class fails the test above, and
that failure is the point. A route enters W1 only when a wrong call can do no worse than put wrong text in front of a
person; anything that changes who can sign in, what a token carries, a secret or a deletion is W2, C or D.
