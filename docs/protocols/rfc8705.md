# RFC 8705 — OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens

**Status in Odudu:** `tls_client_auth` (§2.1, the PKI method) is in scope
for P3b, per the design spec's §8.5, implemented as the **proxy-header
variant**: Odudu never terminates TLS itself (README.md's deployment
section), so it never performs the TLS handshake §2 describes directly.
Instead, a trusted reverse proxy performs the mutual-TLS handshake, and
Odudu trusts a header that proxy sets, gated on `ODUDU_TRUST_PROXY` and the
proxy's own obligation to strip a caller-supplied copy of that header
first. That substitution is what governs which clauses below can be
`covered` at all, and the first reading note is the standing account of it.

§2.1.1 (the `tls_client_auth` metadata _value_, as opposed to §2.1.2's
metadata _parameters_) and §2.2's own body carry no capitalized RFC 2119
keyword and are not rowed, the same convention `rfc7009.md`'s §3 uses.
**§2.2 (Self-Signed Certificate Mutual-TLS Method), §2.2.1 and §2.2.2 are
entirely out of scope**: `self_signed_tls_client_auth` is not a value
`client-metadata.ts`'s `AUTH_METHODS_PERMITTED` accepts, and the section
carries no MUST/SHOULD/MAY of its own to row regardless — it is prose
describing an alternative method, symmetrically with how §2.1's own body
carries none. §1 (Introduction) is non-normative background and out of
scope. §5 (Metadata for Mutual-TLS Endpoint Aliases) — a second, parallel
set of endpoints for a deployment that wants mutual TLS optional on some
routes and required on others — carries three rows below despite being
unimplemented: unlike §2.2, it does contain RFC 2119 keywords, and rowing
them `gap`/`n/a` is what keeps that absence honest rather than assumed.
`mtls_endpoint_aliases` itself is OPTIONAL server metadata and gets no row,
the same convention every other OPTIONAL parameter in this table follows.
§6 (Implementation Considerations) and §7 (Security Considerations) are
commentary except where noted in the reading notes below. §8 (Privacy
Considerations) and §9 (IANA Considerations) impose nothing on an
implementation and are not rowed.

**§3 (Mutual-TLS Client Certificate-Bound Access Tokens), §3.1–§3.4, and §4
(Public Clients and Certificate-Bound Tokens) are not implemented at all.**
Certificate-bound access and refresh tokens are sender-constrained tokens,
already named as **P13**'s own criterion in `docs/request-paths.md`'s "What
is not implemented" ("No DPoP or other sender-constrained tokens, mTLS-bound
tokens included"). Every MUST/SHOULD in §3 that binds the authorization
server itself is rowed `deferred: P13` below, not silently excluded — the
requirements addressed to the client or the protected resource, which
Odudu is neither of, are `n/a` instead.

## Reading notes

### TLS termination and certificate trust are the proxy's, not Odudu's

§2's own first MUST is that the TLS connection "MUST have been established
or re-established with mutual-TLS X.509 certificate authentication." Odudu
cannot observe this directly — it terminates no TLS connection of its own
(README.md's deployment section) — so this MUST is met by the reverse
proxy the deployment puts in front of it, never by a handshake Odudu
itself performs or inspects. §6.5 is what makes this a compliant reading
rather than a gap: "An authorization server or resource server **MAY**
choose to terminate TLS connections at a load balancer, reverse proxy, or
other network intermediary. How the client certificate metadata is
securely communicated between the intermediary and the application server,
in this case, is out of scope of this specification." Odudu exercises
exactly that MAY, and the "out of scope" half is where `ODUDU_TRUST_PROXY`,
`ODUDU_TLS_CLIENT_CERT_HEADER` and the proxy's own obligation to strip a
caller-supplied header (README.md's deployment section, step 4) fill the
gap the RFC deliberately leaves open.

§7.4 (X.509 Certificate Spoofing) draws the consequence out explicitly:
"To cope with that threat, the authorization server **SHOULD** only accept,
as trust anchors, a limited number of CAs whose certificate issuance policy
meets its security requirements." Odudu holds no CA trust store of its own
and makes no such decision — the proxy terminating TLS does, by whatever
`ssl_client_certificate`/`ssl_verify_client` configuration it runs, which
is exactly why README.md's deployment section states the proxy "must also
actually verify the certificate (nginx's `ssl_verify_client on`, not
`optional_no_ca`)" as a hard requirement rather than a suggestion. The
obligation is met, but never by this process.

§7.5 (X.509 Certificate Parsing and Validation Complexity) goes further,
naming the reason a bespoke implementation is the wrong place for any of
this: "implementors **SHOULD** use an established and well-tested X.509
library... and **SHOULD NOT** attempt to write their own X.509 certificate
validation procedures." Odudu parses no X.509 certificate at all — it
never sees the DER bytes, only a string a proxy already validated and
extracted — so both halves are met by construction, not by a library
choice this process had to make.

All three rest on one assumption this document states rather than proves:
that the proxy strips any caller-supplied copy of the certificate header
before setting its own. `infra/conformance/proxy/nginx.conf` is the one
proxy configuration this repository ships with `ODUDU_TRUST_PROXY=true`
set, and it clears the header for exactly this reason.

### The subject comparison is exact-match, not `distinguishedNameMatch`

§2.1's own body notes "that a predictable treatment of DN values, such as
the distinguishedNameMatch rule from [RFC4517], is needed in comparing the
certificate's subject DN to the client's registered DN" — prose, not a
keyword, so it is not rowed on its own. `tlsClientAuthSubjectMatches`
(`packages/protocol-oidc/src/service/tls-client-auth.ts`) answers it with
exact string comparison after trimming surrounding whitespace, a stated
simplification rather than `distinguishedNameMatch`'s per-attribute,
per-encoding normalization — correct only as far as the proxy emits the
subject in one stable, canonical form every time. The comma-bearing
renderings a certificate authority actually produces (RFC 2253's own
escaping, and the `oneline`/`compat` forms openssl and older proxies emit)
are what this simplification has to tolerate without being mistaken for a
duplicated header; `ODUDU-TLS-CLIENT-AUTH-DN-MATCH-01` and
`ODUDU-TLS-CLIENT-AUTH-HEADER-01` are the tests that hold it to that, and
neither traces a clause of its own — nothing in §2.1 requires a specific
matching algorithm, only "a predictable treatment", which naming the
simplification here (rather than promoting it to a MUST this repository
does not implement) is what discharges honestly.

### What "enforcing the binding" is, row by row

§2's third MUST — "The authorization server MUST enforce the binding
between client and certificate" — is one sentence covering several
distinct checks `authenticateTlsClientAuth`
(`packages/protocol-oidc/src/usecase/token-issuance.ts`) performs in
sequence, split into three rows below rather than one so that each can name
the test that actually proves it: `RFC8705-2-01` that a `client_id` was
even presented (§2's second MUST, its own row), `RFC8705-2-02` that the
named client is real, enabled, confidential and registered for this
method, and `RFC8705-2-03` that its certificate's subject actually matches.
A certificate presented alongside another authentication method (a body
`client_secret`, `Authorization: Basic`, or a `client_assertion`) is
refused under RFC 6749 §2.3's own one-method-per-request MUST
(`RFC6749-2.3-01`, `docs/protocols/rfc6749.md`), not a distinct RFC 8705
clause; `ODUDU-TLS-CLIENT-AUTH-ONE-METHOD-01` is the tls_client_auth-specific
regression coverage for that shared rule, not independent proof of it. A
duplicated certificate header (`ODUDU-TLS-CLIENT-AUTH-DUPLICATE-HEADER-01`),
a deployment-configured header name
(`ODUDU-TLS-CLIENT-AUTH-HEADER-NAME-01`), cross-realm isolation
(`ODUDU-TLS-CLIENT-AUTH-REALM-ISOLATION-01`) and registration refused on a
deployment that cannot honour the method
(`ODUDU-TLS-CLIENT-AUTH-REGISTRATION-GATE-01`) are this implementation's own
engineering around that enforcement, not text any RFC 8705 clause states in
these words, so none of them traces a row either.
