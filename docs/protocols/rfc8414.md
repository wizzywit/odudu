# RFC 8414 — OAuth 2.0 Authorization Server Metadata

**Status in Odudu:** in scope in full. A tenant publishes the document so a
client that knows only a resource (an MCP server, per RFC 9728) can find the
authorization server, its endpoints and what it supports without being told
out of band. §1 (Introduction), §4 (Authorization Server Metadata
Registry), §5 (Compatibility Notes), §6 (Security Considerations) and §7
(IANA Considerations) carry no capitalized requirement that binds Odudu and are
not rowed. §5 is why a client may also read `openid-configuration`, which
Odudu keeps serving (`docs/protocols/oidc-discovery.md`). Clause text read
2026-11-05 from rfc-editor.org/rfc/rfc8414 (verified: fetched
`https://www.rfc-editor.org/rfc/rfc8414.txt`).

## Reading notes

### One document, projected from discovery

`resolveAsMetadata` (`packages/protocol-oidc/src/usecase/as-metadata.ts`)
resolves the tenant's OpenID discovery document and projects the members RFC
8414 defines from it (`asMetadataDocument`, `packages/contracts/src/as-metadata.ts`),
so `issuer`, the endpoints, the supported methods and `authorization_response_iss_parameter_supported`
cannot differ between the two documents; a test compares every member both state.
What differs is deliberate. `scopes_supported` gains `mcp:read` and `mcp:write`
here and not in discovery, because they are advertised for a client that
reads this document and not scopes the tenant defines as rows. The three
`..._auth_signing_alg_values_supported` members exist here because §2
requires them wherever `private_key_jwt` is advertised.

### Two URLs, because an issuer is one string

§3.1 inserts the well-known suffix between the host and the issuer's path.
A tenant at the path address has the issuer `<base>/tenants/<name>`, so its
document is `GET /.well-known/oauth-authorization-server/tenants/<name>` on
the base host. A tenant at a verified domain has an issuer with no path, so
its document is `GET /.well-known/oauth-authorization-server` on that host
(ADR 0049). The host's rewrite files that request under
`/tenants/<name>/.well-known/oauth-authorization-server`, which answers only
when the request came through a domain: at the path address the same URL is
`404`, because the issuer's own metadata URL is the other one. The issuer is
always `addressIssuer` of the request's `TenantAddress`, never built from
`Host`.

A tenant that switched address answers at the address it left for the
window ADR 0049 sets, stating the issuer of the address it is read at, and
after it with the empty `404` every other path of that address gives.

### A disabled tenant and an unknown one are the same 404

Discovery still describes a disabled tenant, since it still publishes the
keys its queued logout tokens are signed with. This document points clients
at a token endpoint, which a disabled tenant refuses, so it answers `404`
with no body for a disabled and for an unknown tenant alike; the two cannot be
told apart. `access-control-allow-origin: *` is sent, as discovery does.

### The issuer's scheme

§2's "https" requirement for `issuer` and `jwks_uri`, and §3's for the
well-known path, are the operator's: every URL here is derived from the
configured public address (`ODUDU_PUBLIC_BASE_URL`) or the verified domain, and
in production the server refuses plain HTTP without `ODUDU_TLS`
(`apps/server/src/config-guard.ts`). Local development serves `http`, which
the document then states honestly. Accepted rather than enforced a second time.

### One URL per issuer

§3 permits publishing at several well-known locations. Odudu publishes this
document only at the one each issuer form derives, and the OpenID discovery
document at its own: the two are different suffixes, not copies at different
places.

### Members beyond RFC 8414

§3.2 lets other members appear, and Odudu publishes none: every member is one
RFC 8414 §2 defines, including `ui_locales_supported`. The OIDC-only members
(`claims_supported`, `userinfo_endpoint`, `end_session_endpoint`, the logout
members) are left to the discovery document. `client_id_metadata_document_supported`
is not published until the server resolves client ids that are URLs.
