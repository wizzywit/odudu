# RFC 8693 — OAuth 2.0 Token Exchange

**Status in Odudu:** in scope for P4a, which adds
`urn:ietf:params:oauth:grant-type:token-exchange` as a fourth grant at
`/token`. A client may exchange an access token, a refresh token or an ID
token — resolved without consuming the credential it was handed — for an
access token, an ID token or a refresh token, named by
`requested_token_type`; when absent, the issued type defaults to an access
token, a discretion §2.1 explicitly leaves to the authorization server. An
`actor_token` alongside the `subject_token` produces a delegation, nesting
an `act` claim; its absence produces an impersonation, gated per client by
`tokenExchangeImpersonationAllowed` (`client_oidc_config`). Every issued
shape is capped at the subject token's own expiry, scope only ever narrows,
and the target audience is single-valued, inheriting
`docs/protocols/rfc8707.md`'s decision. §1 (Introduction), §1.1
(Requirements Notation) and §1.2 (Terminology) are non-normative and out of
scope, the same reason every other file in this directory skips them. §4.2
(the `scope` claim) and §4.3 (the `client_id` claim) carry no RFC 2119
keyword — both are pure format descriptions, the value a JSON string and a
client identifier respectively — and get no rows, for the same reason
`oidc-discovery.md` gives OPTIONAL metadata no rows. §5 (Security
Considerations) and §6 (Privacy Considerations) contain no capitalized
keyword of their own; where either motivates a real decision here, a
reading note below says so. §7 (IANA Considerations) registers the grant
type, the request and response parameters and the JWT claims themselves,
not a value Odudu would add to any of those registries, and is not rowed.

## Reading notes

### The four JWT kinds, and why `:jwt` is refused

This issuer signs four kinds of JWT, each carrying a `typ` that tells them
apart: an access token (`at+jwt`), an ID token (no `typ` at all, per OIDC
Core convention), a Logout Token (`logout+jwt`) and a UserInfo response
(`userinfo+jwt`). Section 3's generic
`urn:ietf:params:oauth:token-type:jwt` identifier names none of them — it
names "a JWT this issuer signed," which would accept all four
interchangeably at a grant whose entire purpose is minting a credential for
a third party. `userinfo+jwt` exists because this exact confusion already
happened once: before that private type was minted, a signed UserInfo
response could be presented as an `id_token_hint`, since both were JWTs
from the same issuer with nothing else to distinguish them. Accepting the
generic identifier here would reopen the same confusion one door further
in, at the endpoint that mints new credentials rather than merely verifies
existing ones. `parseTokenType`
(`packages/protocol-oidc/src/service/token-exchange.ts`) refuses it
outright instead of guessing at which of the four kinds it might mean.

### Scope attenuation is this server's policy, not RFC 8693's requirement

No clause in §2.1 or §2.2.1 bounds the issued token's scope by the subject
token's — the `scope` request parameter only names what is desired for the
target service, and an authorization server that issued a wider scope than
the subject token ever carried would still conform to this RFC. Odudu
refuses that anyway: `attenuateScope`
(`packages/protocol-oidc/src/service/token-exchange.ts`) treats any
requested scope the subject token did not hold as `invalid_scope`. The
reason is the design spec's own attenuation invariant (§9: "child scopes ⊆
parent scopes; strictly attenuating, never widening"), written for the
agent layer P5 builds on top of this grant. A token exchange that could
widen scope would make that invariant unenforceable one layer up, so it is
enforced here instead, regardless of which layer next reads it.

### One target, not many

§2.1's MAY — that `resource` or `audience` may each be specified more than
once, naming several resources the issued token is intended for — is
declined, the same way `docs/protocols/rfc8707.md`'s "`resource` stays
single-valued: declined, not absent" declines it for every other grant. A
token usable at several independently registered resources trades away the
narrowing this server's `resource`/`audience` handling exists to provide,
for a trust relationship nothing in Odudu's client or audience model
establishes. `resolveExchangeAudience`
(`packages/protocol-oidc/src/service/token-exchange.ts`) refuses more than
one named target, and refuses `resource` and `audience` naming different
ones, rather than resolving either into a token spanning both.

### An ID token is not a grant

An ID token records no grant: no `grant_id`, no scope persisted anywhere.
Exchanging one therefore yields no scope at all — a different shape of
"nothing to attenuate" than an access or refresh token's inherited grant
scope, which is why `resolveIdToken`
(`packages/protocol-oidc/src/usecase/token-exchange-subject.ts`) returns an
empty scope rather than a maximal one. An ID token's `aud` is also already
fixed, by OIDC Core §3.1.2.2's delivery rule, to the client it was minted
for — the same rule `resolveIdToken` enforces when resolving one as a
`subject_token` in the first place. Naming a `resource` or `audience` for
an issued ID token would ask this grant to widen an audience OIDC Core
already fixed by a different mechanism, so `resolveExchangeAudience`
refuses a named target for that shape rather than silently ignoring it.

### The issued token's expiry is capped at the subject token's, across every later rotation too

§2.1 permits this without requiring it — the issued token's validity period
"may be influenced by the expiration of the subject_token" — leaving the
choice to the authorization server. Odudu enforces it as a hard ceiling on
every issued shape alike: access token, ID token and refresh token all
derive their expiry from `expCeiling`, computed once from the subject
token's own `exp` and threaded through `mintAccessToken` and the two other
issuance branches (`issueExchangedTokens`,
`packages/protocol-oidc/src/usecase/token-issuance.ts`). Every other grant
this server issues mints from a credential the client owns outright, so
that client's own configured TTL is the only ceiling; this grant mints from
a credential the client was handed, and letting an exchange outlive what it
was exchanged from would let a delegated or impersonated credential quietly
outlast the thing that authorized it in the first place. Stricter than
every other grant here, deliberately.

The ceiling does not end at the token this grant first issues. An exchanged
refresh token rotates through the ordinary `refresh_token` grant like any
other, and the ceiling is persisted on the grant row itself
(`token_grants.exp_ceiling`, migration `0060_token_grants_act_chain.sql`) so
`issueRefreshTokens` and `rotateRefreshToken` can reapply it on every hop —
capping both the minted access token's `exp` and the replacement refresh
token's own `expiresAt`, never resetting either to a fresh
`refreshTokenTtlSeconds` — proven through two successive rotations, not
just one, by `ODUDU-TOKEN-EXCHANGE-ROTATION-01`. Without this, the cap held
only until the first
rotation: a client rotating an exchanged credential once would have gotten
a token that outlives the subject token it was exchanged from, silently
undoing the paragraph above.

### The `act` chain also survives rotation, persisted the same way

A grant this table wrote for an ordinary `authorization_code` or
`client_credentials` redemption carries no delegation to reapply, so
`token_grants.act_chain` (migration `0060_token_grants_act_chain.sql`,
alongside `exp_ceiling` above) is null for every grant that was never a
token exchange, and `issueRefreshTokens` reapplies it only when it is not.
Before this, rotating an exchanged refresh token silently produced an
undelegated access token: `issueRefreshTokens` passed neither `act` nor the
ceiling to `mintAccessToken`, so the first rotation of a delegated
credential dropped who was acting for the subject, nesting and all.
`narrowActClaim` (`packages/protocol-oidc/src/service/token-exchange.ts`)
reads the persisted JSON back into an `ActClaim`, rejecting anything
malformed or deeper than `MAX_DELEGATION_DEPTH` the same way `buildActChain`
does at exchange time, rather than trusting a column no other write path
touches. `ODUDU-TOKEN-EXCHANGE-ROTATION-01` proves a genuinely nested
chain — two levels, not one that would pass either way — survives two
rotations with its shape intact.

### The subject token's own `act` chain is not nested

`buildActChain` nests the _actor_ token's own prior `act` beneath the new
actor (`issueExchangedTokens`'s `buildActChain(actorSubject,
actor.token.act)`). The _subject_ token's own `act` claim — resolved into
`ResolvedExchangeToken.act` by every one of `resolveAccessToken`,
`resolveRefreshToken` and `resolveIdToken`
(`packages/protocol-oidc/src/usecase/token-exchange-subject.ts`) — is read
but never consulted when the new chain is built. A subject token that
already carries a delegation history, because it was itself minted by an
earlier exchange, has that history dropped rather than nested beneath the
new actor. Nothing today constructs such a token to exercise this path —
no exchange output is yet fed back in as a further exchange's own
`subject_token` — so the divergence has produced no observed defect. It is
real and unaddressed regardless, and is recorded here rather than justified.

### Why an exchange error carries no extra detail

§2.2.2's MAY permits additional information about the reason for a
failure; this grant never emits any, on the same footing as
`invalidGrant()`'s own discipline at the `authorization_code` path
(`ResolveOutcome`'s own comment,
`packages/protocol-oidc/src/usecase/token-exchange-subject.ts`). A subject
or actor token can fail resolution for reasons from "malformed" to
"syntactically fine, but the grant behind it was revoked," and telling
those apart in the response would hand a caller probing with someone
else's token a way to learn something about it. `invalid_request` alone,
deliberately, the same way `ODUDU-TOKEN-EXCHANGE-ORACLE-01` pins the
impersonation check ahead of it for the identical reason.
