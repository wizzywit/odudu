# RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens

**Status in Odudu:** in scope for P1 in full. Odudu's design (design spec
§2.5) already commits to this profile: access tokens are JWTs typed
`at+jwt`, signed by the realm key, verifiable offline against `/jwks`;
refresh tokens stay opaque. §1 (Introduction) is non-normative and out of
scope. §2.2.1 (Authentication Information Claims — `auth_time`, `acr`,
`amr`) and §2.2.2 (Identity Claims) are OPTIONAL and get no rows, for the
same reason `oidc-discovery.md` gives OPTIONAL metadata: the level column
has no slot for it, and a row would not trace a requirement. §2.2.3
(Authorization Claims — `scope`, `groups`/`roles`/`entitlements`) has two
rows for the MUST and SHOULD claims on `scope`; naming `groups`, `roles`
and `entitlements` at all (§2.2.3.1) is OPTIONAL and gets no row, but its
one SHOULD — encoding their values per RFC 7643 — is not optional to trace
and gets the row below. §7 (IANA
Considerations) registers the media type and claim names; it imposes
nothing on an implementation and is out of scope.

## Reading notes

### The `resource` parameter and audience configuration

The design spec's "audience configuration" sits alongside consent and
dynamic client registration — admin-facing provisioning features, about how
audiences get configured on a client. The `resource` parameter is something
different: a request-time input to the authorization code grant. P1 shipped
the grant without reading it — a client sent `resource`, Odudu ignored it,
and `aud` was populated from the client's configured audiences instead — and
that deviation stayed a visible `gap` rather than a silent one until P3b
closed it. `/authorize` resolves and validates `resource`
(`parseResource`, `packages/protocol-oidc/src/service/resource-indicator.ts`)
and stores the result on the code; `/token` now derives `aud` from that
stored value, narrowed further by a `resource` the token request itself
names, and never widened past it (`resolveAudience`,
`packages/protocol-oidc/src/usecase/token-issuance.ts`) — the same function,
reused against the client's own configured `audiences`, decides a
`client_credentials` grant's `aud`, which has no code to narrow. §3's row
about honouring a supplied `resource` parameter closes below against that
mechanism. Inferring a default resource indicator from `scope`, and
refusing a `scope` that names several of them, are not attempted — nothing
in this server's scope model names a resource at all — and those two rows
stay `gap`.

**The default resource indicator itself is a different matter, and was held
before `resource` existed anywhere in this server.** §3's "if the
authorization request includes no `resource` parameter, the authorization
server uses a default resource indicator" requires `aud` to be populated
from somewhere other than the request when the request names nothing, and
it is: `resolveAudience` returns its `base` argument verbatim when no
`resource` narrows it, and that `base` is the client's configured
`audiences` at `/authorize` and at a codeless `client_credentials` grant, or
the code's own stored `resource` (or, on a refresh, the rotated grant's
`audience`) everywhere else — never re-read from `config.audiences` after a
`resource` has already narrowed it once. `RFC6750-5.3-02` asserts the
resulting `aud` value byte-for-byte, for the no-`resource`-anywhere case,
rather than merely asserting the claim is present; the row stays closed
against that test.

**Two rows in that neighbourhood — §2.2.3's "every scope string has meaning
for the resources identified in `aud`" and §3's "does not issue a token if
the authorization it grants would be ambiguous" — close now, against the
same mechanism, rather than staying `deferred`.** RFC 9068 §3 names
its own way to satisfy this: "one way to accomplish this is through the use
of the `resource` parameter as defined in [RFC8707]." A client that names a
`resource` now gets an `aud` naming exactly that one external resource plus
the issuer — never several at once — so whatever scope is granted in that
token is granted for one resource, not asserted across a whole registered
list simultaneously; a client that names none still gets the configured
list verbatim, the same default §3's other MUST already closes above. That
list being coherent for the scopes a client can be granted remains an
operator decision this server does not itself verify — RFC 9068 asks for
the tool that lets a client disambiguate, not for Odudu to police an
operator's own audience configuration, and providing that tool end to end
is what these two rows were waiting on.
`RFC9068-3-03` closes both, run against `refuses a resource at /token that
the code did not carry`, `still mints a token for a client with no
registered audience`, `mints a client_credentials token for the resource
asked for`, `refuses a client_credentials resource the client is not
registered for`, `a refresh preserves the audience the authorization_code
redemption narrowed`, and `a resource on a refresh request cannot widen the
audience back` (`packages/protocol-oidc/tests/resource-token.int.test.ts`).

### Token-type confusion, and what `typ: at+jwt` closes

An OAuth access token and an OpenID Connect ID Token can end up looking
identical to a naive verifier: both are JWTs, both are signed by the same
authorization server, both can carry the same `iss` and pass signature
verification against the same `/jwks`. If a resource server's check is
"a JWT, signed by an issuer I trust," nothing in that check distinguishes
an access token minted for calling this API from an ID Token minted to
tell some client who the user is. A client (or an attacker who obtained
an ID Token some other way — it is disclosed to the client by design)
could hand the resource server an ID Token, and if the resource server
never checks the token's declared purpose, it would validate.
Token-type confusion is exactly this: two token kinds sharing a
representation and an issuer, distinguished by nothing but out-of-band
assumption.

`typ: at+jwt` in the JWT header closes this by making purpose part of
what gets verified, not just claims content. §4 requires the resource
server to check the header's `typ` before it does anything else with the
token; an ID Token — which per OpenID Connect Core carries no `at+jwt`
`typ` value — fails this check immediately, before its `iss`, `aud`, or
`exp` are ever consulted. The defense holds because it is cheap and
mandatory to check first, not because it is hard to forge: a party that
already controls token issuance could set any `typ` it likes. What it
protects against is a resource server built to the letter of "verify
signature, check claims" but missing the type check, since that omission
is exactly the kind of thing that is invisible in code review and only
shows up against an adversarial corpus — which is why Odudu's own such
corpus (design spec §5) includes both `alg: none` and cross-token-type
substitution among its cases.

### §2.2.3.1: `roles`, `groups` and `entitlements` against RFC 7643's schema

All three are IANA-registered JWT claims (RFC 7643 §4.1.2, referenced by
RFC 9068 §2.2.3.1), not something this project invented. §2.2.3.1 also
SHOULDs that their values be encoded "according to the guidance defined
in [RFC7643]" — Odudu does not: `groups` is emitted as a flat array of
strings rather than RFC 7643's complex multi-valued form (`value`, `$ref`,
`display`, `type` sub-attributes), because Kubernetes reads the claim
named by `--oidc-groups-claim` as a list of strings even for a single
value, and ArgoCD, Grafana and Vault all assume the same shape. Recorded
here as a deliberate divergence, the way ADR 0022 records one for this
same claim's membership scope. `entitlements` is not emitted at all —
Odudu has no entitlement concept.

RFC 7643 §4.1.2 does carry MUST/SHOULD text of its own (the `$ref` and
mutability rules for `groups`, canonicalization for `emails`/
`phoneNumbers`, the `photos` MUST), but every one of them binds a SCIM
service provider managing these as SCIM resources. Odudu implements no
SCIM interface, so none of it applies here, and a `docs/protocols/rfc7643.md`
table would be a page of `n/a: no SCIM interface` rows tracing nothing. No
table.
