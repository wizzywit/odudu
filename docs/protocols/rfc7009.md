# RFC 7009 — OAuth 2.0 Token Revocation

**Status in Odudu:** in scope for P3b in full, per the design spec's §8.3:
`/revoke` (`packages/protocol-oidc/src/view/routes/revoke.ts`) resolves the
presented token to the grant it names —
`packages/protocol-oidc/src/usecase/revocation.ts` — and revokes it. §1
(Introduction) and §1.1 (Requirements Language) are non-normative and out
of scope; §3 (Implementation Note) is design background on the trade-offs
between self-contained and handle-style access tokens, with no capitalized
RFC 2119 keyword in it, and is not rowed; §4 (IANA Considerations)
registers the error code and the token-type-hint registry themselves, not
an entry the server would add to either, and is not rowed; §6
(Acknowledgements) and §7 (References) are never rowed.

## Reading notes

### TLS on the revocation endpoint

§2 carries two MUSTs that the revocation endpoint's URL is HTTPS and that
the authorization server uses TLS in a version compliant with RFC 6749
§1.6. Odudu terminates no TLS — `docs/protocols/rfc6749.md`'s reading note
"TLS: what a boot guard settles, and what it does not" is the standing
account of what `assertProductionTls` does and does not prove, and both
rows here are `accepted:` against it rather than newly argued. The
client-side MUST beside them, that the client itself verifies the URL is
HTTPS before using it, is `n/a`: Odudu is the authorization server serving
that URL, not the client validating it.

### The HTTP-fallback SHOULD

§2's SHOULD that a host reachable over HTTP also offers a revocation
service at the corresponding HTTP URI — while never publishing that URI as
_the_ revocation endpoint — reads at first like the same accepted-against-
the-proxy claim as the TLS rows above: Odudu serves plain HTTP behind a
TLS-terminating proxy uniformly, with no code path that distinguishes an
HTTP request from an HTTPS one. That turns out to be the whole answer, now
that `/revoke` and its discovery metadata exist to have a policy about:
there is exactly one URI, `{issuer}/protocol/openid-connect/revoke`
(`discoveryDocument`, `packages/contracts/src/discovery.ts`), reachable
over whichever transport the deployment's own proxy terminates. A second,
HTTP-only address was never built and is never advertised, so the
companion MUST — that no such second URI is published as _the_ revocation
endpoint — holds by construction. Both rows are `accepted:` against this
note.

### Declarative prose in §2.1, §2.2 and §5: explained, not rowed

Six sentences in this RFC describe authorization-server behaviour in the
declarative, with no capitalized RFC 2119 keyword: §2.1's "the
authorization server first validates the client credentials ... and then
verifies whether the token was issued to the client," "if this validation
fails, the request is refused and the client is informed of the error,"
and "the authorization server invalidates the token. The invalidation
takes place immediately"; §2.2's "the authorization server responds with
HTTP status code 200 if the token has been revoked successfully or if the
client submitted an invalid token"; §2.2.1's "the server **may** include a
'Retry-After' header" (lowercase); and §5's "clients **need to** obtain
its location from a trustworthy source only." None carries a level this
table can assert without inventing one — `rfc8707.md`, written in this
same file trio, takes the same position on lowercase and keyword-free
prose for the same reason: §1.1 here is the older, pre-RFC-8174
boilerplate, but a table cannot apply one rule to one file and its
opposite to a sibling without saying why, and no reason to differ is on
record. Each describes real, expected behaviour of `/revoke` once it
exists — a client-ownership check before invalidation, immediate
invalidation, a 200 regardless of whether the token was recognized — and
each is worth the attention of whoever builds `/revoke`, which is what
this paragraph is for. None is a table row.

### An absent `token` resolves exactly like an unresolvable one

§2.1's `token` parameter is REQUIRED, but `respondToRevocationRequest`
(`packages/protocol-oidc/src/usecase/revocation.ts`) draws no separate line
between "absent" and "present but resolves to nothing": a missing `token`
reads as `''`, which `resolveGrantId` fails to match as a refresh token's
hash and fails to parse as an access token, the same way any other garbage
string does. There is no code path where omitting the parameter answers
differently from sending one this server cannot resolve.

### `token_type_hint` is never read, and both token types are always tried

Neither the route nor the usecase reads `token_type_hint`. `resolveGrantId`
tries a presented value as a refresh token's hash first, and only when that
finds nothing does it try verifying the value as an RFC 9068 access token —
unconditionally, on every call, regardless of what a hint might have said.
That is what "extends its token search across all supported token types"
means when there is no hint to extend past: the search already covers both
types every time. `RFC7009-2.1-02` (a refresh token resolves) and
`RFC7009-2.1-04` (an access token resolves) are the same code path
exercising each half.

### Both revocation directions go through the grant, not the token

§2.1's SHOULD (revoking a refresh token also invalidates the access tokens
under its grant) and its neighbouring MAY (revoking an access token also
revokes the refresh token) are one mechanism here, not two: `resolveGrantId`
maps either token to its `token_grants` row, and `respondToRevocationRequest`
revokes that row. An access token is never itself marked invalid — it stays
a validly signed JWT until `exp` — but `introspect`
(`packages/protocol-oidc/src/usecase/introspection.ts`) already refuses any
token whose grant carries a `revoked_at`, which is the same mechanism
`rfc7662.md`'s §8.2 reading note calls "what makes revocation real inside
an access token's hour". `RFC7009-2.1-05` revokes by refresh token and
finds the sibling access token reported inactive; `RFC7009-2.1-04` revokes
by access token and finds a same-family refresh token — including one that
has since rotated — refused on its next redemption. Rotation matters here
specifically: `refresh_tokens` gets a fresh row and hash on every rotation,
but `grant_id` never changes, so revoking the grant reaches whichever row
is current without the usecase needing to know rotation happened at all.

### The revocation endpoint shares `/token`'s and `/introspect`'s client-authentication path

`respondToRevocationRequest` calls the same `authenticateClient`
(`packages/protocol-oidc/src/usecase/client-authentication.ts`) `/token`
and `/introspect` call, including ADR 0023's per-`client_id` budget on
failed `client_secret_basic`/`client_secret_post` attempts
(`clientSecretLimiter`). This is a structural fact about which function the
route calls, not a behaviour with a dedicated test in this repository the
way `ODUDU-INTROSPECT-RATE-LIMIT-01` pins the same sharing at
`/introspect` — §5's row below is `accepted:` against this note rather
than `covered`.

It inherits that path's reach as well as its budget: `authenticateClient`
reads a Basic header or a body `client_secret` and nothing else, so a
client registered for `private_key_jwt` or `tls_client_auth` cannot call
`/revoke` at all. Accepted rather than deferred, for the reasons
`rfc7662.md`'s "Only the two password methods reach this endpoint" gives
for the sibling endpoint.
