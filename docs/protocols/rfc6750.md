# RFC 6750 — OAuth 2.0 Bearer Token Usage

**Status in Odudu:** in scope for P1. The userinfo endpoint accepts bearer
tokens via the `Authorization` header (§2.1) and, on a POST, via the
form-encoded `access_token` body parameter (§2.2). OAuth 2.1 drops the URI
query parameter method (§2.3) entirely, and Odudu never accepts it.

## Reading notes

RFC 6750 defines three ways a client can present a bearer token
(`Authorization` header, form-encoded body, URI query parameter) and one
way a resource server reports a failed request back (`WWW-Authenticate`
with a `Bearer` challenge and one of three error codes). Odudu is the
resource server for its own userinfo endpoint, so §3's `WWW-Authenticate`
requirements and §5's confidentiality requirements are the ones this
implementation is actually judged against; §2's three presentation methods
are mostly about what the _client_ does with the token it already has, and
two of those three — the `Authorization` header and the form-encoded body —
are ones Odudu's resource server accepts.

An earlier reading of this table recorded the form-encoded body method as
`n/a` because "userinfo is a `GET` endpoint with no request body". That
justification contradicted an OpenID Connect Core MUST: §5.3 requires the
UserInfo Endpoint to support GET _and_ POST, and §5.3.1 has a POST carry
its access token as a Bearer Token per §2 of this specification. The
endpoint answers both methods, so the body method is implemented rather
than excused.

§2's "no more than one method" rule is addressed to the client, but a
resource server that silently picks one of two presentations is choosing
which of two claims about the caller to believe. A request carrying the
token in the header and the body at once — or twice in the body — is
refused with §3.1's `invalid_request` and its HTTP 400.

The URI query parameter method (§2.3) is the one place this table's `n/a`
rows come from a project decision rather than an OAuth-2.1-wide one: OAuth
2.1 drops it because a token in a URL query string ends up in server logs,
browser history, and `Referer` headers by default, and RFC 6750 itself
already downgrades it to "SHOULD NOT ... unless it is impossible" for the
same reason. Odudu never accepts it.

§3's requirements are about the grammar of a challenge, not about one
spelling of one challenge, so they are read that way: the test behind
`RFC6750-3-02`, `RFC6750-3-03` and `RFC6750-3-04` drives every branch of
`packages/protocol-oidc/src/view/routes/userinfo.ts` — the only code in
Odudu that emits a `Bearer` challenge — parses each `WWW-Authenticate` it
gets back as an RFC 7235 challenge, and holds the result to §3's
auth-scheme, at-most-once and character-set rules. Those rules are
universally quantified over auth-params, so `scope`, `error_description`
and `error_uri` are covered on the same terms as the `realm` and `error`
Odudu actually emits: an implementation that began emitting a repeated
`scope`, a `scope` value outside NQCHAR, or an `error_uri` that is not a
URI-reference fails those tests today.

§5.2's and §5.3's token-lifetime rows were `gap` for as long as an access
token's lifetime was `client_oidc_config.access_token_ttl_seconds` and
nothing more — a NOT NULL column defaulting to 300 seconds, with nothing
between it and `exp`, so a client provisioned with a day-long TTL got a
day-long token and "one hour or less" was a property of how clients happen
to be provisioned. `client_oidc_config_access_token_ttl_ceiling`
(`packages/db/drizzle/0013_access_token_ttl_ceiling.sql`) makes it a
property of the server: no row above 3600 seconds can exist, whichever
writer attempts it. The test behind `RFC6750-5.2-02` is deliberately not
about a fixture's TTL — a 300-second client would prove only that the
fixture says 300. It asserts that the database refuses to hold anything
longer than an hour, and then issues a token through `/token` for the
longest-lived client that _can_ exist and reads `exp - iat` off it. The
same id answers §5.3's SHOULD because the bound the constraint imposes is
exactly §5.3's hour.

§5.2's "a token's use is restricted to a specific scope" and §5.3's
audience-restriction SHOULD are answered at issuance. Reading them off
what `/userinfo` refuses was the adjacency that kept them `gap`: those
tests establish that a token missing a scope or an audience is turned
away, which is not the same claim as every issued token carrying one.
`RFC6750-5.2-03` reads the `scope` claim off tokens issued for two grants
made for different scopes and holds each to its own, so a claim that did
not track the grant fails it; `RFC6750-5.3-02` holds an issued token's
`aud` to exactly the client's configured audiences plus this issuer.

The two cookie rows are answered by `RFC6750-5.2-04`, which carries a whole
journey — `/authorize`, the login submission, `/token`, `/userinfo` — and
collects every `Set-Cookie` any of them emits. The only cookie there is the
authentication session cookie
(`packages/protocol-oidc/src/view/routes/login.ts`); what the test holds is
that no cookie value contains the access, refresh or ID token the same
journey produced, and that no cookie value is shaped like a JWS Compact
Serialization at all. It also asserts that the journey set at least one
cookie, so it cannot pass by having observed nothing.

### TLS, and the four §5.2 rows a boot guard does not close

Odudu terminates no TLS. `docs/protocols/rfc6749.md`'s reading note "TLS:
what a boot guard settles, and what it does not" is the reading this table
follows rather than deciding again, and it names RFC 6750 §5.2 among the
places where the same claim appears in another specification's words. The
four rows accepted against this note — the server _implements_ TLS, confidentiality
protection _is applied_ to the client's exchanges, that protection prevents
replay, and confidentiality is maintained where a TLS connection terminates
before the resource-providing server — are assertions about the connection
and about a deployment's topology, not about this process. `ODUDU_TLS` and
`NODE_ENV` are what the RFC 6749 rows phrased as _requires TLS_ rest on,
and an operator who sets them in front of a plaintext listener has lied in
a way nothing here can detect. What would close these four is Odudu
terminating TLS itself, or evidence gathered where the TLS connection
actually is — neither of which is a test in this repository.
