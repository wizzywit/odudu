# RFC 10017 — OAuth 2.0 for Browser-Based Applications (BCP 212), section 6.1

**Status in Odudu:** the Backend for Frontend (BFF) pattern of section 6.1 is
what `@odudu-io/bff` implements (ADR 0054). Odudu the server is the
authorization server and has nothing to hold against this RFC; the clauses
below bind the BFF, which is a client. The other architecture patterns (§6.2
token-mediating backend, §6.3 browser-only client) and the threat analysis of
§5 are non-normative background here and out of scope; the browser-only client
is what `@odudu-io/oidc` offers in the page, and ADR 0054 says why it exists
beside the BFF.

Only the BFF's own routes (`login`, `callback`, `session`, `logout`) are
tested here. §6.1.3.6 governs the proxy that forwards a session's access token
to a resource server, which the package does not have yet; its rows are
`deferred:` and the census in `tools/trace/silenced-musts.json` counts them.

## Reading notes

### Cookie attributes

The RFC wants the cookie to be `Secure`, `HttpOnly` and, as SHOULDs,
`SameSite=Strict`, `Path=/`, without a `Domain`, and named with the
`__Host-Http-` prefix. The package sets `Secure`, `HttpOnly`, `Path=/` and no
`Domain` on every cookie, and names them `__Host-odudu` and
`__Host-odudu-login`. It takes two deliberate steps from the SHOULDs, and the clause table carries
them as `accepted:` against this heading:

- **`SameSite=Lax` instead of `Strict`.** The login cookie binds the PKCE
  verifier to the browser that started the sign-in and must come back on the
  issuer's redirect, a cross-site top-level navigation, which `Strict` would
  withhold. The session cookie uses the same value so the two cannot drift. The
  RFC's reason for `Strict` is CSRF from another site; the custom header and
  the `Origin` check in "The custom header and the GET routes" cover it, and
  `Lax` still withholds the cookie from cross-site subrequests and from
  cross-site POSTs.
- **`__Host-` instead of `__Host-Http-`.** The `__Host-` prefix already forces
  `Secure`, `Path=/` and no `Domain`. `__Host-Http-` additionally stops a script
  from setting the cookie, which `HttpOnly` plus a random server-chosen id
  already makes harmless; the older prefix is accepted by every browser that
  accepts the newer one and by more besides. A client that wants the stricter
  prefix cannot have it today, because the name must start with `__Host-` and
  is otherwise free; allowing `__Host-Http-` is an option to add when its
  browser support is settled.

### The custom header and the GET routes

§6.1.3.3.2 asks the BFF to require a custom request header and, when it does,
to ensure that "every incoming request carries" it. The package requires
`X-Odudu-BFF` and an `Origin` equal to an allowed origin on every route that
changes state, which is `logout`. It does not require the header on `login`,
`callback` and `session`: the first two are browser navigations, which cannot
add a header, and `session` is a read with no side effect whose response a
cross-origin page cannot read, because the BFF sends no CORS headers. `login`
writes one record, the login record, bound to the browser by its cookie; it
changes no signed-in state, so a forged request can at most start a sign-in the
person never finishes. When the proxy arrives, every proxied call requires the
header.

### A client without a secret

§6.1.3.1 requires a confidential client. `clientSecret` is optional in the
options so a development setup against a public client works; without it the
BFF is not the architecture of this RFC. The guide says so, and ADR 0054 records
the choice.
