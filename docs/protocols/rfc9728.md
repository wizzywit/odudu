# RFC 9728 — OAuth 2.0 Protected Resource Metadata

**Status in Odudu:** in scope for the one resource Odudu has, a tenant's MCP
endpoint. The document tells a client that was given only the MCP URL which
authorization server to use and which scopes the resource takes; it is what an
MCP client reads after the endpoint's `401` points it here. §1 (Introduction),
§4 (Protected Resource Metadata Registry), §6 (Authorization Server
Metadata), §8 (Privacy Considerations) and the IANA sections carry no
capitalized requirement that binds Odudu and are not rowed. Clause text read
2026-11-05 from rfc-editor.org/rfc/rfc9728 (verified: fetched
`https://www.rfc-editor.org/rfc/rfc9728.txt`).

## Reading notes

### The resource is the MCP URL, and one URL per tenant address

`resolveResourceMetadata` (`packages/mcp/src/usecase/resource-metadata.ts`)
states `resource` as `mcpResourceUrl` of the request's `TenantAddress`
(`packages/mcp/src/service/resource.ts`): the tenant's address plus `/mcp`,
with no trailing slash, because a client compares it as a string (§3.3, §7.3).
`authorization_servers` holds exactly one entry, `addressIssuer` of the same
address, which is the `issuer` the tenant's RFC 8414 document states
(`docs/protocols/rfc8414.md`); clients use only the first entry, so a second
would not be read. `scopes_supported` is `mcp:read` and `mcp:write`, and
`bearer_methods_supported` is `header`, since a token in a query string or a
form body is not accepted. A test compares the two documents' issuer.

### Two URLs, because a resource is one string

§3.1 inserts the well-known suffix between the host and the resource's path.
A tenant at the path address has the resource `<base>/tenants/<name>/mcp`,
so its document is `GET /.well-known/oauth-protected-resource/tenants/<name>/mcp`
on the base host. A tenant at a verified domain has the resource
`https://<domain>/mcp`, so its document is
`GET /.well-known/oauth-protected-resource/mcp` on that host (ADR 0049). The
host's rewrite files that request under
`/tenants/<name>/.well-known/oauth-protected-resource/mcp`, which answers only
when the request came through a domain; at the path address the same URL is
`404`. A tenant that switched address answers at the address it left for the
window ADR 0049 sets, stating the resource of the address it is read at.

### A disabled tenant and an unknown one are the same 404

The document points a client at an authorization server whose token endpoint
a disabled tenant refuses, so it answers `404` with no body for a disabled
and for an unknown tenant alike; the two cannot be told apart.
`access-control-allow-origin: *` is sent, so a browser-based client may read it.

### The challenge

`challengeFor` (`packages/mcp/src/service/challenge.ts`) builds
`Bearer resource_metadata="<url>", scope="<scope>"`, where the URL is
`resourceMetadataUrl` of the tenant's address: the one a client fetches next.
`insufficientScope` builds the `403` form,
`Bearer error="insufficient_scope", scope="<scopes>", resource_metadata="<url>"`
(RFC 6750 §3.1, with the parameter §5.1 adds). Only the `Bearer` scheme is
used. The helpers exist before the endpoint that sends them.

### Members not published

Odudu publishes the four members above and no other: no `jwks_uri` (the MCP
endpoint does not sign anything a client verifies), no `resource_name`, no
`resource_signing_alg_values_supported`, no `signed_metadata`, no
`dpop_*` or `tls_client_certificate_bound_access_tokens` members, because the
endpoint accepts neither. Every rule that applies only to a published member
is therefore not applicable.

### One URL per resource

§3 permits publishing at several well-known locations. Odudu publishes at the
one each address form derives.

### TLS

§7.1's TLS requirement is the operator's: every URL is derived from the
configured public address (`ODUDU_PUBLIC_BASE_URL`) or the verified domain,
and in production the server refuses plain HTTP without `ODUDU_TLS`
(`apps/server/src/config-guard.ts`). Local development serves `http`, which the
document then states honestly.

### Caching

§7.10 recommends caching directives. The document carries none, so a tenant
that is disabled or switches address is read as such on the next fetch; a
client applies its own heuristics.
