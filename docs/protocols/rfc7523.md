## Reading notes

### One refusal, not several

§2.2 gives no guidance on distinguishing failures, and OIDC Core §9 gives
none either — but the two are read together with ADR 0028: a `jwks_uri`
is a client-supplied URL, so whether a request against it succeeds is
exactly what P3a's revert of registration-time dereferencing exists to
keep un-observable. `authenticatePrivateKeyJwt` therefore answers the
same `invalid_client`, with no `error_description` and the same
`WWW-Authenticate: Basic realm="token"` challenge every other `/token`
refusal already sends (RFC 6749 §5.2 expects a challenge matching the
scheme attempted; a distinct one here would itself be the oracle, so this
is a deliberate divergence, not an oversight) — whichever of these eight
failed: the assertion didn't parse, the client is unknown, the client is
disabled, the client's registered method isn't `private_key_jwt`, the
client publishes no keys at all, its key set could not be fetched (the
address guard, DNS, the transport, an HTTP status, a wrong content type,
the size cap, or invalid JSON — one failure, read off one `catch`, not
several), the signature didn't verify (a wrong key, or a fetched value
that is valid JSON but not shaped like a JWK Set), or the `jti` was
already spent. A ninth refusal sits upstream of all eight, in `issueTokens`
itself rather than in `authenticatePrivateKeyJwt`: an assertion presented
alongside Basic or a body `client_secret` (RFC 7521 §4.2 / RFC 6749 §2.3's
one-mechanism-per-request rule). Same bytes, same challenge, and it shares
the same logging closure so it is not the one refusal that logs nothing.
The real reason — for all nine — is logged, where only an operator reads it.

This is not constant-time, and the bound below covers less than it might
look like it does. An unreachable `jwks_uri` first goes through
`deps.lookup(url.hostname)` (`client-keys.ts`'s `fetchFresh`) —
`apps/server/src/client-key-transport.ts`'s `defaultClientKeyLookup`,
`node:dns/promises.lookup` with no timeout of its own — before the
transport's connect and total timeouts (5s / 10s,
`DEFAULT_CONNECT_TIMEOUT_MS` / `DEFAULT_TOTAL_TIMEOUT_MS`) ever apply. A
slow or black-holed resolver blocks for however long the platform
resolver takes, which is unbounded here. So the honest statement is: the
socket phase is bounded at 10s, the DNS phase is not, and a bad signature
answers immediately either way — a caller timing requests can still tell
an unreachable host from a bad signature, and, for a resolver slow enough,
from a merely slow one too. The negative cache (`client-keys.ts`'s
`NEGATIVE_CACHE_TTL_MS`) only shortens repeat attempts at the same uri;
it does not bound the first one. Nothing in this codebase claims a
stronger property than that.

### The assertion's `jti` is claimed after the signature verifies, never before

Claiming a `jti` before its signature is checked would let an assertion
with a forged or absent signature spend a `jti` it never had authority
over — no key required, only the ability to observe or guess a client's
`jti` values. The client's own later, genuinely signed use of that same
`jti` would then be refused as a replay it never made: a denial of
service costing the attacker nothing. `authenticatePrivateKeyJwt` verifies
first, so a failed verification leaves `assertion_jti` untouched. The rest of
how a `jti` is spent is the next note.

### A jti is never waited on, and is spent whatever becomes of the request

Four properties are wanted together: a replay that arrives while the first use
is still running is refused at once; an assertion whose first use is refused
after authenticating is still spent; a request that succeeds takes no connection
beside its own; and a replayer holding one captured assertion cannot park the
pool on it. The first design, a plain `INSERT … ON CONFLICT DO NOTHING` on the
request's transaction, failed the first two: a unique-index conflict _waits_ for
the other transaction, so a replay blocked on the first use's uncommitted row,
and if that use then rolled back the replay's insert succeeded and it
authenticated. Pool-sized numbers of replays could sit on the one row. A claim on
a connection of its own, the design before that, failed the third, and
deadlocked a pool of N under N concurrent assertions.

What is built, in `usecase/private-key-jwt-authentication.ts`:

1. After the signature verifies, `pg_try_advisory_xact_lock` on a hash of
   (tenant, client, `jti`), on the request's own transaction. It never waits. If
   another transaction holds it, that transaction is using this very assertion
   at this moment, so this one is a replay and is refused, `invalid_client`, at
   once. A lock collision between different `jti`s would refuse a genuine
   request; with a 64-bit hash that is a 2⁻⁶⁴ event.
2. Under the lock, a read for a committed row. Present: refused as a replay.
3. The request's work runs (`settle`). On success the row is inserted on the
   same transaction, which commits it, so success costs no second connection. On
   failure, before the transaction rolls back and lets go of the lock, the row
   is inserted on a connection of its own, so there is no instant at which a
   replay finds the lock free and the row absent. If the pool has no connection
   to give, the failing request waits two seconds, logs, and answers its refusal:
   the jti then stays unspent, the one case the guarantee yields to an exhausted
   pool. Nothing in that path can turn a refusal into a `500`.

The row is inserted only after the work, never before it, because a row inserted
early on the request's transaction would block that same insert on a separate
connection (the failure path's) behind the request's own uncommitted row.

Tests: `[ODUDU-PRIVATE-KEY-JWT-04]` races two uses of one assertion that both fail
after authenticating (exactly one reaches the failure, the other is `401`, the
`jti` ends spent, five rounds), spends a jti while the store refuses the write,
and sends N+1 replays on a pool of N beside a refresh grant, which all complete.
`[ODUDU-PRIVATE-KEY-JWT-03]` is N concurrent distinct assertions on a pool of N.

### A `client_id` beside an assertion must name the assertion's client

RFC 7521 §4.2: when `client_id` is sent with a `client_assertion` it must
identify the same client as the assertion's subject. A mismatch is refused
`invalid_client` before the key is looked up (`[ODUDU-PRIVATE-KEY-JWT-05]`).

### No clock tolerance

Neither `parseClientAssertion` nor jose is given any leeway: an assertion whose
`exp` has passed by a second is refused, and a lifetime of 301 s is refused where
300 s is accepted. RFC 7523 §3 lets a server allow a small leeway; none is
allowed because the one client of this server in production is the console's
gateway, which signs on the host that verifies, so there is no skew to forgive,
and any leeway would stretch the window the `jti` memory has to cover. A
third-party client whose clock runs fast by more than the 240 s of headroom a
60-second assertion leaves is refused, and the remedy is its clock, or a longer
assertion up to the ceiling. If a deployment ever needs a tolerance it is one
constant, applied to `exp` and `nbf`, and its cost is that many seconds more of
`jti` retention.
