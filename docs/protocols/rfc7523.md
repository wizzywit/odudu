# RFC 7523 — JWT Profile for OAuth 2.0 Client Authentication and Authorization Grants

**Status in Odudu:** §2.2's `client_assertion`/`client_assertion_type`
client authentication is implemented at `/token`
(`packages/protocol-oidc/src/usecase/token-issuance.ts`,
`authenticatePrivateKeyJwt`), combined with OIDC Core §9's
`private_key_jwt` rules (`iss`/`sub` both the client_id, `aud` the token
endpoint). §2.1's JWT authorization grant (using an assertion in place of
an authorization grant, not alongside client authentication) is out of
scope — P3b's exit criterion is client authentication only. §1
(Introduction) and §5 (Security Considerations) are non-normative or
already folded into the reading notes below; §6 (IANA Considerations) is
never rowed.

## Reading notes

### One refusal, not several

§2.2 gives no guidance on distinguishing failures, and OIDC Core §9 gives
none either — but the two are read together with ADR 0028: a `jwks_uri`
is a client-supplied URL, so whether a request against it succeeds is
exactly what P3a's revert of registration-time dereferencing exists to
keep un-observable. `authenticatePrivateKeyJwt` therefore answers the
same `invalid_client`, with no `error_description`, whichever of these
failed: the assertion didn't parse, the client is unknown, the client's
registered method isn't `private_key_jwt`, the address guard refused the
`jwks_uri`, the host didn't answer, the fetched document wasn't a JWK
Set, the signature didn't verify, or the `jti` was already spent. The
real reason is logged, where only an operator reads it.

This is not constant-time: an unreachable `jwks_uri` takes as long as
`clientKeySet`'s fetch allows before answering (5s to connect, 10s total
— `apps/server/src/client-key-transport.ts`'s defaults) while a bad
signature answers immediately, so a caller timing requests can still
tell the two apart. The negative cache (`client-keys.ts`'s
`NEGATIVE_CACHE_TTL_MS`) only shortens repeat attempts at the same uri;
it does not close that gap. Nothing in this codebase claims a stronger
property than that.

### The assertion's `jti` is claimed after the signature verifies, never before

Claiming a `jti` before its signature is checked would let an assertion
with a forged or absent signature spend a `jti` it never had authority
over — no key required, only the ability to observe or guess a client's
`jti` values. The client's own later, genuinely signed use of that same
`jti` would then be refused as a replay it never made: a denial of
service costing the attacker nothing. `authenticatePrivateKeyJwt` verifies
first, so a failed verification leaves `assertion_jti` untouched; two
concurrent, identically valid assertions still resolve to exactly one
success, because `assertionJtiRepository.claim`'s own atomicity (an
`INSERT … ON CONFLICT DO NOTHING … RETURNING`) is what decides between
them, not request order.
