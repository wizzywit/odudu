# OpenID Connect Core 1.0

**Status in Odudu:** in scope for P1, scoped to the surface reachable from
the authorization code flow: ID Tokens (§2), the Authorization Code Flow
in full (§3.1), standard claims, scopes and the UserInfo endpoint
(§5.1–§5.4), the mandatory-to-implement feature list (§15.1), and security
considerations (§16). The Implicit Flow (§3.2) and Hybrid Flow (§3.3) are
`n/a`: OAuth 2.1 and this phase's design (see
`docs/superpowers/specs/2026-09-11-p1-oauth-oidc-core-design.md` §1)
support only `response_type=code`. Self-Issued OpenID Provider (§7),
Subject Identifier Types (§8), Client Authentication (§9, tracked instead
under RFC 6749), Signatures and Encryption (§10), Offline Access (§11),
Refresh Tokens (§12), Serializations (§13) and String Operations (§14) are
out of this table's scope entirely — not because they are unimportant, but
because they sit outside the four regions this task was scoped to read.

## Reading notes

### `nonce`: binding an ID Token to one authorization request

`nonce` exists because an ID Token, once issued, is a bearer credential
with no cryptographic link back to the request that produced it — nothing
about a validly signed, unexpired ID Token proves it was issued in
response to _this_ authentication attempt rather than a different one for
the same user. A client that generates a fresh, unguessable `nonce` before
sending the Authentication Request and checks it against the ID Token it
gets back closes that gap: the ID Token now carries proof that the OP
processed the exact request the client thinks it did. What this defends
against is replay — an attacker who has captured a previously issued,
still-valid ID Token (from a leaky log, a compromised proxy, a browser
history) presenting it to a client as though it were the answer to a fresh
login attempt the client just initiated. Without a nonce check, the client
has no way to tell a stale, replayed token from a live one. The value
itself is opaque to Odudu: the server's whole obligation is to echo
whatever the client sent, verbatim, in the `nonce` claim, and otherwise
leave it alone (§2 is explicit that "Authorization Servers SHOULD perform
no other processing on nonce values used").

### Why the ID Token's audience is the client, and the access token's is the API

These are two different tokens answering two different questions, and
conflating their audiences is the exact confusion RFC 9068's `at+jwt`
type exists to prevent (see the design's §2.5). The ID Token answers "who
did the user authenticate as, to which client, when" — its consumer is
the RP itself, so its `aud` **MUST** contain the client's `client_id`
(§2). The access token answers "is this bearer allowed to call this API"
— its consumer is a resource server, so its audience is that resource
server's identifier, not the client's. A resource server that skips
verifying the access token's audience and instead trusts any
token signed by the right issuer — the mistake `at+jwt` is designed to
make detectable — could be handed an ID Token (whose `aud` is a client it
already trusts) and treat it as a valid access credential, or accept an
access token minted for a completely different API. Odudu's decision to
type access tokens distinctly from ID Tokens (`typ: at+jwt` vs. a JWT
ID Token) gives a resource server a cheap, mandatory check — reject
anything that isn't typed as an access token — before it ever gets to
comparing audience values.

### `auth_time`: when the user actually authenticated, and when it's required

`auth_time` is the timestamp of the end-user's last active authentication
— not the ID Token's own `iat`, which is just when this particular token
was minted and can be much later than the login itself if a session is
long-lived. It is OPTIONAL by default, but becomes REQUIRED in two cases:
when the request carried `max_age` (the client needs to verify the OP
actually re-checked freshness), or when `auth_time` was requested as an
Essential Claim via the `claims` parameter. Both triggers are out of scope
for P1 for the same reason — `max_age` needs the flow tree semantics P2
builds, and the `claims` parameter needs the per-client machinery P3
builds — but the claim itself is cheap for P1 to support unconditionally:
Odudu's session/authn-flow layer already knows when a user last actively
authenticated, so emitting `auth_time` whenever it's available is a
straightforward addition, and doing so now means the two deferred triggers
have something to attach to when P2 and P3 land.

### ID Token validation (§3.1.3.7): the client's ordered checks

This entire section is addressed to the client — Odudu is the OP being
validated, not the RP doing the validating — but a later task implementing
`/token` needs to know what shape of token a correct client will accept,
because every step here is something Odudu's issuance must not violate.
In order: decrypt if encryption was negotiated at registration; the `iss`
claim must exactly match the OP's issuer identifier; the `aud` claim must
list the client's own `client_id`, and the token is rejected if it lists
an audience the client doesn't trust; if `azp` is present (only relevant
to extensions Odudu doesn't use), it should be checked; the signature is
validated using the algorithm in the JWT header — over a direct
TLS-protected channel (true for the code flow, always) certificate
validation may substitute for a signature check, but the signature is
still validated for every other case; the current time must be before
`exp`; `iat` may be used to bound how long a client stores nonces against
replay; `nonce` must be present and must match if one was sent; `acr`
should be checked if requested; `auth_time` should be checked against any
freshness requirement. Odudu's issuance path is what makes every one of
these checks succeed for a correctly implemented client — a wrong `iss`,
a missing audience entry, a stale `exp`, or a dropped `nonce` all turn
into an RP-side rejection of an otherwise successful login.

### `prompt` and `id_token_hint`: closed in P1, and what is left

§15.1 makes `prompt=login` mandatory-to-implement for every OP, and the
specification's bar for it is narrow: do not reuse an existing session,
and return an error (typically `login_required`) if reauthentication
cannot be performed. A single-step login executor that unconditionally
shows the login form — with no attempt to compare `max_age` or `acr`
against session state — already satisfies that bar; nothing about the
unconditional case needs the flow-tree machinery. What _does_ need flow
tree semantics is _conditional_ reauthentication: deciding, from
`max_age` or a requested `acr`, whether the current session is still
fresh enough to skip a new login. That distinction is why `max_age`-
triggered reauthentication (§2's `auth_time` requirement, §3.1.2.1,
§15.1) stays deferred to P2 while `prompt=login` is answered here.

The same argument covers `prompt=none`, and more cheaply. Its bar is: do
not interact with the end-user, and return an error if the end-user is not
already authenticated and cannot be silently authenticated (§3.1.2.3,
§15.1). `handleAuthorizationRequest` calls `startAuthentication`
unconditionally and never reads the `__Host-<realm>-session` cookie it
later sets, so P1 can never silently authenticate anyone — which makes
"always return `login_required`" a complete and conformant implementation
of `prompt=none` for this server, reached with no session-reuse machinery
at all. It is answered as a redirect, not a rendered page: `login_required`
is an authorization error _response_ (§3.1.2.6), and the request that
carries it has already had its `redirect_uri` matched against the client's
registrations. Whoever builds session reuse in P2 turns this unconditional
answer into a conditional one and must not weaken the rest of it: no page,
no authentication session, no cookie.

`prompt` parsing (`service/prompt.ts`) refuses `none` alongside any other
value, which §3.1.2.1 requires, and refuses a value outside the four the
specification defines, which §3.1.2.1 leaves as a MAY. `consent` and
`select_account` are accepted and have no effect of their own — their own
rows stay deferred to P3 and P2 — so this server recognises them without
yet obeying them.

**The row §3.1.2.1 phrases for `prompt=login`'s failure is `deferred: P2`.**
"An error is returned if reauthentication cannot be performed" has no
reachable branch here: /authorize starts a fresh authentication for every
request that gets that far, and a failed password attempt re-renders the form
rather than ending the authorization request. There is no state in which this
server would have to answer that error, so there is nothing a test could
observe, and marking the row `covered` against the test that proves the form
is shown would be marking a requirement green with an adjacent assertion. It
becomes real in P2, where a session can exist and reauthentication can be
refused — which is what `deferred: P2` says, and is why it is recorded that
way rather than as a `gap` indistinguishable from unfinished work.

`id_token_hint` is a third case that looks like it needs session reuse and
does not. Validating that Odudu issued the hint (§3.1.2.2) is signature and
`iss` checking against the realm's own keys, which `/token` and `/userinfo`
already do — the same publishable set `/jwks` serves, so a hint signed by a
key that has since been retired is no longer honoured. And §3.1.2.1's rule
admits the end-user who "becomes logged in as a result of the request" —
which is every successful P1 login — so honouring the hint means comparing
its `sub` to whoever authenticated. The validated subject rides on the
parked request (`PendingRequest.idTokenHintSubject`) because that
comparison cannot happen until somebody has actually signed in; the login
form has no field for it, and a hidden field would put the constraint in
the hands of whoever is submitting the form.

A hint that cannot be read, or that this server did not issue, is
`invalid_request` at /authorize, and that check runs _before_ `prompt=none`
is acted on: a request carrying an unusable parameter is malformed, and
answering it with the prompt's own `login_required` would report a problem
the client does not have. A hint this server did issue, naming somebody
other than the end-user who then signs in, is `login_required` at the
redirect URI with nothing issued — no code, and no SSO session cookie for a
login the request itself said it did not want. The authentication session
is deliberately left unconsumed, so the end-user the hint names can still
sign in against the same parked request.

**Two `id_token_hint` rows stay `gap`.** §3.1.2.2's SHOULD to accept a hint
past its `exp` is not implemented: `verifyJwt` enforces `exp` for every token
this server reads, and carving out an exception belongs with the session
lookup that would make an expired hint useful in the first place. §3.1.2.1's
MAY to answer `invalid_request` when `prompt=none` arrives without a hint is
declined on purpose — `login_required` describes what actually happened.

**An access token is not an ID Token, and is refused as a hint.** §3.1.2.1
says the parameter carries an ID Token previously issued by this OP, so a
check that asked only "did this realm sign it?" would accept an access token
minted for the same end-user — valid signature, this realm's `iss`, the same
`sub`. What it cannot be is "must be an ID Token": OIDC Core §2 gives an ID
Token no `typ` of its own and the ones `/token` issues carry none, so the
demand that can honestly be made is _must not be an access token_, which RFC
9068 §2.1's `typ: at+jwt` names exactly. `verifyJwt` therefore requires every
caller to state a `typ` policy — the type it demands, a type it refuses, or
`TYP_UNCHECKED` — the way it already requires an audience policy, because
this confusion existed for precisely as long as that option could be left
unsaid. `/userinfo` makes the mirror-image check of the token presented to
it.

**Discovery advertises none of this, deliberately.** OIDC Discovery 1.0 §3
defines no metadata for `prompt`: `prompt_values_supported` comes from
Initiating User Registration via OpenID Connect, the extension that adds
`prompt=create`, and is not part of the document this server publishes.
§15.1 makes `none` and `login` mandatory for every OP, so there is nothing
optional for a client to discover — and a list naming the four values this
server _parses_ would claim the `consent` and `select_account` behaviour it
does not yet have. `packages/contracts/src/discovery.ts` is therefore
unchanged, and no clause row is added for a claim that is not served.

### Response Mode: `query` and nothing else

`response_type=code` defaults to the `query` Response Mode (§3.1.2.1), and
that is the only mode Odudu implements: `fragment` and `form_post` deliver
the authorization response by means this server has no code for. §3.1.2.6
requires an unsupported mode to produce an HTTP 400 carrying no error
response parameters, which is what `/authorize` renders — the mode names
how a response reaches the client, so an unsupported one leaves no way to
deliver an error either, and the check therefore sits above the §4.1.2.1
redirect boundary with the other rendering failures.

A repeated `response_mode` is answered the same way. Collapsing
`response_mode=query&response_mode=fragment` to whichever value was read
first would let a request that did name `fragment` reach the
repeated-parameter rule and be answered with a redirect carrying error
parameters — a response delivered in `query` to a request that also asked
for a mode this server does not implement. It is refused above the
boundary with the other two parameters whose repetition leaves no way to
deliver a response at all (`packages/protocol-oidc/src/service/query-normalization.ts`).

The discovery document states `response_modes_supported: ["query"]` rather
than omitting the member, because OpenID Connect Discovery §3 defaults an
omitted value to `["query", "fragment"]` — advertising a mode `/authorize`
rejects.

### §5.1's `email`: a subset of addr-spec, stated rather than approximated

§5.1 requires the `email` claim to conform to RFC 5322's addr-spec. That
obligation runs one way — what Odudu emits must be a valid addr-spec — and
says nothing about accepting every addr-spec a mail system might. Full
addr-spec admits quoted local parts, parenthesised comments, folding
whitespace and domain literals; a regular expression claiming to implement
all of it and getting it subtly wrong would be worse than a narrower rule
that says plainly what it enforces.

So `packages/domain-identity/src/service/email.ts` enforces a strict
subset — dot-atom local part, dot-atom domain of two or more labels, RFC
5321 §4.5.3.1's octet limits — chosen so that everything accepted is
unambiguously a valid addr-spec.

**Where that subset is enforced is the whole of the claim.** The claim is
emitted verbatim from `users.email`
(`packages/protocol-oidc/src/service/claims.ts`), so the obligation is
true or false of the column, not of any one function that writes to it. A
repository method constrains one writer; it said nothing about a test
helper, a future admin API, a migration or a DBA, and for a while it said
nothing about any path that actually produced a claim either. The column
now carries `users_email_addr_spec`
(`packages/db/drizzle/0012_users_email_addr_spec.sql`), a `CHECK` spelling
the same subset in SQL, so there is no write path that can put a
non-conforming address where the claim is read from.
`userRepository.create` keeps its own check, demoted to what it is: an
earlier, friendlier refusal that names the option an operator got wrong
instead of surfacing a constraint violation.

Two spellings of one rule drift. The integration suite
(`packages/domain-identity/tests/identity.int.test.ts`) runs a fixed list
of addresses — conforming and not — past both the column and
`isEmailAddress` and fails if they ever disagree.

The cost is stated rather than hidden: a user whose real address needs a
quoted local part, a comment, a domain literal or a single-label domain
cannot be stored. Raising that ceiling means implementing the grammar, not
widening the pattern — and now means writing a migration as well, which is
the right amount of friction for changing what a claim is allowed to say.

### The third error parameter §3.1.2.6 does not know about

§3.1.2.6 SHOULDs that an error response carry nothing beyond `error` and
`state`. Odudu's error redirects carry a third parameter, `iss`, because
RFC 9207 §2 — published eight years later, and normative for Odudu —
MUSTs the issuer identifier onto _every_ authorization response, the
error ones above all: an error response steered to the wrong client is
precisely the mix-up attack `iss` exists to defeat. A later
specification's MUST beats an earlier one's SHOULD, so this row is `n/a`
rather than `gap`. Removing `iss` to satisfy §3.1.2.6 would remove the
countermeasure; the obligation lives in `docs/protocols/rfc9207.md`.

### `redirect_uri` at the Token Endpoint: always required in Odudu

OIDC Core §3.1.3.2 permits the authorization server to accept an omitted
`redirect_uri` on the token request when only one redirection URI is
registered for the client. Odudu does not exercise that discretion: the
Authorization Endpoint rejects any Authorization Request that omits
`redirect_uri` before anything else happens, so `redirect_uri` was
necessarily present on every Authorization Request Odudu has ever issued
a code for. RFC 6749 §4.1.3's condition — the parameter is required at
the token endpoint if it was present at the authorization endpoint —
therefore always holds for Odudu. Making it unconditional removes a
branch from the token endpoint rather than adding one.

### §16.3: the signing half of token manufacture/modification carries no keyword

§16.3 describes two independent mitigations for a forged or modified
token: "the token can be digitally signed by the OP" — a plain
descriptive sentence, no RFC 2119 keyword — after which "the Relying
Party SHOULD validate the digital signature to verify that it was issued
by a legitimate OP." Only the second half is a testable RFC 2119
requirement, and it falls on the client, not Odudu; the table below
carries a row for it, not for the unstated signing half, since Odudu
already signs every ID Token unconditionally per §2.

### Where `deferred:` rows land, and one open question

Rows below name two phases: **P2** for anything needing flow tree
semantics (_conditional_ reauthentication triggered by `max_age`,
`prompt=select_account`'s multi-session selection, and `acr`/`amr` values
that report which authentication methods and context were actually
satisfied — all of this waits on the authentication-method modeling P2
does); **P3** for anything needing a consent screen, request objects, or
per-client registration data that doesn't exist until dynamic client
registration lands (`prompt=consent`, signed requests, signed or encrypted
UserInfo responses). `prompt=login`'s own reauthentication behavior is
answered in P1, not deferred — see above. Two items have no phase at all: ID Token
encryption negotiation (§2) and the end-user-facing mechanism to revoke
previously granted tokens (§16.18); see the report's "Scope gaps in the
phase roadmap" section.

### Rows that quantify over a set, and what closing one has to show

Four of §3.1.2.2's obligations are stated over a set rather than over a
case: _all_ the OAuth 2.0 parameters are validated, _all_ the REQUIRED ones
are present and conform, _any_ error ends in a §3.1.2.6 response,
unrecognized parameters are ignored. A test that picks one member of the
set and passes proves the member, not the row — which is how a row comes to
read `covered` while the behaviour it names is only partly there.

So each of these is closed by an enumeration held in the test file itself.
`OIDC-CORE-3.1.2.2-02` names the seven parameters an authorization request
to this server has — RFC 6749 §4.1.1's five, plus the two RFC 7636 §4.3
adds and OAuth 2.1 makes mandatory — and asserts the set it exercises
_equals_ that list, so a member dropped from the table fails the test
rather than shrinking it silently. `state` is the member with no value the
server may refuse: OAuth's rule for it is that it returns unchanged, and
that is what is asserted of it. `OIDC-CORE-3.1.2.2-04` sweeps every
rejection this endpoint has, above the RFC 6749 §4.1.2.1 boundary and
below it, and holds each to one of the two shapes §3.1.2.6 allows — a
bare HTTP 400, or a redirect carrying a registered error code. The same
sweep is what `OIDC-CORE-3.1.2.6-04`, `-05` and `-06` run over, so `error`,
`state` and the query component are claims about every error response
rather than about a chosen one.

The one place these rows are narrower than their words is `scope`. §3.1.2.1
lists it REQUIRED, and an omitted `scope` here resolves to the default
rather than failing — RFC 6749 §3.3 permits exactly that, and the default
is `openid`, the value §3.1.2.2 is asking after. `OIDC-CORE-3.1.2.2-03`
states that exception rather than hiding it.

### §3.1.2.3's two countermeasures, split into two rows

§3.1.2.3 asks for CSRF _and_ clickjacking countermeasures in one sentence,
and for most of P1 one row carried both against one test id — a test that
asserted the CSRF half only. Nothing failed. `reconcile` holds a `covered`
row green so long as every result carrying its id passes, so a row whose
words name two obligations and whose id names a test proving one of them is
indistinguishable, to the tool and to a reader skimming the status column,
from a row that is wholly met. The clickjacking half had no implementation
at all.

The fix is structural rather than a better test. The sentence is two
obligations with two different defences — an unguessable token in the form
against a cross-site _submission_, a framing refusal against a cross-site
_frame_ — so it is two rows, each naming its own test id. Deleting either
test now leaves a row citing an id no test carries, which `reconcile`
reports as an error in both modes. Carrying both halves under one id would
not: dropping one of two test files leaves the surviving one green and the
row with it. The general rule the episode argues for is that a row's
requirement text should name one obligation, and a conjunction in the
specification's words is a reason to split rather than to write a longer
row.

What discharges the second row is in `packages/protocol-oidc/src/view/html-response.ts`:
`Content-Security-Policy: frame-ancestors 'none'` with `X-Frame-Options:
DENY` beside it, on every page this server renders to an end-user. The
countermeasure lives at one choke point rather than at each `reply.send`,
and `html-response.test.ts` fails the build if any other file in the view
layer names the HTML media type — so a page added later cannot acquire a
content type without acquiring the headers too.

### §16.4: the three ways this server can expose an access token

"Access Tokens MUST NOT be exposed to unauthorized parties" is a property,
and no test can establish a property over every party. What it can
establish is that the server emits access tokens through exactly one
channel, by enumerating the channels it emits anything through at all:
the `Location` header of an authorization response, the HTML pages
`/authorize` and the login endpoint render, and the Token Endpoint's own
response body. `OIDC-CORE-16.4-01` holds the first two to carrying no
token — the authorization response carries `code`, `state` and `iss` and
nothing else — and holds the third, the one channel where a token belongs,
to reaching only a client that authenticated for it: no `Set-Cookie`, and
`Cache-Control: no-store` so nothing between the two stores a copy.

What that leaves outside the row is everything past this server's own
socket: a client that logs the token, a proxy terminating TLS, an
operator reading the database. Those are real exposures and none of them
is what this row can be held to.

### §15.1's "at minimum", and what an accepting test has to be run against

`display`, `ui_locales`, `claims_locales` and `acr_values` are mandatory to
implement "at minimum" by not erroring, and Odudu implements exactly that
minimum: the parameters are parsed like any other and then ignored. The
trap in testing an obligation shaped this way is that "did not error" is
satisfied by a request that was going to be refused for some other reason,
and by a request that was going to be refused for this one. Each of
`OIDC-CORE-15.1-01`, `-02` and `-03` therefore sends its parameter on a
request that is otherwise admitted, and asserts the login form comes back —
so a rejection caused by the parameter shows up as a refused request rather
than as a differently worded error. The values tried include ones no server
could satisfy (`zz-ZZ`, an acr no realm defines), because the row says _any_
requested value.

`acr_values` has a second half that is not this row: reporting in `acr`
which authentication context was actually satisfied. That waits on P2's
authentication-method modeling, and is tracked on §2's `acr` row rather
than here.

### TLS, and the six rows here this process cannot close

Odudu terminates no TLS: it serves HTTP behind a reverse proxy. `docs/protocols/rfc6749.md`'s
reading note "TLS: what a boot guard settles, and what it does not" is the
whole of the argument, and it already names these rows. §3.1.2, §3.1.3 and
§5.3 ("communication with the ... Endpoint uses TLS") and §16.17
("implementations support TLS", "confidentiality protection is applied using
a TLS ciphersuite providing confidentiality and integrity") are claims about
the connection and the ciphersuite on it. `assertProductionTls`
(`apps/server/src/config-guard.ts`) makes an operator assert TLS before a
production boot, which is what closes RFC 6749's four rows phrased as the
server _requiring_ TLS; none of these five is phrased that way. An operator
who sets `ODUDU_TLS=true` in front of a plaintext listener has lied, and
nothing in this process can observe the difference. They are `accepted:`
against this note rather than `n/a` on the strength of a true sentence about
deployment boundaries: the obligations are Odudu's, they are simply
discharged by the proxy in front of it, and closing them here would need
Odudu to terminate TLS itself. §16.17's remaining SHOULD (BCP 195 / RFC 9325) is the same claim.

§2's `iss` row is the sixth, for the same reason in a different spelling —
see the note below.

### `iss`: the half of §2 this process cannot assert

§2 requires the ID Token's `iss` to be a case-sensitive **`https`** URL with
no query or fragment. `realmIssuer` (`packages/protocol-oidc/src/service/issuer.ts`)
builds the identifier from a scheme, an authority and a path, so a query or a
fragment has nowhere to enter, and `OIDC-DISCOVERY-3-02` holds the value
byte-identical to the `issuer` discovery publishes — but the scheme is
whatever the request arrived under, which behind the TLS-terminating proxy
Odudu expects is whatever that proxy asserts through `X-Forwarded-Proto`.
That is the same operator assertion the TLS note declines to treat as proof,
and the row is the same row `docs/protocols/rfc9207.md` leaves `gap` for the
`iss` _parameter_ — see its reading note "The scheme in the `iss` value".
Closing one of these two and not the other would be picking which of two
identical claims to believe, so this one is `accepted:` against this note, as
that one is against its own. What would close both is a scheme this process
establishes rather than reads off a forwarded header.

### §3.1.3.2's steps, and why they carry RFC 6749 test ids

§3.1.3.2 restates, for the OpenID Connect case, the verification steps RFC
6749 §4.1.3 already puts on the Token Endpoint: authenticate the client,
confirm the code was issued to it, confirm the code is valid and unused,
confirm the `redirect_uri` matches. Odudu has one token endpoint and one set
of checks, so these rows cite the assertions that hold those checks —
`RFC6749-10.5-02`, `RFC6749-4.1.3-01`, `RFC6749-5.2-01`, `RFC6749-4.1.2-02`
and `RFC6749-4.1.3-02` — rather than a second suite asserting the same
behaviour under different names. "The authorization code is valid" cites
`RFC6749-5.2-01` in particular because that assertion sweeps every way a code
can fail to be valid — unknown, expired, already consumed — where an
assertion about expiry alone would be one member of that set.

The step §3.1.3.2 adds that RFC 6749 does not is its last one: the code was
issued in response to an **Authentication** Request, so that an ID Token is
returned. That is `OIDC-CORE-3.1.3.2-01`, and it is one behaviour with
§3.1.3.3's `id_token` member: a code carrying the `openid` scope redeems for
an ID Token, and a code without it redeems for an access token and no
`id_token` member at all.

### §3.1.3.4's 400, and the 401 RFC 6749 §5.2 requires

§3.1.3.4 defines the Token Error Response's parameters by reference to RFC
6749 §5.2 and then states the body is `application/json` with HTTP status 400. §5.2, the section it defers to, requires 401 for `invalid_client` when
the client attempted to authenticate — and Odudu answers `invalid_client`
with 401 and a `WWW-Authenticate` header, because a 400 there would drop a
challenge the client is owed.

`OIDC-CORE-3.1.3.4-01` therefore holds every distinct token-endpoint failure
to `application/json` unconditionally, and to 400 for every error code except
`invalid_client`, which it pins to 401. The exception is written into the
assertion rather than left out of it, so a future 401 on some other error
fails the test instead of passing unnoticed.

### §5.3.2's four ways of saying one thing

"UserInfo claims are returned as members of a JSON object", "the UserInfo
Endpoint returns the JSON Serialization of the response", "the UserInfo
Endpoint returns a content-type header identifying the response format" and
"the content-type is `application/json` when the response body is a plain
JSON object" are four rows over one fact, and all four cite
`OIDC-CORE-5.4-01`, which reads the content-type and the parsed body of a
real UserInfo response. Each row's
"unless a different format was registered" escape is unreachable here: signed
and encrypted UserInfo responses need per-client registration data that does
not exist until P3, and those rows are `deferred: P3` immediately below.

### §15.1's `auth_time`, answered unconditionally

§15.1 makes returning `auth_time` _when requested_ mandatory for every OP.
The specification gives two ways to request it — `max_age` (§3.1.2.1) and an
Essential Claim in the `claims` parameter (§5.5) — and Odudu honours neither
_as a request_: both are parsed like any other parameter and ignored. What it
does instead is emit `auth_time` in every ID Token it issues
(`packages/protocol-oidc/src/usecase/token-issuance.ts`), so a client that
asks either way is answered, by a superset of what it asked for.

That is why this row is `covered` while §2's two `auth_time` rows stay
deferred: those two are about `max_age` forcing reauthentication (P2) and
about the `claims` parameter (P3), which are the request mechanisms, not the
claim. `OIDC-CORE-15.1-05` sends each request form on a login that completes
and checks the ID Token's `auth_time` against the `auth_time` stored on the
code that login issued — so a claim naming the token's own issuance time, or
carrying milliseconds, is a failure rather than a presence.
