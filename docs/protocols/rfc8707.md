# RFC 8707 — Resource Indicators for OAuth 2.0

**Status in Odudu:** in scope for P3b, per the design spec's §8.1: the
`resource` parameter is accepted at `/authorize` and `/token`,
single-valued, validated against the client's configured audience
allowlist, making `aud` derived rather than asserted. `/authorize` resolves
and validates it (`parseResource`,
`packages/protocol-oidc/src/service/resource-indicator.ts`) and stores the
result on the code; `/token` now reads it too, narrowing what the code (or,
on a refresh, the grant it rotated) carries, or deciding a codeless
`client_credentials` grant's audience against the client's own configured
list (`resolveAudience`,
`packages/protocol-oidc/src/usecase/token-issuance.ts`) — see
`docs/request-paths.md`'s `/token` entry for a transcript. §1
(Introduction), §1.1 (Requirements Notation and Conventions) and §1.2
(Terminology) are non-normative and out of scope; §1.1 is also the reason
every lowercase "must"/"should" elsewhere in this document — §2.1's and
§2.2's restatements of already-normative obligations, both discussed below
— carries no row, since §1.1 states plainly that only the all-capitals
form is normative here. §3 (Security Considerations) and §4 (Privacy
Considerations) contain no capitalized RFC 2119 keyword and are not rowed.
§5 (IANA Considerations) registers the parameter and error code
themselves, not a value Odudu would add to either registry, and is not
rowed.

## Reading notes

### `resource` stays single-valued: declined, not absent

§2's MAY that multiple `resource` parameters indicate a token intended for
several resources is not planned. The design spec's decision is a single
`resource` value, checked against one client's own audience allowlist —
the multi-resource form trades that for a token whose bearer can present
it at any of several resources interchangeably, which RFC 8707 §3 itself
flags as needing "a high degree of trust between the involved parties."
Nothing in Odudu's client or audience model establishes that trust between
two independently registered resources, so the row below is `accepted:`
against this note rather than left open.

### The omitted-`resource` MAY, already covered elsewhere

§2.1's MAY — that an authorization server either processes a request that
omits `resource` using a predefined default, or instead requires the
parameter and fails omission with `invalid_target` — names two branches.
Odudu takes the first: `resolveAudience`
(`packages/protocol-oidc/src/usecase/token-issuance.ts`) returns its `base`
verbatim when no resource indicator narrows it, whether `base` is the
client's configured `audiences` or a code's (or grant's) already-resolved
value, which is `docs/protocols/rfc9068.md` §3's row, closed against
`RFC6750-5.3-02`. Rowing the same choice again here would double-count an
obligation already closed under a different RFC's clause number, the way
`docs/protocols/oidc-frontchannel.md` declines to re-row the `sid` Claim's
definition once `oidc-backchannel.md` has closed it. Not rowed here.

### No discovery metadata to advertise

RFC 8707 registers no member of the OAuth 2.0 Authorization Server Metadata
or OpenID Connect discovery document — unlike, say, `resource_indicators`
being a thing a client could detect support for before sending one. A
client learns whether `resource` is honoured only by sending it and reading
`aud`, or by out-of-band knowledge of this server. `oidc-discovery.md`
carries no row for this RFC and gains none from this task; recorded here so
a reader does not go looking for one.
