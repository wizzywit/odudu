# OpenID Connect Discovery 1.0

**Status in Odudu:** in scope for P1. This is the OIDF Config OP
conformance plan written out as a clause table, so it is scoped
exhaustively rather than to a subset: every REQUIRED and RECOMMENDED
member of OpenID Provider Metadata (§3), plus the normative statements
governing the `/.well-known/openid-configuration` request, response, and
validation (§4). OPTIONAL metadata members are recorded in the reading
notes where Odudu's own document depends on them, but do not get rows —
the parser's level column has no slot for "OPTIONAL" and a row for every
one of them would not, in fact, be tracing anything Odudu is required to
do. §1 (Introduction), §2 (OpenID Provider Issuer Discovery, which is
WebFinger-based and itself OPTIONAL), §5 (String Operations), §6
(Implementation Considerations), §7 (Security Considerations) and §8–9
(IANA, References) are out of this table's scope: §2 because Odudu's
issuer is fixed by the realm's path (design spec §6) and never resolved
by WebFinger, the rest because they impose nothing beyond what §3–4
already state or are non-normative.

`token_endpoint` is REQUIRED "unless only the Implicit Flow is used"; OAuth
2.1 removes the Implicit Flow (`docs/protocols/rfc6749.md`), so for Odudu
it is unconditionally REQUIRED and is tabled as such.

## Reading notes

Odudu's `/.well-known/openid-configuration` document carries the metadata
this table marks `gap` or `deferred`, plus these strict, non-configurable
values that make later conformance testing predictable:

- `response_types_supported: ["code"]` — OAuth 2.1 and this phase's design
  support only `response_type=code` (`docs/protocols/rfc6749.md`); nothing
  else is ever a candidate value.
- `code_challenge_methods_supported: ["S256"]` — PKCE is mandatory for
  every client and `S256` is the only method (`docs/protocols/rfc7636.md`).
  This member is not part of OpenID Connect Discovery 1.0 itself (it
  entered the OAuth Authorization Server Metadata registry through RFC
  7636 and RFC 8414); it belongs in Odudu's discovery document but not in
  this table, since this table traces Discovery 1.0's own clauses.
- `authorization_response_iss_parameter_supported: true` — Odudu supports
  RFC 9207's `iss` authorization-response parameter unconditionally; the
  clause defining this metadata member is tabled in `docs/protocols/rfc9207.md`
  §3, not here, since RFC 9207 is the member's source specification.
- `id_token_signing_alg_values_supported` and (once advertised)
  `token_endpoint_auth_signing_alg_values_supported` are `["RS256", "ES256"]`
  — the phase's only two signing algorithms; no symmetric (`HS*`) or `none`
  value is ever listed.
- `response_modes_supported: ["query"]` — the only Response Mode Odudu
  answers in (`docs/protocols/oidc-core.md` §3.1.2.6). It is stated rather
  than omitted: §3 defaults an omitted value to `["query", "fragment"]`,
  which would advertise a mode the authorization endpoint refuses.
- `subject_types_supported: ["public"]` — pairwise subject identifiers are
  not part of this phase's scope; only `public` is offered.
- `registration_endpoint` is omitted from the document entirely while
  dynamic client registration remains P3's work, rather than published
  and left non-functional.
- `scopes_supported` always lists `openid`, per §3's unconditional
  requirement that the server support the `openid` scope value.
