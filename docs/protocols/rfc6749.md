# RFC 6749 — The OAuth 2.0 Authorization Framework

**Status in Odudu:** in scope for P1, but only the surface P1 implements: the
`authorization_code`, `refresh_token` and `client_credentials` grants, and
the authorize, token, userinfo and jwks endpoints. Odudu implements OAuth
2.1 (`draft-ietf-oauth-v2-1-15`), which is stricter than this RFC in three
ways recorded throughout the table below: the implicit and resource owner
password credentials grants are removed, PKCE is mandatory for every client
with `S256` only, and `redirect_uri` matching is exact string comparison.

## Reading notes

RFC 6749 defines four actors — resource owner, client, authorization
server, resource server — and its MUST/SHOULD/MAY statements are addressed
to different ones of them. Odudu is the authorization server, and for the
userinfo endpoint also the resource server. A number of requirements in
this RFC are addressed purely to the _client_ (a third-party application
Odudu does not implement) or to _client developers_; those are recorded as
`n/a` with that reasoning, not silently dropped, so the count of what was
considered stays honest — the same treatment Task 1 gave RFC 7636 §5's
client-side guidance.

Client _registration_ — assigning a client type, redirect URIs, and
credentials — is P3's job (dynamic registration, client management). P1
consumes already-registered clients; it does not register them. So
requirements about what happens _when a client registers_ are deferred to
P3, while requirements about what the authorization server does _at
request time_ with an already-registered client's data (matching a
`redirect_uri`, requiring authentication at the token endpoint, enforcing
PKCE) are in scope for P1 and recorded as `gap`.

RFC 6749 §8 (Extensibility) and the handful of clauses that talk about
extension grant types, extension response types, or new token types are
`n/a` for a different reason than the OAuth 2.1 decisions: they are
guidance for someone _defining a new registered extension_ to OAuth, not
requirements on an implementation of the extension points themselves.
Odudu implements the three grants and endpoints the extension mechanism
was designed to support; it does not itself mint new grant types, response
types, or token types, so these clauses never apply.

### The default scope, and the empty parameter value

This section is what §3.3's SHOULD asks an authorization server to
publish: its scope requirements, and its default value.

**The requirements.** Odudu accepts three scopes — `openid`, `profile` and
`email` — and refuses any authorization request naming one outside that
list with `invalid_scope`. The list is a single constant
(`SUPPORTED_SCOPES` in `@odudu/contracts`), read both by the authorization
endpoint's validation and by the discovery document's `scopes_supported`,
so what is advertised and what is accepted cannot drift apart. `openid` is
required in practice on every Authentication Request (OIDC Core §3.1.2.1),
and is what a request naming no scope resolves to.

**The default.** An authorization request that names no `scope` is
resolved to `openid`. §3.1's rule that a parameter sent without a value is
treated as omitted is what makes `scope=` reach that default rather than
fail as an unrecognized scope, and it is applied to every parameter of the
authorization request at once, in
`packages/protocol-oidc/src/service/query-normalization.ts`, rather than
one rule at a time.

### The §4.1.2.1 split, and why it is the whole of `/authorize`

Section 4.1.2.1 draws a line between two families of authorization-request
failure, and that line is the reason the authorize endpoint has two
completely different error-reporting paths instead of one.

The first family is: the `redirect_uri` is missing, invalid, or doesn't
match what was registered, or the `client_id` itself is missing or
invalid. In this family, the authorization server has not yet established
that the redirect target is one the real client controls. It **must not**
redirect the user-agent anywhere — it renders an error page directly,
in the authorization server's own UI. If it redirected instead, it would
be sending the browser (potentially carrying details of the request, and
certainly demonstrating that this endpoint will redirect on demand) to
a URI supplied by whoever made the request, with no assurance that URI
belongs to the client it claims to. That is precisely the shape of an
open redirector (§10.15): an endpoint that will send a user-agent to an
attacker-chosen location because the location came in as a parameter, not
because it was proven to be a party to the interaction. Rendering the
error, rather than redirecting on it, is what keeps `/authorize` from
becoming that.

The second family is everything else: the resource owner denies access,
the scope is invalid, `response_type` is unsupported, the server hit an
unexpected condition. Here, the redirect target _has_ been validated —
it's the registered `redirect_uri`, confirmed before the server does
anything else with it — so redirecting back to the client with an
`error` query parameter is safe and is in fact the whole point: the
client needs to learn what went wrong to react appropriately, and the
only channel back to the client at this point in the flow is a redirect
through the resource owner's user-agent.

So the split is not arbitrary error taxonomy: it's "do we know the
redirect target is legitimate yet?" A `/authorize` implementation has to
run that check — validate `client_id` and `redirect_uri` against the
registration — strictly before it decides how to report any other
failure, because the answer determines which of the two response
mechanisms is even safe to use.

§10.15 (Open Redirectors) itself carries no MUST, SHOULD, MAY, REQUIRED,
or RECOMMENDED — it is advisory prose describing the failure mode above,
not a normative statement, so it has no row in this table. The obligation
it describes is tracked instead under the §4.1.2.1 rows, which do contain
the RFC's actual MUST: the authorization server must not redirect the
user-agent when the `redirect_uri` is missing, invalid, or mismatched.
Odudu additionally closes the gap §10.15 warns about — a client's
partially registered redirection URI being treated as sufficient
validation — by matching `redirect_uri` as an exact string with no
wildcards, per OAuth 2.1.

### TLS: what a boot guard settles, and what it does not

Odudu terminates no TLS. It serves HTTP and expects a reverse proxy in
front of it (`infra/conformance/compose.yaml` is the worked example), so
no check inside this process can observe a ciphersuite, a certificate, or
whether the byte stream was encrypted at all.

What it can do is refuse to take part. `assertProductionTls`
(`apps/server/src/config-guard.ts`) stops the server booting with
`NODE_ENV=production` and `ODUDU_TLS` off, so a production deployment
cannot serve a single request until an operator has asserted that TLS is
in place. That is what closes the four rows phrased as _the authorization
server requires TLS_ — §2.3.1, §3.1, §3.2 and §10.11. Requiring is the
obligation, and a server that will not run without it requires it as
strictly as this process is able to.

It closes nothing phrased as TLS being present or good on the wire, and
those rows stay `gap` on purpose:

- §10.3 and §10.4 ("transmitted only over TLS with server authentication")
  and §10.9 ("requires TLS **with server authentication**") assert
  something about the connection and the certificate on it. An operator
  who sets `ODUDU_TLS=true` in front of a plaintext listener has lied, and
  nothing in this process can tell.
- OIDC Core §3.1.2, §3.1.3, §5.3 and §16.17, and RFC 6750 §5.2, are the
  same claim in other specifications' words — communication _uses_ TLS,
  the implementation _implements_ or _supports_ TLS, a ciphersuite
  provides confidentiality and integrity, BCP 195 is followed. Closing
  those needs Odudu to terminate TLS itself, or a deployment-level proof
  outside this repository's test surface.
- §3.1.2.1's two SHOULDs are about the _client's_ redirection endpoint and
  about warning the resource owner before a redirect to a non-TLS one.
  Neither is a configuration assertion; the second is an unimplemented
  feature.
