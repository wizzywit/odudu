# RFC 7636 — Proof Key for Code Exchange

**Status in Odudu:** in scope for P1. PKCE is mandatory for every client and
`S256` is the only permitted method.

## Reading notes

PKCE defends against authorization code interception: on a platform where a
public client's redirect URI (a custom scheme on a phone, say) can be claimed
by more than one app, a malicious app can register the same scheme and catch
the authorization code meant for the legitimate client. Without a client
secret — public clients don't have one — whoever holds the code can redeem it
for tokens. PKCE closes this by having the client generate a one-time secret,
the `code_verifier`, before the authorization request; it sends only a
derived `code_challenge` up front and proves possession of the verifier when
it later redeems the code at the token endpoint. An attacker who only
intercepts the code never sees the verifier and cannot complete the exchange.

The RFC defines two ways to derive the challenge from the verifier: `S256`
(the challenge is a SHA-256 hash of the verifier, base64url-encoded) and
`plain` (the challenge is just the verifier, unchanged). `plain` exists only
for clients that technically cannot compute SHA-256 and know in advance,
out-of-band, that their server accepts it — the RFC itself is lukewarm about
it, marking it `SHOULD NOT` be used in new implementations. Under `plain` the
challenge sent on the wire _is_ the verifier, so anything that can observe the
authorization request (the same class of attacker PKCE exists to defend
against) recovers the verifier and the defense collapses. Odudu has no
constrained clients that need `plain` and no deployments to stay compatible
with, so it implements only `S256` and requires PKCE on every authorization
request — stricter than the RFC, which makes PKCE itself optional and lets
`code_challenge_method` default to `plain` when absent.

The verifier and challenge are otherwise unremarkable: a high-entropy random
string 43–128 characters long, transformed once, checked once. The
interesting requirements are less about the happy path and more about
refusing to degrade — rejecting a missing challenge, rejecting an
unsupported method, and (per §7.2) never falling back to `plain` after
attempting `S256`.
