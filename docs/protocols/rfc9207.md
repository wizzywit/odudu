# RFC 9207 — OAuth 2.0 Authorization Server Issuer Identification

**Status in Odudu:** in scope for P1 in full. The `iss` parameter is a
short, self-contained countermeasure to mix-up attacks, and Odudu's
discovery document unconditionally sets
`authorization_response_iss_parameter_supported: true`
(`docs/protocols/oidc-discovery.md` reading notes). §1 (Introduction) is
non-normative background on mix-up attacks and is out of scope. §5 (IANA
Considerations) registers the metadata name and updates the `iss`
parameter's registry entry; it imposes nothing beyond what §2 and §3
already state.

## Reading notes

Mix-up attacks target a client juggling more than one authorization
server: if one of them is attacker-controlled, the attacker can arrange
for the honest server's authorization response to be delivered to the
client while the client believes it came from the attacker's server (or
vice versa), and the client sends a code or token to the wrong party. §2's
`iss` parameter closes this by having the authorization server state its
own identity, in the clear, in every authorization response — success and
error alike — so the client can compare it against the identifier of the
server it believes it just talked to before trusting anything else in the
response. Odudu supports only one client-facing flow topology per realm
today, but the protection is cheap and the client-side validation
obligation in §2.4 is unconditional, so there is no scoping argument for
leaving it out.

§2's single MUST is tabled as two rows, success and error, because one row
covered by one test is what let the error half go missing: a test that
inspects only the code-carrying redirect proves nothing about the redirect
an attacker actually steers a victim into.
