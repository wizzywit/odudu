# RFC 6238 — TOTP: Time-Based One-Time Password Algorithm

**Status in Odudu:** `@odudu/crypto`'s `totp.ts` implements the algorithm
directly against `node:crypto` — no dependency, because §5.1's own
conclusion is that the security of TOTP rests entirely on HOTP (RFC 4226),
which is HMAC plus a twenty-line truncation, and that is exactly what
mutation testing is good at pinning. §1 (Introduction/Scope/Background) and
§7/§8 (Acknowledgements/References) are non-normative and out of scope.
Appendix A is the reference implementation the vectors below were checked
against; Appendix B is the vectors themselves.

## Reading notes

### The vectors are the RFC's own, fetched and read directly

`https://www.rfc-editor.org/rfc/rfc6238` (plain-text form,
`rfc-editor.org/rfc/rfc6238.txt`) was fetched on 2026-09-16 and Appendix A
and Appendix B were read in full — not recalled, and not taken on trust
from a transcription. Appendix B's Table 1 (SHA-1, SHA-256 and SHA-512,
six timestamps each) was compared cell by cell against
`packages/crypto/src/service/totp.test.ts`'s `it.each` tables. The brief's
SHA-1 and SHA-256 **code** columns matched the RFC exactly; its SHA-256
**secret** did not (see below), so it was corrected, and SHA-512 vectors —
present in the RFC but absent from the brief entirely — were added. RFC
4226's own Appendix D (`https://www.rfc-editor.org/rfc/rfc4226.txt`), also
fetched and read on 2026-09-16, supplied ten further HOTP vectors (counters
0-9, same secret, six digits) used as additional `totpCode` cases — TOTP is
HOTP with the counter replaced by a time step, so these exercise the same
truncation directly, over digest bytes appendix B's six fixed timestamps
happen not to touch.

### The seed extension for SHA-256 and SHA-512 is not zero-padding

Appendix B states the shared secret is the ASCII string
`"12345678901234567890"` and that it is used unchanged for SHA-1. It does
not restate the extension rule in prose; the rule is only visible in
Appendix A's reference implementation, in the three string literals its
`main` method builds:

```
seed   = "3132333435363738393031323334353637383930"                          (20 bytes)
seed32 = seed + "313233343536373839303132"                                    (32 bytes)
seed64 = seed + seed + seed + "31323334"                                      (64 bytes)
```

Decoded from hex to ASCII, `seed32` is `"12345678901234567890123456789012"`
and `seed64` is the string `"1234567890"` repeated six times plus `"1234"`.
The rule is: **extend the seed by continuing the same repeating digit
cycle `1234567890`**, not by padding with zero bytes, truncating, or simply
repeating the 20-byte block a whole number of times and stopping short (the
32-byte case ends mid-cycle, at `...9012`). Both `packages/crypto/src/service/totp.test.ts`'s
`SEED_SHA256` and `SEED_SHA512` constants were built by generating exactly
this cyclic string, encoding it as bytes, base32-encoding the result, and
then decoding that base32 string back to hex to confirm it matched the
RFC's own hex literals above before it went into a test.

### The brief's SHA-256 seed was wrong

The task brief's skeleton test defined `SEED_SHA256` as
`SEED_SHA1` concatenated with itself — the 20-byte SHA-1 secret repeated
twice, base32-encoded, which decodes to 40 bytes. RFC 6238's own SHA-256
secret is 32 bytes, built by the cyclic extension above, not by doubling
the 20-byte one. Decoding the brief's string back to hex does not match
Appendix A's `seed32` hex literal at all — it is a plausible-looking base32
string (doubling a valid base32 string still produces a valid, differently-
sized one), not a transcription error that happens to net out to the same
bytes. Had it shipped, every SHA-256 test would have passed against a
40-byte secret nothing else in the RFC or in this implementation ever
produces, pinning nothing about the actual SHA-256 vectors. It is corrected
in `totp.test.ts` to the base32 encoding of the true 32-byte seed
(`GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQGEZA`); the SHA-1 codes
and SHA-256 codes the brief listed were both otherwise correct against the
RFC.

### `verifyTotp`'s fixed shape

The interface `verifyTotp({ secret, code, now, lastStep })` takes no
`digits` or `algorithm` parameter, so both are fixed inside it — six
digits, SHA-1 — rather than inferred from the presented code. A candidate
that is not exactly six ASCII digits is refused before any HMAC is
computed, checked against `/^\d{6}$/u` rather than `code.length`: a
length check alone counts UTF-16 code units, while the buffer handed to
`crypto.timingSafeEqual` is UTF-8 bytes, and a string such as `"12345é"`
has six of the former and seven of the latter — enough to reach the
comparison and have it throw on mismatched buffer lengths instead of
returning a refusal. The shape check closes both the length gap and the
timing signal a mismatched-length call would otherwise leak. A ±1-step
verification window closes §5.2's "we RECOMMEND that at most one time
step is allowed as the network delay" and §6's resynchronization limit at
once — the same tolerance answers both. `lastStep` exists only to hold
§5.2's "the verifier MUST NOT accept the second attempt of the OTP after
successful validation": without it, a code would validate repeatedly for
its entire 30-to-90-second acceptance window.

### Mutation testing: a Stryker-reported score that undersells the suite

`packages/crypto/stryker.config.json` already carries a documented
`@stryker-mutator/vitest-runner` defect (targeted test selection returning
zero completed tests, reporting the mutant Survived regardless) that holds
`sign.ts` and `jwks.ts` near a 0% score. `totp.ts` has the same test shape —
`it.each` blocks pinning specific vector outputs — and is affected the same
way: adding ten genuinely new RFC 4226 vectors left its reported score
unchanged (6.25% before and after). Every mutant Stryker reported as
Survived in the truncation, modulo, big-endian counter encoding and
replay-guard logic was applied to `totp.ts` by hand and run directly
through `vitest run totp`, outside Stryker's test-selection path; all of
those failed the suite. Two mutants really do survive, and are equivalent
rather than gaps: `currentStep - offset` in place of `currentStep +
offset`, because a symmetric `[-1, 1]` window visits the same three steps
either way, and an empty-string encoding in place of `'utf8'` in the final
`Buffer.from(candidate, …)`, because `Buffer.from` falls back to `utf8` for
an unrecognised encoding and every candidate string here is ASCII digits,
for which that fallback is indistinguishable from the original. The updated
`stryker.config.json` comment records this.
