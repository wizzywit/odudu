# RFC 7662 — OAuth 2.0 Token Introspection

**Status in Odudu:** in scope for P3b in full, per the design spec's §8.2.
No `/introspect` endpoint exists in this repository yet — this table is
written before the endpoint that resolves its rows, which is this
increment's own first task. What resolves each row is `active` consulting
**session liveness**, not only a grant's `revoked_at`, and scoping a
description to callers whose own `client_id` appears in the token's `aud`
— the two mechanisms §8.2 names. §1 (Introduction) is non-normative
background on what introspection is for and is out of scope; §3 (IANA
Considerations) registers the response-name registry itself, not a name in
it, and is not rowed; §6 (References) is never rowed. §2.2's response
members other than `active` — `scope`, `client_id`, `username`,
`token_type`, `exp`, `iat`, `nbf`, `sub`, `aud`, `iss`, `jti` — are
OPTIONAL and get no rows, for the same reason `oidc-discovery.md` gives
OPTIONAL metadata.

## Reading notes

### §2.2's fused MUST, and the spike that settles it

A spike ran before this table was written, per `CLAUDE.md`'s P0 rule for a
claim about third-party (specification) behaviour: `assumption:` §2.2
permits answering `{"active": false}` to an authenticated caller not
authorized for the token, rather than requiring an error. The assumption
**held, and more strongly than that phrasing states**. §2.2's final
normative paragraph, verbatim:

> If the introspection call is properly authorized but the token is not
> active, does not exist on this server, or the protected resource is not
> allowed to introspect this particular token, then the authorization
> server MUST return an introspection response with the "active" field set
> to "false". Note that to avoid disclosing too much of the authorization
> server's state to a third party, the authorization server SHOULD NOT
> include any additional information about an inactive token, including
> why the token is inactive.

Two things follow that the brief's own phrasing understates. First,
`{"active": false}` for an authorized caller who simply is not entitled to
the token is **required**, not merely permitted — the design spec's
decision to scope a description by `aud` membership stands, and the
alternative it rejected, an explicit error, would be a conformance
violation rather than a defensible different choice. Second, the sentence
fuses three distinct conditions — token inactive, token unknown, caller not
allowed — into one response on purpose: an introspection response must not
let a caller distinguish them. That MUST is the `2.2` row below headed
"the authorization server responds with `active: false`"; the `SHOULD NOT`
that follows it, about omitting any further detail on an inactive token,
is a second, separate row rather than a footnote on the first.

### TLS on the introspection endpoint

§2 and §4 each carry a MUST that the introspection endpoint runs under
TLS. Odudu terminates no TLS — `docs/protocols/rfc6749.md`'s reading note
"TLS: what a boot guard settles, and what it does not" is the standing
account of what `assertProductionTls` does and does not prove, and both
rows here are `accepted:` against it rather than newly argued.

### Two restatements, rowed once

§4 restates two obligations §2 already states: that the endpoint requires
authentication of the protected resources that call it (§2.1), and that an
inactive-token response carries nothing beyond `active: false` (§2.2's
`SHOULD NOT`). Both are rowed once, at the section that states them first.
§4 adds one genuinely new obligation next to the first restatement — that a
protected resource be **specifically authorized** to call the endpoint,
not merely authenticated — and that gets its own row below.
