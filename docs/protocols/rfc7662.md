# RFC 7662 — OAuth 2.0 Token Introspection

**Status in Odudu:** in scope for P3b, per the design spec's §8.2.
`/introspect` (`packages/protocol-oidc/src/view/routes/introspect.ts`) and
`/revoke` (RFC 7009, `packages/protocol-oidc/src/view/routes/revoke.ts`)
both exist. What resolves each `active` row is
consulting **session liveness**, not only a grant's `revoked_at`, and scoping a
description to callers entitled through their own `client_id` **or**
through any RFC 8707 resource URI they are registered under — the two
mechanisms §8.2 names, the second corrected from its own literal wording
by "The caller's identity: `client_id` against resource URIs" below. §1
(Introduction) is non-normative
background on what introspection is for and is out of scope; §3 (IANA
Considerations) registers the response-name registry itself, not a name in
it, and is not rowed; §6 (References) is never rowed. §2.2's response
members other than `active` — `scope`, `client_id`, `username`,
`token_type`, `exp`, `iat`, `nbf`, `sub`, `aud`, `iss`, `jti` — are
OPTIONAL and get no rows, for the same reason `oidc-discovery.md` gives
OPTIONAL metadata.

## Reading notes

### The caller's identity: `client_id` against resource URIs

§8.2's own sentence, read literally, compares the caller's `client_id`
against the token's `aud`. Those are different namespaces: `aud` is built
from `client_oidc_config.audiences`, RFC 8707 resource URIs, while a
`/introspect` caller authenticates with client credentials and is
identified by a `client_id` — and a `client_id` never appears in an `aud`
built from resource URIs, so the sentence taken literally would answer
`{"active": false}` to every caller.

The rule actually implemented: a caller is entitled to a description when
the token's `aud` intersects the caller's own identity, where that
identity is its `client_id` **or** any value in its own registered
`audiences`. A resource server is a client whose `audiences` name the
resources it serves, which is how a deployment expresses "this token is
for me"; the `client_id` half is kept so a deployment that registers
audiences as client ids still works. `IntrospectionCaller`
(`packages/protocol-oidc/src/usecase/introspection.ts`) carries both,
named as its own type so a call site cannot pass a bare string and have
either dimension silently mean nothing.

`callerIsAddressed` is what actually enforces this, and it is checked in
both directions, not merely exercised: forcing it to always match turns an
unentitled caller's `active: false` into `active: true`, leaking the
token's `scope`, `sub` and `aud` to a party the `aud` membership check
exists to keep them from; forcing it to never match turns an entitled
caller's own description back into `active: false`. Either fault is a
distinct kind of failure — one discloses too much, the other discloses
nothing to a resource server that owns the token — and each is caught by
the test naming that direction (`RFC7662-2.2-01` for entitlement granted,
`RFC7662-2.2-02` for entitlement withheld). Neither direction can be
inferred from the other passing; both have to be checked.

### Why a grant needs its own claim

`token_grants` carries no unique constraint over `{client_id, subject_id,
session_id}`, and every path that creates a grant — `authorization_code`
and `client_credentials`; a refresh reuses the grant it rotates rather
than creating one — inserts a fresh row. For `client_credentials`,
`subject_id` is the client's stable `service_subject_id` and `session_id`
is always `null`, so every grant that client will ever hold shares the
identical triple. A query over that triple cannot tell a revoked grant
from a live sibling.

So the access token carries a private `grant_id` claim — the
`token_grants` row's own id, generated before the token is minted and
signed into it — and both introspection and `/revoke` (`rfc7009.md`'s
"Both revocation directions go through the grant, not the token") look a
grant up by that id alone. See `docs/protocols/rfc9068.md`'s reading note
on private claims for how `grant_id` sits beside `sid`.

### §2.2's fused MUST, and the spike that settles it

A spike ran before this table was written, per `CLAUDE.md`'s P0 rule for a
claim about third-party (specification) behaviour: `assumption:` §2.2
permits answering `{"active": false}` to an authenticated caller not
authorized for the token, rather than requiring an error. The assumption
**held, and more strongly than that phrasing states**. §2.2's final
normative paragraph, verbatim:

> If the introspection call is properly authorized but the token is not
> active, does not exist on this server, or the protected resource is not
> allowed to introspect this particular token, then the authorization
> server MUST return an introspection response with the "active" field set
> to "false". Note that to avoid disclosing too much of the authorization
> server's state to a third party, the authorization server SHOULD NOT
> include any additional information about an inactive token, including
> why the token is inactive.

Two things follow that the brief's own phrasing understates. First,
`{"active": false}` for an authorized caller who simply is not entitled to
the token is **required**, not merely permitted — the design spec's
decision to scope a description by `aud` membership stands, and the
alternative it rejected, an explicit error, would be a conformance
violation rather than a defensible different choice. Second, the sentence
fuses three distinct conditions — token inactive, token unknown, caller not
allowed — into one response on purpose: an introspection response must not
let a caller distinguish them. That MUST is the `2.2` row below headed
"the authorization server responds with `active: false`"; the `SHOULD NOT`
that follows it, about omitting any further detail on an inactive token,
is a second, separate row rather than a footnote on the first.

The fused row is pinned against the "does not exist on this server" leg by
`RFC7662-2.2-04` — a well-formed, validly signed token whose `grant_id`
simply names no row, the purest instance of "unknown" since nothing about
the token itself is wrong. Two adjacent cases pin the same fused answer for
reasons that are not this row's own: a token whose grant has been revoked
answers identically, and so does one whose grant id matches a sibling grant
only by coincidence of client, subject and session — the case a per-grant
`grant_id` claim exists to make impossible (see "Why a grant needs its own
claim" above). All three share the one `catch`-free code path through
`introspect`, so a test naming any one of them would catch a regression
that merged the three conditions back into visibly different answers.

`RFC7662-2.2-02` pins the SHOULD NOT beside it with `toEqual`, not
`toMatchObject`: `toMatchObject` would still pass a response that leaked
`scope`, `client_id` or any other member alongside `active: false`, which
is exactly the disclosure the SHOULD NOT forbids. Asserting the whole
object, not a subset of it, is what makes the row's own evidence prove the
SHOULD NOT rather than merely the boolean.

### §2.3's declarative sentences, already rowed elsewhere

§2.3 is titled "Error Response" but contains exactly one capitalized RFC
2119 keyword — the MUST below, that a query for an inactive, unknown, or
disallowed token is answered per §2.2 rather than as an OAuth error
object. Its other two sentences, describing an HTTP 401 on invalid client
credentials or an insufficient bearer token, are declarative ("...the
authorization server responds with an HTTP 401...") and carry no keyword
of their own. Both restate an obligation already normative — and already
rowed — elsewhere: `docs/protocols/rfc6749.md` §5.2 rows the 401-on-
`invalid_client` behaviour (`RFC6749-5.2-02`), and
`docs/protocols/rfc6750.md` §3.1 rows the 401-on-`invalid_token` behaviour
(`RFC6750-3.1-01`). Rowing them again here, at a level the text does not
carry, would both invent a level and double-count an obligation this
process has already rowed once. Not rowed here.

### TLS on the introspection endpoint

§2 and §4 each carry a MUST that the introspection endpoint runs under
TLS. Odudu terminates no TLS — `docs/protocols/rfc6749.md`'s reading note
"TLS: what a boot guard settles, and what it does not" is the standing
account of what `assertProductionTls` does and does not prove, and both
rows here are `accepted:` against it rather than newly argued.

### Two restatements, rowed once

§4 restates two obligations §2 already states. The first pair is close but
not identical: §2.1's MUST that the endpoint "require some form of
authorization" permits a bearer token as well as client authentication,
while §4's MUST names authentication specifically; they are treated as one
obligation and rowed once, at §2.1, because §4 draws no distinction that
changes what a test would check. The second pair is exact: an
inactive-token response carries nothing beyond `active: false`, stated
once as a `SHOULD NOT` at §2.2 and restated in the same words at §4. Both
are rowed once, at the section that states them first. §4 adds one
genuinely new obligation next to the first restatement — that a protected
resource be **specifically authorized** to call the endpoint, not merely
authenticated — and that gets its own row below.

### `gap` versus a decided MAY

An unaddressed MAY is `gap` when nothing in this phase forces a decision on
it — CORS and JSONP, neither of which building `/introspect` or `/revoke`
requires taking a position on. The same kind of MAY resolves to `accepted`
instead once building the row's own feature necessarily forces the choice,
or an already-committed mechanism exercises it — the three rows below settle
three such choices. Before `/introspect` existed, this whole class read
`deferred: P3b` rather than `accepted` or `gap` — see
`docs/superpowers/plans/2026-09-19-p3b-sessions-logout-token-surface.md`
for when it was built. This rule applies the same way in `rfc7009.md` and
`rfc8707.md`.

### An absent `token` fails the same way an unreadable one does

§2.1's `token` parameter is REQUIRED, but Odudu draws no separate line
between "absent" and "present but unreadable": `respondToIntrospectionRequest`
(`packages/protocol-oidc/src/usecase/introspection-request.ts`) reads a
missing `token` as `''`, which reaches `introspect`'s `verifyJwt` call and
fails it the same way any other malformed token does — falling under the
SHOULD below rather than a distinct error path. There is no code path where
omitting the parameter answers differently from sending garbage in it.

### `token_type_hint` is never read

Neither the route nor either usecase reads `token_type_hint` — the endpoint
has exactly one token type it understands (an RFC 9068 access token,
`typ: 'at+jwt'`), so there is no second type a search could extend to and
nothing a hint could narrow. Ignoring it is not a choice with an
alternative implementation; it is what having one type means.

### Authorization is not optional at this endpoint

An unauthenticated call answers `401 invalid_client`, never a description —
proven by removing the authentication step: bypassing `authenticateClient`
in `respondToIntrospectionRequest` for a call presenting no Basic
credentials turns the 401 into a 200. `RFC7662-2.1-01`
(`introspect.int.test.ts`) is that call.

### An unreadable token answers exactly like an inactive one

`introspect`'s only path for a token it cannot parse, whose signature does
not verify, or whose issuer does not match is the `catch` around
`verifyJwt` — it returns `{ active: false }` and never throws.
`RFC7662-2.1-02` (`introspection.test.ts`'s `'answers inactive for a token
that does not parse, without saying why'`) is the case with nothing at all
to read; `RFC7662-4-03` (`'...signed by another tenant'`) is a well-formed
token whose signature specifically fails.

### The endpoint accepts POST only, never GET

`registerIntrospectRoute` (`packages/protocol-oidc/src/view/routes/introspect.ts`)
registers `app.post` on the introspection path and nothing else — no GET
handler exists for it, so a token value can never reach this endpoint via a
query string a server-side log might capture.

### Two MAYs left `gap`, with a destination in `docs/NEXT.md`

Neither is decided: an entitled caller always sees a token's whole `scope`
(§2.2's MAY to narrow it per protected resource), and any client that
authenticates with its own registered secret may call `/introspect` for any
token (§4's SHOULD that a protected resource be specifically authorized to
call the endpoint, not merely authenticated — `callerIsAddressed` limits
what a caller _learns_, not whether it may ask). The design spec's §8.2
names only the audience-scoping mechanism `introspect` already implements,
so nothing in this repository has argued against either — which is what
`gap` means here, as opposed to `deferred:` naming a phase that will decide
it. Both are recorded in `docs/NEXT.md`'s "Decisions still open", with the
trigger that would turn either into a real decision.

### Only the two password methods reach this endpoint

`respondToIntrospectionRequest` authenticates through `authenticateClient`
(`packages/protocol-oidc/src/usecase/client-authentication.ts`) alone, which
reads a Basic header or a body `client_secret` and nothing else — it never
calls `authenticatePrivateKeyJwt` or `authenticateTlsClientAuth`, both of
which live in `usecase/token-issuance.ts` and are dispatched only from
`/token`. So a client registered for `private_key_jwt` or `tls_client_auth`
presents no credential this endpoint can read, and is refused
`invalid_client` every time. `/revoke` is identical, by the same call —
`rfc7009.md`'s "The revocation endpoint shares `/token`'s and
`/introspect`'s client-authentication path".

**Accepted, not deferred.** No clause in either RFC requires a particular
set of client-authentication methods; §2.1's MUST is that the endpoint
require authorization at all, which it does (`RFC7662-2.1-01`). What is
missing is reach, not conformance, and closing it means extending the
assertion and certificate dispatch `/token` already has to two more routes
— a client-authentication change rather than an introspection one. The
trigger sits in `docs/NEXT.md`.

### §5's disclosure guarantee is the audience check, not a separate control

§5's MUST — that privacy-sensitive introspection-response information not
reach an unintended party — has no mechanism of its own here: it holds
exactly to the extent `callerIsAddressed` holds, because a caller outside
the token's `aud` receives `{ active: false }` and nothing else. It learns
nothing about the token — not the subject it names, not its scope, not
even that it is a live token rather than a nonexistent one, since the two
answer identically. `RFC7662-2.2-02` is this row's evidence for exactly
that reason: the unentitled caller in that test would be the unintended
party §5 is written against, and its response carries no more than any
other caller's would.
