# P5 — agent identity and approvals

What the phase found, in the shape `docs/phases/p2b.md` established: the running record the spec and plan do not keep. The
argument is in [ADR 0059](../adr/0059-an-approval-is-one-object-with-two-channels.md) and the amendments to ADR 0003 and ADR 0050;
how it was planned is in the [spec](../superpowers/specs/2026-11-24-p5-agent-identity-design.md) and the plan beside it. The three
spikes it began with are in [p5-spikes.md](p5-spikes.md).

## What shipped

Eight increments, each merged into the phase branch with CI green and its review answered:

1. **Placement.** Section 11 split P5 and added P5c; ADRs 0055 to 0059; the roadmap, `docs/NEXT.md` and the tests that map them.
2. **`@odudu/domain-agents`.** `admitChild`, the four invariants as a pure function (scope narrows, expiry never passes the parent or
   the session, depth, fan-out), with property tests (fast-check) and a mutation run (35 mutants, none survived).
3. **Schema and repositories.** `agent_instances`, `agent_approvals`, `agent_delegations`, `agent_budget_windows`, `token_grants.may_act`,
   the client fields `agent_type` and `delegated_actors`, the nine `agent_*` tenant settings; every table under row-level security and
   probed with a foreign tenant.
4. **The exchange.** An agent-type client that exchanges a token starts an instance (`act.sub`), a nested exchange a child; the depth
   is a setting; `may_act` is minted from the client's `delegated_actors` and a person's delegations, kept on the grant and read by the
   refresh branch.
5. **Revocation and budgets.** Revoking a grant revokes everything exchanged from it and every instance rooted there; the reaper
   deletes instances, approvals, delegations and windows; a write is spent against the sign-in, the instance and the daily window in one
   step.
6. **CIBA in poll mode.** `bc-authorize`, the grant, discovery, the approval page (a themeable page kind of its own), the mail, rate limits.
7. **Operators and people.** The admin routes for agents and approvals, the console's Agents area, the settings screen, the `me`
   delegation routes, the audit vocabulary (`agent_identity`).
8. **Documents and the closing pass.** The concept page, the guide, the transcripts run on a live stack, the CIBA reading note, the
   roadmap and section 11 reconciled, `CHANGELOG.md`.

## What it found

- **The spec and the shipped wire disagreed about `sub`.** Section 9 of the umbrella spec said `sub` is the agent instance; ADR 0050 and
  everything P5a shipped keep `sub` as the person and put the agent in `act`. The design followed the wire and amended ADR 0003 and
  section 9.
- **Revocation order is the whole difficulty.** The first cascade deadlocked with an exchange holding a grant while it wanted an
  instance, and the next three fixes each left a cycle a review found. Ten rounds ended in one rule: every revoker takes the lineage
  root of its seeds first, in id order, and only then works unordered; the reaper skips a root a revoker holds. Four cases still deadlock;
  the transaction that loses is run again inside the server, three attempts in all (`withTenantRetrying` in `@odudu/db`), and answers
  `500` with `40P01` only after the third (spec 5.4; [Scaling](../../apps/docs/content/en/operating/scaling.md), "When two revokes meet").
- **The audit vocabulary cannot precede its writers.** A lint fails any action with no production writer, so the task that added the
  eleven actions was folded into the ones that write them.
- **An automated review of the exchange found real defects.** Of 19 comments, 17 were valid or partly valid, among them a client id shaped like a UUID
  read as an instance head, an exchanged token whose act head is an ended instance, and exchanged tokens not capped at the instance's expiry.
- **The first review of the approval page found two unplaced deferrals that were defects of the feature:** a tenant on its own domain got
  a sign-in page that could not return to the approval, and the page was exempt from the theme. Both were fixed in the increment; the
  page is a page kind of its own.
- **MCP tokens carry no instance id**, so a call through the endpoint is counted against the sign-in and the daily window only. The
  changelog had said three levels; it now says what is true.
- **Replaying the transcripts found three stale facts**: the `me` OpenAPI page still showed seven paths (nine since delegations), the
  agent lists page the cursor `next` (the parameter is `cursor`), and a `content-length` that a hand edit had not raised.

## The OIDF conformance plan for CIBA

The spec's exit criterion asked for a green OIDF plan, on the assumption that the suite has one for poll mode. **It has not**
([p5-spikes.md](p5-spikes.md), spike 1): the suite release the `conformance` job builds, `release-v5.1.36`, has one CIBA plan, the
FAPI one (`fapi-ciba-id1-test-plan`), every module of which needs a signed authentication request and the FAPI client
authentication, neither of which Odudu serves. The proof stays the integration tests, tagged with the clauses of
`docs/protocols/oidc-ciba.md`, and the transcripts. The umbrella spec's P5 row says so.

## Left

What the phase leaves is in `docs/NEXT.md`, each against the phase that will take it:

- `may_act` is one object for one actor and an array for several; §4.4 shows only the object (P14).
- Revoking a delegation does not end runs already started; they end at their expiry or by an administrator's revoke (decided and
  documented; the owner may reopen it).
- A mint counts the tenant's live instances (`liveCount`), which is a count bounded by `agent_max_live_instances`, 100,000 at most;
  at that ceiling it is a scan on the token path, and P11's load work is where it would be measured.
- `bc-authorize`: exotic Unicode casing could split an alias across the per-hint counters, live requests count in any state until they
  lapse, and a refused request under pool starvation is untested (P13).
- The injection probe's snapshot ignores `agent_budget_windows`, which every write call spends (P5b).
- `agent_max_live_instances` is a soft cap: mints under different parents are not serialised, so the count can pass it by up to the
  mints in flight. The setting's page says so.

The blocks of the admin-path transcripts that show a client or the tenant settings were edited, not run: each page needs a system
administrator's token, which the console's own key signs for, and a throwaway tenant. `docs/NEXT.md` no longer carries a row for it
because `contributing/transcripts.md` states it; the next phase that changes an admin route re-runs those pages.
