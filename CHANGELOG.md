# Changelog

All notable changes to Odudu are written here, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/) as [RELEASING.md](RELEASING.md) describes.

## [Unreleased]

### Added

- Agent instances. A client marked as an agent (`agent_type`) that exchanges a person's token (RFC 8693) now starts a run of its own: the issued token keeps the person as `sub` and names the run in `act.sub`, and a run that exchanges its own token starts a run under it, nested in `act`. A run can only be narrower than the one above it: its scope is a subset, it ends no later than its parent or the person's session, its depth is within `agent_max_delegation_depth`, and a parent holds at most `agent_max_children` live runs and the tenant at most `agent_max_live_instances`. A client that is not an agent exchanges exactly as before.
- `may_act` is now written into a person's access token, from the sign-in client's `delegated_actors` and from the person's own delegations (below), with the narrower scope ceiling applying to an agent client both name. The grant keeps it, so exchanging the refresh token is held to it as well. A sign-in with neither source has no `may_act`, as before.

- Nine tenant settings for agents, under **Agents** in the console's Settings and through the settings API: `agent_max_delegation_depth`, `agent_max_children`, `agent_max_live_instances`, `agent_instance_ttl_seconds`, `agent_instance_idle_seconds`, `agent_approval_ttl_seconds`, `agent_writes_per_grant`, `agent_creates_per_grant` and `agent_window_writes`. Each has a default and a range, and a tenant export and import carry them.
- A client has `agent_type`, which marks it as an agent, and `delegated_actors`, the `client_id` of each client allowed to act for its people (at most 20, each an existing client of the tenant). Both are on the admin API, the console's Advanced tab and a tenant export and import.
- `odudu reap` reports four more tables, after `authorization_codes`: `agent_budget_windows`, `agent_approvals`, `agent_delegations` and `agent_instances`. It deletes a budget window two days after it opened, an approval and a delegation thirty days after they lapsed or were revoked, and an agent instance seven days after it was revoked or lapsed, once nothing beneath it is left, together with its subject.
- An agent's writes are counted against up to three limits in one step, so calls made together can never overspend: the sign-in's own allowance, the share of an agent instance, and a daily window for each person and agent client. A call through the MCP endpoint counts at every level its token carries: a token an agent client got by token exchange counts against its run's share as well as the sign-in and the daily window, a revoked or expired run spends nothing, and a nested run is given what its parent had left, never more. A write carried by a token whose grant was revoked is refused once the revoke has committed; one that commits at the same moment as the write counts as a write that finished just before it. The limits are the tenant's `agent_writes_per_grant`, `agent_creates_per_grant` and `agent_window_writes`, which the MCP server now reads instead of a fixed 20 and 10; their defaults keep today's behaviour.
- Revoking a grant revokes everything exchanged from it and every agent instance rooted at any of them, however deep, within the revocation's own transaction (one statement for each stretch of depth, repeated until a scan finds nothing left, so a child committed while it waited is found too): signing out, ending a session, withdrawing a consent, a refresh token replayed, an authorization code replayed, a recovered account, a removed service account and an admin revoking a person's grants all reach what an agent was given from them. Each agent instance that ends this way with nothing above it ending too, the top of a run of instances ended together, leaves one `agent.instance_revoked` audit row (event type `agent_identity`) naming the instance, its owner, its agent client and its depth, with `count`, how many instances ended from it down, itself included, and `via`: `cascade`, or `owner_ended` when an agent's run is refused because its owner's session or account has ended.
- OpenID CIBA, poll mode. A client given the `urn:openid:params:grant-type:ciba` grant (**Backchannel authentication** in the console) asks a named person to approve something with `POST /tenants/<tenant>/protocol/openid-connect/bc-authorize`, then polls the token endpoint with the `auth_req_id` it gets back until it answers tokens for that person (`authorization_pending`, `slow_down`, `expired_token` and `access_denied` meanwhile). A hint that names nobody is answered as one that names a person is, so the endpoint cannot be used to find out who has an account. A client may hold 20 live requests for one hint, answered `access_denied` past that whether or not the hint names anyone, and 30 requests a minute. A person with 20 approvals already waiting is not told so: the request ends as `expired_token`, as one for nobody does. A public client cannot hold the grant. Discovery and the authorization server metadata advertise the endpoint, the `poll` mode and the grant. `odudu reap` reports `ciba_requests` and deletes a request thirty days after it expired. The audit trail gains `ciba.requested`, `ciba.poll_refused` and `ciba.token_issued`.
- The person a CIBA request names is mailed a link and decides on an approval page, `/tenants/<tenant>/approval/<id>`. The mail goes to a verified address, says which client is asking and carries only the approval's id; the page shows the client, what it asks for, its `binding_message` and the expiry, and approves or denies with a form token tied to the signed-in session and the approval. A person with no session is sent through the console's sign-in and back to the page at the tenant's own address, its canonical domain included. The page is a new themeable page kind, `approval`, with its own template and `page-approval` stylesheet hook. A person's address is mailed at most three approval notices an hour; past that the request still succeeds and sends nothing. Anything that is not the signed-in owner's pending approval (unknown, someone else's, expired, already answered) gets one `404` page, so a link says nothing about other people's approvals. A request for nobody, or for a person at the limit, sends no mail and runs the same database statements as one that does.
- The admin API lists and ends a tenant's agents and shows the approvals asked of their owners. `GET /admin/tenants/<name>/agents` pages the agent instances in the order they were started, narrowed by `owner` and `state` (`live`, `expired` or `revoked`), each with its lineage (`owner`, `owner_username`, `agent_client`, `parent`, `depth`), its expiry and `remaining_budget`, what its own share of changing and creating calls has left; `GET .../agents/<id>` reads one. `DELETE .../agents/<id>` revokes the instance, everything started beneath it and the grants any of them acted in, with everything exchanged from those, and answers how many grants and instances it ended; with `?dry_run=true` it answers the same counts and changes and records nothing. `GET .../agent-approvals` pages the approvals agents asked of their owners, newest first, narrowed by `state`; each names its `owner` and that owner's `owner_username`, `null` for a subject with none. All four routes take `manage-sessions`, and an owner holding an admin capability the caller does not is out of reach, as for every other change to a user. No agent token can call any of the four.
- The console has an **Agents** area under Security, for an administrator who holds `manage-sessions`. It draws each agent run under the run that started it, with the agent's client, the person it acts for, its state, what it has left to write and when it expires, narrowed by state or by owner. **Revoke** says, from a count the server makes first and changes nothing by, how many instances and grants it will end before it asks for confirmation. **Approvals** lists what agents asked people to approve and how each was answered, never the digest of the action.
- An administrator's revocation of an agent is recorded twice: `agent.instance_revoked` with `via` set to `admin`, naming the instance, its owner and how many instances it ended, and `agent.instance_revoke`, with the administrator as the actor and the counts of grants and instances. A revocation refused for the owner's capabilities is recorded as `agent.instance_revoke` with the outcome `refused`.
- A person can let an agent client act for them through the me API: `GET`, `POST` and `DELETE /me/delegations`. A delegation names the client they sign in with, an enabled agent client, a scope ceiling and a lifetime of up to 90 days, and a person holds at most 20 live ones. Making one needs a recent sign-in and is refused to an agent's own token; withdrawing one does not end instances already minted, which run until they expire. Withdrawing a person's last delegation, where the sign-in client names no `delegated_actors`, returns new sign-ins to the rule before delegations existed: no `may_act` claim and no scope ceiling, so any agent client may act for them. Each is recorded as `agent.delegation_created` or `agent.delegation_revoked`.
- Three admin capabilities for the console assistant, `use-assistant`, `read-assistant-activity` and `manage-assistant`, which `tenant-admin` carries and which `odudu seed client --capability` can give a service account. A tenant made before this release gains them when `odudu console provision` runs. `GET /admin/tenants/<name>/assistant/status` answers a caller holding `use-assistant` whether the assistant is on: `{"enabled": false}` until `ODUDU_ASSISTANT_MODELS` names a usable `standard` model, then the model each slot runs, the modes offered, the default mode, the models to choose from and the provider, with the host of a self-hosted endpoint and never a key. An AI agent's token is refused this route, and the MCP endpoint answers as it did.
- The console assistant's conversations, behind a configured model and `use-assistant`: `POST /admin/tenants/<name>/assistant/conversations` starts one for the caller (with `page_context`, a route and optionally an object, each a short identifier and never free text), `GET .../conversations/<id>` loads it, `POST .../conversations/<id>/messages` sends a message and streams the turn as server-sent events, and `POST .../conversations/<id>/stop` ends a running turn. A conversation is its owner's alone: anyone else is told it does not exist. The message is stored before the model is called and each step as it ends, so a turn resumes on any server from what is stored; closing the connection ends the turn and what had been said is kept. The console reaches the streaming route without buffering it. With no model configured these paths answer `404`, and an AI agent's token is refused them all.
- Every tenant has a built-in client, `odudu-assistant`, that the console assistant's conversations act as, listed in **Clients** beside `odudu-mcp`. It has no redirect URI and no usable grant, so nothing can sign in to it or get a token from it; it cannot be created, deleted or left in a tenant export, and disabling it turns the assistant off for that tenant. A tenant made before this release gains it when the server starts. A conversation's tool calls act under a grant of it that the server derives from the administrator's own console sign-in, with the scope `mcp:read` in Ask mode and, until a write has a grant of its own, in Act mode too: the administrator's own capabilities still limit every call, signing out or revoking the sign-in ends the conversation, and each call's audit row names `odudu-assistant` as the actor client. A conversation that rests past an agent instance's idle time carries on with a new instance when it is next used. A console client that lists `delegated_actors` must name `odudu-assistant` there, or the assistant is refused. The built-in clients, `odudu-admin`, `odudu-mcp` and `odudu-assistant`, count toward a tenant's `max_clients`, so a tenant at its ceiling can make one client fewer than before, and an import document's `max_clients` must allow for `odudu-admin` and `odudu-assistant` beside its own clients. The assistant client can be renamed, described and disabled, and no other setting of it can be changed. A refused assistant identity or call token leaves an `assistant.access_refused` audit row.

- A **Console assistant** section in the console's Settings, where the server has the assistant switched on and for an administrator who holds `manage-assistant` (a holder of `read-assistant-activity` sees it read-only). A tenant chooses whether the assistant is offered, the mode a person starts in (Ask by default), whether email addresses are masked, how long traces are kept (30 days by default), whether auditors can read conversations (yes by default), and its monthly token limits for each model slot, the answers at once and the steps in one answer. `GET` and `PUT /admin/tenants/<name>/assistant/settings` read and replace them, on an `ETag`, and each change leaves an `assistant.config` audit event with every changed setting as before and after. A tenant that turns the assistant off reads `{ "enabled": false }` from `GET /admin/tenants/<name>/assistant/status`, no other tenant does, and in that tenant starting a conversation or sending a message is refused as a path that was never served. Masking email addresses replaces each address the assistant reads, and in page text, with its first character, `***` and its domain before it reaches the model provider. A system administrator holding `manage-tenants` and `manage-assistant` can manage another tenant's settings. The assistant stops at these limits (see below).
- The console assistant stops at its token limits. Each model call is reserved before it is made, at the most it could cost, and settled to the provider's own count when it ends, so two calls made together cannot both take the last of a limit, though one call can overshoot it. Four levels count, each in tokens: the tenant's month for each model slot (the three monthly settings), one administrator's day (a quarter of that month's allowance, UTC), one conversation's month (2,000,000) and one answer (1,000,000). A level that refuses ends the answer with a message that names the limit and who can change it, and the assistant never moves to a cheaper model. The panel is sent a `data-budget_warning` part when a level passes 80 percent, and the last part of every answer, `data-turn_end`, names why it ended: `done`, `step_cap`, `budget_turn`, `budget_conversation`, `budget_admin`, `budget_tenant`, `aborted` or `error`. A refusal leaves an `assistant.budget` audit event, as does a provider charging more than was reserved; it holds the level, slot, tenant, person and answer and never message text.
- A tenant's **Answers at once** and **Steps in one answer** settings are enforced. A message past that number is refused with `429` and a `Retry-After` while the tenant already has that many answers in progress, counted in the database across every server. An answer ends at the lower of the tenant's steps and free chat's own (8) and reports `step_cap`.
- A conversation longer than one request can hold is compacted before each model call: the oldest exchanges go first, then the output of earlier tool calls, and the last message is cut only if nothing else is left. The newest tool result is cut to a prefix that fits, with a note, rather than left out, and one tool result is cut at 60,000 characters. A reservation is between about 37,000 and 132,000 tokens, so a monthly limit below about 150,000 refuses every answer and one below about 530,000 can refuse some. A call that reports no usage, or only zeros, is charged its whole reservation, so on a provider that does not report usage the meter is an estimate.
- `odudu reap`, and the server's scheduled pass, also resolve the assistant's budget bookkeeping, each tenant in its own short transaction after the retention deletes, so a failure there never undoes them. A call whose process died is counted in full, because what it cost is unknown, and one that never reached the provider is given back; spent counters, settled reservations and lapsed answer places are deleted a bounded batch at a time. The report gains an `assistant` object only on a pass where this did something or failed; its `failed` counts tenants whose upkeep failed, and `odudu reap` then exits 1. [Operating the assistant's budget](apps/docs/content/en/operating/assistant-budget.md) has the details.
- `GET /admin/tenants/<name>/whoami` answers `assistant_available`, true when the server resolved a model for the console assistant. The console asks for the assistant's settings only where it is true, so a server with no assistant is not sent a request it answers as a path that was never served.
- A **Console assistant** section in the console's Settings, where the server has the assistant switched on and for an administrator who holds `manage-assistant` (a holder of `read-assistant-activity` sees it read-only). A tenant chooses whether the assistant is offered, the mode a person starts in (Ask by default), whether email addresses are masked, how long traces are kept (30 days by default), whether auditors can read conversations (yes by default), and its monthly token limits for each model slot, the answers at once and the steps in one answer. `GET` and `PUT /admin/tenants/<name>/assistant/settings` read and replace them, on an `ETag`, and each change leaves an `assistant.config` audit event with every changed setting as before and after. A tenant that turns the assistant off reads `{ "enabled": false }` from `GET /admin/tenants/<name>/assistant/status`, no other tenant does, and in that tenant starting a conversation or sending a message is refused as a path that was never served. Masking email addresses replaces each address the assistant reads, and in page text, with its first character, `***` and its domain before it reaches the model provider. A system administrator holding `manage-tenants` and `manage-assistant` can manage another tenant's settings. The monthly token limits are stored and shown; the assistant does not yet stop at them.
- An **Ask the assistant** button in the console, with its shortcut (Command K, or Control K elsewhere) beside it, for an administrator who holds `use-assistant` where the server has the assistant and the tenant has it on. It sits in the menu, or in the top bar where the menu is hidden, and opens a panel beside the page, or over it where there is no room: the panel is a frame for now, and conversations arrive in it later. A tenant that switched the assistant off, a server without one and a caller without `use-assistant` see no button, no panel and no shortcut, and the console asks nothing more. The shortcut does nothing while a text field in a dialog has the focus. Text the assistant writes will be drawn without images, raw HTML or links that leave the console.
- The assistant's panel. **Ask the assistant** opens a conversation beside the page, or over it on a narrow screen. You ask a question and the answer is written as you watch, with each step the assistant takes listed, and **Stop** ends it here and on the server. The first time, a notice names where your messages go (the provider, or the host of a model your operator runs) and who can read the conversation. The panel says why an answer stopped: the step limit, which allowance was used (the tenant's month, your share of a day, the conversation or the answer), or a failure in plain words with the request's reference. A **Mode** switch chooses Ask or Act, a line at the top says whether you are within your allowance and warns at 80 percent, and the panel comes back to the conversation when it is opened again. An administrator of the system tenant looking at another tenant is not offered the button, since the conversation would have no owner there. A change that waits for approval is said to wait; the card that decides it comes later.
- The console gateway streams `POST /console/api/admin/tenants/<name>/assistant/conversations/<id>/resume` as it is written, as it does a message, so a reverse proxy in front of it must not buffer that route either.

- The console assistant can change things in Act mode, and only with the administrator's approval. A conversation in `act` mode may propose one of twelve changes (a description or name, a role, group or scope that grants nothing, a message override, the tenant's display name and languages, a theme draft). Each is stored as an approval for the administrator, with a card that shows what it would change as before and after, from a read the server made and never from the assistant's words, and the answer ends there. `GET /admin/tenants/<name>/assistant/conversations/<id>/approvals` lists the waiting cards, `POST .../approvals/<approval>` with `{ "approve": true }` or `false` decides one, and `POST .../resume` carries the conversation on and streams the rest of the answer. Only the administrator's own console sign-in can decide: a token the assistant or any other agent holds is refused, and so is another administrator. An approved change runs once, under a grant made for it that holds `mcp:write` alone and ends when it returns, and a changed input, an expired or refused approval, or a second attempt runs nothing. `PUT .../mode` switches a conversation between `ask` and `act`, and in `ask` a change is refused with a reason the assistant reads. A change whose value is too long to show whole on the card is not proposed, at most five changes wait in a conversation and ten for a person, and each approval request is signed with a key derived from `ODUDU_KEK`. Approved assistant writes count in the sign-in's write allowance (`agent_writes_per_grant`, 20 by default), so a sign-in can make at most that many. Rotating `ODUDU_KEK` makes outstanding approvals fail their signature, and they expire within 15 minutes. Deciding is audited as `assistant.approval`; sending another message, stopping or leaving Act mode withdraws what was waiting as a refusal.
- Every console assistant turn leaves audit rows. `assistant.turn` is written when a turn begins (`detail.phase` `started`: the person, conversation, turn, profile, mode and model slot) and when it ends (`ended`: the tokens by slot, the steps and why it stopped, with the outcome `refused` for a token limit and `failed` for an error). A `started` event with no `ended` event more than the turn deadline later (five minutes by default) means the server died, the stream was never read to its end, or the `ended` event could not be written (the server logs `assistant.turn_audit_failed` for that); no monitor ships. A turn is not begun when its first row cannot be written. Each `agent.tool_call` row the assistant leaves now names its `conversation` and `turn`; it is written after the call, so when it cannot be written the read has already run and only its data is withheld (the turn's later calls are then refused), and an approved change stands, recorded by its `assistant.approval` and the change's own rows. None of these rows holds message text, tool output or the name of anything in the tenant. [Operating the assistant's budget](apps/docs/content/en/operating/assistant-budget.md) describes them.

### Changed

- The fixed ceiling of eight on how deep an agent's runs may nest is now `agent_max_delegation_depth`, which defaults to 3 and takes 1 to 8. It applies to agent clients only.
- Starting an assistant conversation (`POST /admin/tenants/<name>/assistant/conversations`) now needs an administrator's own console sign-in, which the conversation's grant is derived from. A token with no sign-in behind it, such as a service account's, is refused with `403`.
- The MCP server's per-sign-in limits of 20 changing calls and 10 creations are the tenant settings `agent_writes_per_grant` and `agent_creates_per_grant`, with the same defaults.
- The audit trail has a seventh event type, `agent_identity`, for what happens to agent runs. It is always stored, so a tenant cannot switch it off, and `?event_type=` on the audit routes takes it.

### Security

- A client that registered itself cannot hold the CIBA grant. Dynamic Client Registration without an initial access token refuses it (`invalid_client_metadata`, naming the grant), and `bc-authorize` and the token endpoint answer `unauthorized_client` to a client registered anonymously or from a metadata document, even if it somehow holds the grant. Clients an administrator created are unchanged.
- A `may_act` restriction on an access token now holds when the refresh token of its grant is the subject of an exchange: the claim is kept on the grant, where before a refresh token carried none. Nothing minted the claim before this release, so no earlier token is affected.
- No credential a client holds can approve a CIBA request. Only the signed-in person the request names can decide it, from the approval page, with a form token tied to their session and to that one approval; anything else, including another person's approval, one that does not exist and one already answered, gets the same `404` page.
- `bc-authorize` answers a hint that names nobody exactly as it answers one that names a person, in its status, its members and the later poll, and runs the same database statements, so it cannot be used to find out who has an account.
- Ending a grant ends everything made from it, however deep and whichever way it ended: a sign-out or a replayed token no longer leaves a token exchanged from the grant, or an agent run, live.

### Fixed

- Two revocations, exchanges or mints that cross over the same chain of grants no longer answer `500` when PostgreSQL ends one of them to break a deadlock. The server runs the transaction that lost again, up to three attempts in all, for sign-out, ending all access, the admin revoke, client and person changes, the token endpoint and the MCP mint; only a third loss answers `500`.
- Deleting a client or a person now ends what was exchanged from their grants by other clients, the tokens an agent acted with under a deleted service account, and the agent instances they ran, together with the instances' own subjects. Before, those tokens stayed live, detached from the grant they came from, and the instance subjects were left listed.
- The me API's CORS preflight now allows `POST` beside `GET`, `PATCH` and `DELETE`, which the delegation route needs from a browser application.
- Revoking a grant whose cascade ended several thousand independent agent runs no longer fails: the audit rows are written in chunks instead of one insert that exceeded the database's limit of 65,535 bound values.

## [0.2.0] - 2026-11-23

### Added

- SDKs, in this repository under `sdks/` and licensed Apache-2.0, each with its own version and changelog. Published to npm and PyPI at 0.1.0. Eight npm packages under the scope `@odudu-io`:
  - `@odudu-io/oidc` is the core without a framework: discovery, the authorization code flow with PKCE, refresh, `prompt=create`, sign-out, a token for the "me" API's audience, and a service's own sign-in with a client secret or a `private_key_jwt` key that renews its token before it expires.
  - `@odudu-io/react` puts the signed-in person into a React app, with a provider, components and hooks, in a mode where a server keeps the tokens or one where the page does and holds them in memory.
  - `@odudu-io/bff` is a backend for frontend (RFC 10017), with adapters for Express and Fastify: the tokens stay on the server, the browser holds one `__Host-` cookie, and a proxy adds the token to calls to the APIs you list. `@odudu-io/next` is the same for Next.js.
  - `@odudu-io/node` checks the access token an API receives, with Express, Fastify and `http` helpers.
  - `@odudu-io/admin-client` and `@odudu-io/me-client` are typed clients for the admin API and the "me" API.
  - `@odudu-io/mcp-stdio` is `odudu mcp` as a package, so `npx @odudu-io/mcp-stdio` runs it on a machine with neither the container image nor a checkout.
- A Python package, `odudu` (Python 3.10 or later), with synchronous and asynchronous clients for the admin API and the "me" API, and, with the `verify`, `fastapi` or `flask` extra, a verifier of Odudu's access tokens, tested against the same fixtures as `@odudu-io/node`.
- The "me" API serves its OpenAPI 3.1 description at `/me/openapi.json`, with no token and no tenant in the path, as `/admin/openapi.json` does for the admin API, and the documentation has a reference page for each of its operations. The typed clients are generated from it.
- Nine runnable examples under `examples/`: a web app, a single-page app, an API, a service that calls it, a Next.js app, a React app with a backend for frontend, a script that calls the admin and "me" APIs, a Python API, and an MCP client. Each is run against a live stack in CI.
- `odudu seed client --capability <name>` gives a service client's account an admin capability when the client is made, once for each one: `view-users`, `manage-users`, `manage-clients`, `manage-tenant`, `manage-keys`, `manage-sessions`, `view-audit`, `view-domains` or `manage-domains`. That is how the first service can call the admin API, which gives a capability only to a caller that already holds one; after that, an administrator changes it in the console or the admin API. A name that is not a capability, or a client that has no service account, is refused and makes no client.
- A tenant export carries every sign-in flow, each by name, and the flow each client is pinned to, and an import restores them, so a client keeps the flow it ran after a move between installations. The document gains `flow_name` (the name of the default flow, which a tenant may have changed), `flows` (every other flow, by name, at most 19) and a `flow` on each client (a flow's name, the default's name for a client pinned to it, or null for a client that follows the default). An import refuses a flow name used twice, a named flow that takes the default's name, and a client that names a flow the document does not hold, each at its path, before it writes anything. A document exported before this release still imports and leaves every client on the default flow, named `default`. A server from before this release refuses a document that carries the new members, naming the unknown key. The published theme, the clients' themes and the images they use are still not carried by an export; this release leaves them out too.
- A tenant chooses whether its registration form asks for a username, under Registration and recovery in the console's Settings (**Username at registration**) or through the settings API as `registration_username`: `required` (the default, as before), `optional` (a blank field gets a generated handle) or `generated` (no username field, and every new account gets a handle of `u-` and ten lowercase letters and digits). `optional` and `generated` need both `login_with_email` and `verify_email` on, because a person with no chosen username signs in by email, and the server refuses the change otherwise and refuses turning either off while the setting is not `required`. A person who chose no username has the handle as their username, and an application receives it as `preferred_username`; it is not an identifier, which is `sub`. A tenant document from before the setting imports with `required`.
- The “(required)” after a label on the registration and update-profile pages and the “(optional)” on the registration page are each an element of their own, with the classes `marker`, `marker-required` and `marker-optional`, so a tenant stylesheet can colour or resize them. A stylesheet cannot replace the word with an asterisk: the checker accepts only `content: none` or an empty string. The pages look the same until a stylesheet says otherwise.
- Each tenant serves a "me" API where a signed-in person reads their own account with their own access token: `GET /tenants/<name>/me/profile`, `/me/credentials`, `/me/sessions` and `/me/consents` (at `/me/...` on a tenant's own domain). A token for it names the tenant's `/me` address as its audience and holds `me:read`. `me:read` and `me:write` are two new scopes every tenant defines, and a tenant that exists before the upgrade gets them when the server migrates; no client has either until you assign it, a request for either is refused with `invalid_scope` at any audience but the tenant's `/me` address, and a request for `me:write` carries `me:read` with it. No path or parameter names a person: the token's own subject is the only one read. A list takes `limit` and `cursor` and answers `items` and `next_cursor`; the credential list adds `recovery_codes_left`, and carries no secret, seed, key or hash. A token that holds `me:write` without `me:read` is refused with `insufficient_scope`. A read refuses a query member it does not know with `400`, `profile` included.
- A person can change their own account through the "me" API with a token that holds `me:write`: `PATCH /tenants/<name>/me/profile` amends their profile claims, `DELETE /me/sessions/<id>` ends one of their sessions and `DELETE /me/sessions` the others (a hundred at most in one request, which says whether any remain), `DELETE /me/consents/<client_id>` withdraws a consent and revokes the grants under it, and `PATCH` and `DELETE /me/credentials/<id>` rename and remove an authenticator. Each change leaves an audit row naming the person, with the fields changed and never their values. Every change needs a session that still stands, so a token whose session has ended, or that names none, is refused `401` `invalid_token` while reads keep answering. The audit trail gains `subject.credential_rename` and `email.changed`, and a session a person ends is recorded as `session.ended` with `via` set to `self`.
- A browser application on another origin can call the "me" API. A client lists its origins in `web_origins` as it does for the token and UserInfo endpoints (a `+` stands for the origins of its redirect addresses), and an answer to a token issued to that client then carries `access-control-allow-origin` for the origin that asked, with `Vary: Origin`. A preflight is answered with `GET, PATCH, DELETE, OPTIONS` and the headers `authorization` and `content-type` for an origin that an enabled client of the tenant lists, and with no allowance for any other; a disabled client allows none, and one tenant's origins never open another's routes. Every answer to an allowed origin exposes `WWW-Authenticate` and `Retry-After`, so a script can read the RFC 9470 challenge of a gated change and the wait of a `429`, and a refusal before the token is read (`401`, `403`, and a `429` for as many refusals as a second budget of 60 a minute allows) is answered to an origin that an enabled client of the tenant lists, never for a tenant that is not there.
- The "me" routes have a budget of 600 requests a minute for each address a request comes from, a preflight included, spent before the token is read; past it the answer is `429` with `Retry-After`. It is kept in the process, as the MCP endpoint's is.
- After a tenant switches to a domain of its own, or back to its path address, the "me" routes keep answering at the address it left for the same hour its tokens are accepted there. Before, a token issued under the old address could be used at the other routes of that window and not at these.
- A new email address is asked for through `PATCH /me/profile` and does not take effect until the person follows the link mailed to the new address. The answer is `202` whether or not another account holds the address, and then nothing is mailed. A server with no way to send mail answers `503` `mail_unavailable`.
- Changes that could lock a person out or hand their account over (a new address, a new username, ending all other sessions, withdrawing a consent, removing an authenticator) need a recent sign-in. An older one is answered `401` with the RFC 9470 challenge (`insufficient_user_authentication`, `max_age` and, for a person who holds a second factor, `acr_values`), and the application sends the person through `/authorize` again. The window is the tenant setting `session_freshness_seconds`: 300 seconds by default, 30 to 3600, in the console's Settings under Sessions.
- Removing an authenticator through the "me" API is refused with `409` when it is the last way to sign in (`last_sign_in_method`) or the last second factor of a tenant that requires one (`last_second_factor`).
- An application can send a signed-in person to Odudu to change one credential. The authorization request takes `action`, one of `update-password`, `configure-totp`, `configure-passkey` or `generate-recovery-codes`; the person sees the page Odudu already shows for that change, with a "Cancel and go back" control, and the redirect carries `action_status` (`success`, `cancelled` or `error`) beside `code`, `state` and `iss`. A sign-in older than the tenant's `session_freshness_seconds` is asked for again first. `action_status` is a hint, since a person who closes the tab sends nothing: the application reads the outcome from the credential list of the "me" API, which also counts the recovery codes left. A requested password change asks for the current password first, a requested authenticator replaces one the person already has, and a person who holds recovery codes is asked to confirm before they are replaced. The guide in the documentation is called Send a person to change a credential.
- What a client may start is its `allowed_actions` setting, empty for every client: a field of the client in the admin API (create, amend and read), a checklist under Application actions on the Advanced tab of the client in the console, a member of a tenant export and import, and `odudu seed client --allow-action <action>`, which assigns `me:read` to the client itself. A request that names an action the client is not allowed, an unknown name, the parameter twice or empty is refused with `invalid_request` at the client's redirect address. A client that may start an action has to hold `me:read`, which is how it reads the outcome: naming an action without it is refused with `allowed_actions_need_me_read`, and the scope cannot be unassigned from such a client or deleted while one holds it. Dynamic registration refuses `allowed_actions`, as it does `skip_logout_confirmation`.
- The audit trail records each action an application sends a person to: `action.requested` each time the page is shown, then `action.completed`, `action.cancelled` or `action.failed`, with the action in `detail` and the application as the actor client.
- A link an administrator mails can return the person to an application. `POST /admin/tenants/<name>/subjects/<id>/password-reset`, `verification` and `actions-email` take an optional `client_id`, and a `redirect_uri` when that client registers more than one; the last page of the link then offers a "Return to the application" link to that registered address with `action_status` (`success`, or `error` for a link that cannot be used), a hint that the "me" API confirms. The two older sends gain an optional body, and a request without one behaves as before; a body that names any other field is now refused with `400`, where a body was ignored before. A `client_id` that is not an enabled client of the tenant is refused with `400` `return-client-unknown`, an address the client does not register with `return-redirect-uri-unregistered`, and none named where the client registers several with `return-redirect-uri-required`. The page drops the link when the client was deleted, disabled or stopped registering the address after the mail was sent.
- A person who holds a passkey and no password can set a first password. `update-password`, sent by an application (`/authorize?action=update-password`) or owed by an administrator, asks for no current password when there is none, and sets one only on a sign-in whose passkey assertion verified the person (a passkey that proved only possession, or a sign-in that ran no passkey, ends in `action_status=error` as before). The tenant's password rules and the breached-password check apply, the address on file is told by mail (`password_added`, to a verified address only, in English and Arabic), the audit row is `password.changed` with `first_password` and `notice`, and the person's sign-in flow does not change. A person who holds a password is still asked for it.
- A set of recovery codes can be replaced once an hour, on every page that makes one, because each set costs ten password hashes and a person with a valid password could otherwise ask for them without end. A person who asks sooner while they still have codes to spend is shown how many minutes to wait (`429`), and the audit trail records `recovery_codes.refused`. The first set and a set with no code left to spend are never held back. A set the sign-in is waiting for (a new authenticator, say) is issued at once, and a reload of the page that shows it, which would make a different set, is held to one every 30 seconds (the same `429`, `recovery_codes.refused` in the audit trail): the page then says how many seconds remain and offers a button that asks again, and the acknowledgement that finishes the sign-in carries no code and is never held back, so the bound cannot keep a person from finishing it. The hour is counted from when the last set was made, which the server records on the person from this version on: sets made before the upgrade have no time, so each can be replaced once straight away.
- The credential list of the "me" API says when a person's recovery codes are running low: `recovery_codes_low` is `true` when they hold a set with fewer unspent codes than the tenant's `recovery_code_warn_below` setting, and `false` when they hold no set. The setting is 3 by default, 0 to 10, and 0 turns the warning off; it is in the console's Settings under Registration and recovery. Odudu serves no page of its own that a person lands on after signing in, so an application shows the warning from this field and sends the person to `generate-recovery-codes`; the sign-in itself never gains a step for it.
- A tenant chooses what its new authenticators are made with, under Authenticators in the console's Settings or through the settings API: `totp_algorithm` (`SHA1`, `SHA256` or `SHA512`), `totp_digits` (6 or 8), `totp_period` (30 or 60 seconds), `webauthn_user_verification` and `webauthn_resident_key` (`required`, `preferred` or `discouraged`) and `recovery_code_count` (8 to 16). Every setting starts at what Odudu has always done, so a tenant that changes nothing sees nothing change. A tenant export and import carry them. `recovery_code_warn_below` may not exceed `recovery_code_count`.
- An authenticator app, a passkey and a set of recovery codes keep what they were made with. A change applies to the next one made: an app already enrolled is checked by its own algorithm, digits and period and a passkey by its own user verification, so nobody is locked out by a change of policy. The enrolment page tells the person what their app must support when the parameters are not `SHA1`, 6 digits and 30 seconds, and the `otpauth://` address and QR code carry them.
- A tenant can ask every person for a passkey. With `require_passkey` on, under Authenticators in the console's Settings or through the settings API, a person who signs in and holds no passkey for the address they signed in at is asked to register one before the sign-in completes. Sessions already open are not touched, the person is asked once however often they sign in, and a person who removes their last passkey is asked again. The page has no way to skip it: an administrator can clear the action under Required actions on the person's record, which lets that one sign-in finish and is asked again at the next while the switch is on. Turning the switch off stops new actions and does not remove one already owed, so clear it on the person's record as well. A deployment with no public base URL, or one that is an IP address, never asks unless the tenant has a domain of its own. The setting is off by default and is carried by a tenant export and import.
- A session is shown against the browser it was opened on. A sign-in that ends in a redirect sets a cookie, `<tenant>-device` (`__Host-<tenant>-device` with TLS on): random, `HttpOnly`, same-site, good for 400 days, per tenant address, and sent back and set again at every sign-in. It names no one and is never put in a token. A session stores a digest of it, which `GET /tenants/<name>/me/sessions` returns as `device` (it was always `null`) and the admin API's session lists return as `device` too; sessions that share one were opened on one browser, and a session opened before the upgrade has `null`. The console's session lists for a person, a client and the tenant gain a Device column that groups the sessions of one browser together with a count. A person who clears their cookies starts a new device.
- A passkey sign-in records whether the passkey verified the person: the `login.passkey` audit row says `user_verified` in its detail, so a sign-in made with a passkey that proved only possession can be told from one that proved the person.
- A new password is refused when it is a password known from breaches. A tenant chooses where it is checked with `breached_check`, under Password policy in the console's Settings or through the settings API: `dataset` (the default), `remote` or `off`. The dataset is a table in your own database, filled by `odudu breached-passwords load <file>` from a file of SHA-1 hashes in the published range format; it starts empty, so nothing is refused until you load one. The command reads the file as a stream, adds 5,000 hashes to a statement and skips those already held, so loading the same file again adds nothing.
- The check runs after the tenant's other password rules, on registration, a reset link, an administrator's actions link and the change-password page, and the refusal has its own message, in English and Arabic, that never says which source found it. `remote` asks a range service at one fixed host, `api.pwnedpasswords.com`, for the first five characters of the hash and sends nothing else. It waits at most 3 seconds without holding a database connection, reads at most 128 KiB, allows a tenant 4 lookups at once and the server 8, and connects only to a public address. `breached_on_error` says what a lookup that failed does: `open` accepts the password (the default) and `closed` refuses it and asks the person to try again.
- The audit row of a password write, `account.registered`, `password.reset` or `password.changed`, says in `detail.breached_check` what the check decided: `passed`, `dataset_empty` (the dataset holds no hash, so nothing could be found), `error_open` or `off`. `odudu breached-passwords status` says whether the dataset holds anything.
- A person whose verification link was used or has expired can ask for another from the page that says so. The page has a _Send a new link_ button, which posts the key of the refused link to `POST /tenants/<name>/login-actions/resend-verification`; a new mail goes to the address that link was for, with the client it returned to, only while that address still needs verifying. At most three an hour are queued to one address, apart from the budgets of other mail, and counted per server process, so several instances multiply it; the answer is the same page whether or not one was: an unknown key, a verified address, a spent budget and a queued mail cannot be told apart. The audit trail records `email.verification_resent` for each request that queued a mail, with no address in it.
- `odudu reconcile-accounts` folds accounts that hold one address apart from its case into one, in every tenant. The account with a verified address stays, and where exactly one has signed in, that one; then the oldest. It takes the credentials a person set up from the others, one transaction for each group, and the others are disabled with their address cleared and their pending links deleted, so no account is deleted and nothing already in the audit trail is touched. It prints one JSON line for each pair merged, with the address that was cleared, then a report. Each retired account leaves one `account.reconciled` audit row naming the one that stayed and the credentials and consents that moved, with no address. A merge is not reversed by enabling the account again: what moved stays with the survivor. It refuses a group, and changes nothing in it, where more than one account has signed in, where no account has a verified address, or where an unverified account that has signed in would be left behind by a verified one; the report lists them with their subject ids. A sign-in is seen from a live session, a grant, a credential that was used or an audit row recording a successful sign-in, so a person whose only sign-in is older than the tenant's audit retention, with no session left, looks as if they never signed in. A group in which an account signs in while it is being merged is refused as `loser_signed_in` and left as it was. `--dry-run` reports what it would do and changes nothing (its pair lines carry no `moved`), and running it again finds only what was refused. It needs `ODUDU_APP_DATABASE_URL`, as `odudu reap` does, and exits `1` when a group failed.
- Two accounts of a tenant can no longer hold one address apart from its case: migration `0139` builds a partial unique index on `(tenant_id, email_search)`, which reads `users` once and blocks writes to it while the migration builds it, with the server stopped. Run `odudu reconcile-accounts` before upgrading where you can. A database that still holds such a pair does not fail the migration: the index is skipped with a warning, the server boots without it, says so at every start, and the first start after the command has folded the pairs builds it `CONCURRENTLY`, so writes go on. An index you drop on purpose is built again at the next start.
- Three more required actions: `verify-email`, `update-profile` and `accept-terms`, set on a person under Required actions in the console or with `PUT /admin/tenants/<name>/subjects/<id>/required-actions`. A sign-in asks for them in that order, `verify-email` before the password and the other two after the second factor and the recovery codes. The address page shows the address held and mails the verification link to it when asked, at most three an hour to one address; "I have verified it" checks the address again, and opening the link ends the action wherever it is opened. The profile page lists every profile field a person can edit through `PATCH /me/profile`, with what they hold, marks the ones the tenant requires and ends once each of those has a value; every value sent is checked by the rules the me API applies, all refusals at once, and nothing is written until the whole form is acceptable. The terms page links the terms, names the version and has one box, and carries the version it shows: if the terms changed while it was open it comes back at the new version and records nothing. Each page has no way out when the tenant asks, and is themed and translated like the others.
- A tenant can publish terms: `terms_uri` (an https address, or http to this machine, no fragment) and `terms_version` (1 to 64 characters, `1` by default) under Terms in the console's Settings, through the settings API, in a tenant export and import and with `odudu seed tenant --set`. Setting them asks nobody: an administrator owes `accept-terms` to each person, and again when the terms change. `terms_uri` is at most 2048 characters and carries no user name or password, and `terms_version` is counted in characters. A person's acceptance is recorded with the version and the time, and the audit trail gains `terms.accepted`; `GET /admin/tenants/<name>/subjects/<id>/terms-acceptances` lists them, newest first and paged, under `view-users`, an MCP read tool `list_subject_terms_acceptances` serves it, and the Required actions tab of the subject shows them.
- A tenant chooses which profile claims `update-profile` needs a person to have: `required_profile_fields`, given and family name by default, none allowed, under Profile in the console's Settings or through the settings API, in a tenant export and import.
- An application may start `verify-email` and `update-profile` through `/authorize?action=`, and a client's `allowed_actions` lists them; `accept-terms` is the tenant's alone and is refused by the setting and by `/authorize`.
- The admin API refuses an action that cannot be owed, with `409`: `no-email` for `verify-email` on a subject with no address, `terms-not-configured` for `accept-terms` while the tenant has no `terms_uri`, and `no-editable-profile-fields` for `update-profile` where the tenant requires a profile field a person may not edit; a person may edit every profile claim today, so no tenant is refused yet. Only the actions a request adds are judged, so a list that keeps an action which has since become impossible can still be saved.
- Three page kinds a theme can replace, `verify-email`, `update-profile` and `accept-terms`, each with the form, fields, submit and error parts of the others, and a `page-` class for each.
- A tenant can hold several sign-in flows, up to 20 in all, the default flow included. `GET /admin/tenants/<name>/flows` lists them by name (never paged, with a `total` and an `ETag`), `POST` makes one from a name and steps (1 to 64 characters, unique within the tenant, at most 20 steps), `GET /flows/<id>` reads one, `PUT /flows/<id>` replaces its name and steps and needs `If-Match` (`428` without it, `412` when stale), `POST /flows/<id>/make-default` makes it the tenant's default, in one transaction, on its `ETag` in `If-Match` (audited as `flow.default_set`; a sign-in already under way takes its next step from the new default), and `DELETE /flows/<id>` removes it, on the flow's `ETag` in `If-Match` like the other writes, so a flow another administrator has changed is not deleted unseen. A name another flow holds is refused with `409` `flow-name-taken`, a 21st flow with `409` `flow-limit`, and deleting the default flow with `409` `default-flow`; a step list is refused at save time with the `400` types `PUT /flow/executions` already has, the unknown and the repeated authenticator carrying `errors` that name the step as `steps[N].authenticator`. The creates, replaces and deletes are audited as `flow.create`, `flow.amend` and `flow.delete`, with the name and steps. `GET`/`PUT /flow/executions` still read and write the default flow's steps, and `PUT` now refuses more than 20 steps with `400`. A client names the flow it runs through its `flow_id`; a client that names none runs the default.
- The console's Sign-in flow page lists the tenant's flows with the default marked, makes one from the default's steps (**New flow**), opens one to change its name and steps with the same editor as the default's, makes any other flow the default (**Make default**), and deletes any but the default, each after a confirmation.
- An MCP client with `mcp:read` and a tenant administrator's `manage-tenant` capability reads the flows with `list_flows` and `get_flow`, so the endpoint now has 64 tools that read. Creating, replacing and deleting a flow are not offered to an agent.
- A client can run a sign-in flow of its own. Its `flow_id` setting is the id of one of the tenant's flows, or null, which every client has until it is set, to follow the tenant's default: a field of the client in the admin API (create, amend and read, with `unknown_flow` in `errors` for a flow the tenant does not have), a **Sign-in flow** choice on the Advanced tab of the client in the console, and `odudu seed client --flow <name>`. `/authorize` runs that flow for a request from the client: the first step offered, the steps after it and whether a single sign-on session a person already holds is enough are the flow's, so two clients of one tenant can ask for different things. A sign-in stays on the flow its client named when it began, however the client's setting changes before it ends; one that began on the default follows the tenant's default at each step, as before. The audit trail records `flow_id` on `client.create` and `client.amend`. A tenant export carries each client's flow by name instead of its id.
- A flow some client names is not deleted: `DELETE /flows/<id>` is refused with `409` `flow-in-use`, whose `detail` says how many clients name it and gives the `client_id` of at most ten of them. `GET /flows` gives each flow a `client_count`, and the console's flows list shows it in a Clients column and says so in the delete dialog.
- A step of a sign-in flow can set what a new authenticator is made with, for the flows that ask for it: an `otp` step takes `algorithm`, `digits` and `period`, a `passkey` step `user_verification` and `resident_key`, a `recovery-code` step `count`, each under the same choices and range as the tenant setting of the same meaning, as `settings` on the step in `POST /admin/tenants/<name>/flows`, `PUT /admin/tenants/<name>/flows/<id>` and `PUT /flow/executions`. A key left out takes the tenant's value, so a flow with no settings behaves as before. A person who enrols during a sign-in is enrolled under the flow that sign-in runs, the flow their client names or else the default; what was enrolled earlier keeps the values it was made with. Settings on any other step, or a key its authenticator does not read, are refused with `400` `flow-step-settings` naming the step. A tenant export and import carry them, and the audit rows of a flow's creation, amendment and replacement through `PUT /flow/executions` record them.
- The Sign-in flow page shows each `otp`, `passkey` and `recovery-code` step's settings beside it, each starting at the tenant's own value, and keeps the settings a flow already has when only its order is saved.
- A person is told by mail when a password reset sets their password. The message goes to the address on the account, verified or not, says the password was reset using a mailed link and when, and carries no link, code or password; it is in English and Arabic, wears the tenant's mail look, and can be reworded under Message overrides (`resetCompleted.*`). The `password.reset` audit row says in `detail.notice` whether it was queued (`sent`) or the account has no address (`skipped_none`). It is queued in the transaction that sets the password, so a reset that rolls back sends nothing.

### Changed

- The admin API's OpenAPI document is smaller. Each response and schema that many operations share is defined once and referenced, where each operation spelled its own copy of the error response, so a generated client holds one type for each.
- `odudu mcp` runs on `@odudu-io/mcp-stdio`. Its flags, environment variables, help and exit status are the same.
- The guides for a web app, a single-page app, an API and a service, and the example each one uses, now sign in and verify tokens with the SDKs and no longer by hand.
- Each field of the registration form now says whether it is required or optional, in words after its label, and a required input carries the HTML `required` attribute so a browser asks before the request. The update-profile page keeps marking only its required fields, now with the same markup. The server still checks every field as before.
- This release cannot be rolled back by redeploying the previous image: migration `0137` moves a tenant's sign-in steps into the new `flows` table and drops `authentication_executions`, which the previous release reads. Take a backup first (the Upgrading page says so); the way back is the backup restored into a fresh database.
- The page a verification or registration link opens names the address and the tenant above its button, and still changes nothing until the button is pressed: a mail scanner that opens the link leaves it unspent. A link mailed before the upgrade opens the same page. The page a refused verification link shows now offers the new-link button, so it is a `verification` page where it was a `notice` one; a theme's `verification` template can place the way back to sign in with a new optional `links` part, and a theme without it shows the page without that link.
- `max_sessions_per_browser` is now exact for one person's sessions on a browser that already holds the device cookie. Before, `k` sign-ins from one browser at the same instant left `cap + (k - 1)` sessions; they now leave the cap. Two people signing in at once on one browser are still counted only through the browser's cookies. A session one of them leaves that the browser's cookies no longer name still cannot be ended by signing out, and is listed under its device and counted against the cap. A browser's first sign-in, which has no device cookie yet, is bounded as before.
- An application that sends a person to `generate-recovery-codes` now asks before it makes a first set, as it already did before replacing one. Nothing is made while the question is on the screen, so reloading it changes nothing and cancelling it no longer follows a set that was made at once.
- A tenant's discovery document and its authorization server metadata list `me:read` and `me:write` in `scopes_supported`, with the tenant's other scopes. A tenant starts with twelve scopes where it started with ten, and the console's scope list and a tenant export show the two.
- An administrator who sets a subject's address (`PATCH /admin/tenants/<name>/subjects/<id>`) is refused with `409` when another subject of the tenant holds it in any case, as an exact repeat already was. Before, `Ada@example.com` and `ada@example.com` could be held by two accounts, which registration and a mailed link already treated as one address. A subject can still change the case of its own address.
- A link mailed to a subject an administrator has disabled (a reset, a verification or an actions link) is refused as an expired one is, and the "me" API refuses an access token whose subject is disabled, so the token stops reading at once.
- A mailed link keeps its four actions: `POST .../actions-email` takes `update-password`, `configure-totp`, `configure-passkey` and `generate-recovery-codes`, and refuses the others with `400`, since a link cannot show the pages of the rest.
- A sign-in clears an owed action no page could finish instead of stopping at it: `verify-email` for an address already verified or not there, `accept-terms` for terms the tenant no longer has or a version the person accepted, and `generate-recovery-codes` for a person with no authenticator app, as before.

- The console's Settings page is easier to read and to move around. Its sections are listed by links under five headings, in a strip or a rail that stays in view, with the section in view marked and a dot on one that holds unsaved changes. Authenticators is split into groups for the authenticator app, passkeys and recovery codes, and **Require a passkey** has a section of its own, **Passkey requirement**. Password policy and Profile are grouped, a duration is typed with a unit menu (seconds, minutes, hours or days) and a value outside its range is marked before you save. **When a remote lookup fails** is dimmed unless the breached-password check is set to the remote lookup.
- The sign-in flow's step rows say less. A step's settings carry the names the Settings page uses, under a **Settings** heading, and the move buttons are chevrons. A client's sign-in flow choice names the tenant default flow and links to the flow editor, and the Sessions lists call the device column **Browser**.
- An administrator's change of a person's email address (`PATCH /admin/tenants/<name>/subjects/<id>`, or the Email field on the person's record in the console) is no longer stored at once. Odudu mails the new address a link and keeps the current address on the account, verified and able to sign the person in, until the person follows it; a verified current address is told that a change was asked for. The subject carries `pending_email` in `GET` and `PATCH`, the record in the console shows the pending change with **Cancel the change**, and asking for the address the person already has withdraws it. The change is refused with `409` (`no-mail-relay`) when neither the tenant nor the deployment has a way to send mail, and with `503` when the deployment has no public base URL, before anything is written. Before, the new address replaced the old one, unverified, so a person who signed in by address could no longer sign in.
- With **Verify email addresses** (`verify_email`) on, a password reset link is mailed only to an address the person has verified. A request for any other address is answered as before, with the same page and the same timing, and mails nothing, so nobody can tell from the answer whether an address is held or verified. A person with an unverified address asks for a new verification link, or an administrator sends one or a reset from the person's record. With the setting off, nothing changes: a link goes to any address an account holds. Before, a reset link also went to an address nobody had proved.

### Fixed

- The admin API's OpenAPI document described every `204 No Content` response as a JSON body with an empty schema, so a client generated from it tried to parse an empty answer. Version 0.1.0's document had the same fault. It now describes those responses with no body.

### Security

- `odudu seed assign-scope`, a tenant import and a default assignment of `me:write` now refuse a client that would hold it without `me:read`, as the admin API's assignment already did.
- A mail the person did not ask for no longer completes anything by being opened, and the page it opens says which address and tenant it would confirm, so it can be recognised and left alone. Asking for a new verification link tells nothing about whether an address exists or is waiting to be verified: the page, the status and the bytes are the same in every case.
- Removing a second factor through the "me" API needs a sign-in that ran two factors (a password and an app code, or a passkey that verified the person), not only a recent one. A sign-in made through a client whose flow asks for a password alone is answered `401` with the RFC 9470 challenge naming `acr_values="2"`, as an application that ignores the challenge would otherwise pass.
- A token that carries `act`, one issued to an agent acting for the person, may read the "me" API and is refused every write with `403` `agent_not_permitted`.
- An application cannot make an action look successful: the redirect's `action_status` is written by Odudu from the state of the request it kept, never from anything the browser or the client sends, and an action the client is not allowed is refused before any page is shown. Recovery codes are not replaced until the person confirms, the page that shows the new set has no way to cancel it, and a requested password change needs the current password, which counts against the tenant's lockout like a wrong password at sign-in.
- A person is told by mail when they change how they sign in. Setting up an authenticator app or a passkey, saving a new set of recovery codes, removing an authenticator through the "me" API and asking for a new email address each send a notice, in the tenant's theme and in the person's language (English and Arabic ship), saying what changed and when and what to do if it was not them. It carries no link, code or secret. The notice goes only to a verified address: for an address nobody verified the change is still allowed, nothing is mailed, and the audit row says `notice` is `skipped_unverified` (`skipped_none` where the person has no address, `sent` otherwise), on `otp.enrolled`, `passkey.enrolled`, `recovery_codes.issued`, `subject.credential_delete` and the `subject.profile_amend` that asks for an address. A request for a new address tells the address being left, since the new one already gets the link; a request for an address already in use, for the address the account has, or that is throttled queues no notice, and the audit row says `skipped` with the reason. Changes an administrator makes keep their own mails.
- A passkey assertion that lacks user verification, which a passkey made where the tenant did not require it can give, proves possession of the key and nothing else, so it signs in as one factor: the person is still asked for an authenticator app code where they have one or the tenant requires one, and a sign-in by the passkey alone has `acr` `1` and an `amr` with no `user`. Passkeys made with verification required are unchanged, and are still refused an assertion without it, whatever the tenant has chosen since. Passkey sign-in always asks the browser for `preferred` verification.
- A passkey the browser reports as not stored on the device is refused at enrolment under any `webauthn_resident_key` value, because passkey sign-in names no username and only a stored passkey can answer it. The person is told to add one that can be stored.
- The change-password page offers "End my other sessions", checked. A person who leaves it checked signs themselves out everywhere else: every other session ends, with the refresh tokens bound to it and a back-channel logout to each client that registered one, and the session they are using stays. A form that sends nothing for the box ends none, as a browser does for a box that was cleared. Whether the person asked is recorded as `ended_other_sessions` on the `password.changed` audit event. A password set from a mailed link still ends every session whatever the person chose, so the reset page has no box.
- A password that appears in a breach list can no longer be chosen where a tenant checks one, which every tenant does against its dataset once one is loaded. Nothing leaves the server for the dataset. The remote lookup sends five characters of a SHA-1 hash to one fixed host and neither the password nor its full hash; it carries no cookie, tenant name or account. `odudu seed` still checks only the policy rules, and the password an administrator's link lets a person set goes through the check like any other.
- An administrator's change of an email address no longer stores an address nobody has proved. The address a person holds changes only when they follow the link mailed to the new one, so a mistyped or hostile address can no longer receive mail for the account, or the way into it through a reset link.

## [0.1.0] - 2026-11-07

The first stable release. It gathers everything from the release candidates and
adds the MCP server: each tenant serves an MCP endpoint that an AI assistant can
read from and, within strict limits, write through. Odudu has had no
independent security review.

### Added

- Every tenant has two new scopes, `mcp:read` and `mcp:write`, for the clients that will use its MCP endpoint, and a tenant that exists before the upgrade gets them when the server migrates. Neither is given to any client until you assign it. A request for either is refused with `invalid_scope` unless the resource is the tenant's MCP address (its address followed by `/mcp`) or the admin API, at the sign-in request and at the token endpoint for every grant, so a client registered for several audiences must name the MCP address as its `resource`. The consent screen says in plain words what each lets an application do, in English and Arabic, and `odudu seed restore-scopes` creates them again if one is deleted.
- Every tenant has a built-in public client, `odudu-mcp`, for local MCP tools to sign in through: PKCE is required, it holds no secret, and its access tokens are for the admin API. It asks for `mcp:read`, with `mcp:write` optional, and shows each person a consent screen. A tenant that exists before the upgrade gets it when the server migrates, unless the tenant already has a client of that name, which is left alone. Its redirect addresses are `http://127.0.0.1` and `http://[::1]`, and a public client registered with a loopback address and no port is accepted at any port, as RFC 8252 asks of an app that listens on a free one; `localhost`, other hosts and confidential clients are still matched exactly. You can disable `odudu-mcp` but not delete it, and the client ID is reserved. A tenant export carries it, and an import reproduces it.
- Each tenant publishes OAuth 2.0 authorization server metadata (RFC 8414), so a client that knows only a resource can find where to sign in without being told. It is at `/.well-known/oauth-authorization-server/tenants/<name>` on your base address, or at `/.well-known/oauth-authorization-server` on a tenant's own domain, and states the tenant's issuer and the same endpoints as its discovery document. It lists `mcp:read` and `mcp:write` among the scopes, `none` and `private_key_jwt` among the ways a client authenticates, and the signing algorithms `private_key_jwt` accepts. A tenant that is disabled or does not exist answers an empty `404`.
- Each tenant publishes OAuth 2.0 protected resource metadata (RFC 9728) for its MCP endpoint, so an MCP client given only that address can find where to sign in. It is at `/.well-known/oauth-protected-resource/tenants/<name>/mcp` on your base address, or at `/.well-known/oauth-protected-resource/mcp` on a tenant's own domain. It states the MCP address as the `resource`, the tenant's issuer as its authorization server (the same issuer its authorization server metadata states), and `mcp:read` and `mcp:write` as the scopes. A tenant that is disabled or does not exist answers an empty `404`.
- An access token that carries `mcp:write` lives ten minutes at most, even where the tenant or client sets a longer lifetime (a shorter one still applies), and is issued with no refresh token, so a client holding `mcp:write` signs the person in again to keep writing. `offline_access` asked for beside `mcp:write` is ignored without an error. `mcp:read` follows the tenant's lifetimes as before.
- A tenant can have a public address of its own, such as `login.acme.com`, instead of `/tenants/<name>` under your server's address. Its sign-in pages, the issuer its tokens carry, its cookies and the links in its mail follow that address, and a tenant that does nothing behaves exactly as before. The guide is [Custom domains](apps/docs/content/en/operating/custom-domains.md).
- A tenant proves it owns a host by publishing a DNS TXT record under `_odudu-challenge.<host>`, in the console's new Domains area or through `/admin/tenants/{tenant}/domains`. A tenant registers up to twenty domains and has one as its address; registering claims nothing, and the first tenant to prove a host keeps it.
- Switching a tenant to its domain, and back, from the base address. Sign-in cookies belong to one host, so people sign in again at the new address; sessions at the address left are not ended and resume if the tenant switches back. For one hour, the longest an access token lives, the address the tenant left keeps serving the token, user info, introspection, revocation, key, logout and discovery endpoints, and points sign-in to the new address. The console says how many people a switch hides passkeys from before you confirm it.
- `GET /internal/domain-check?domain=<host>` for your reverse proxy's on-demand TLS question (Caddy's `on_demand_tls { ask }`): `200` for a host Odudu serves, `404` for every other, with no body. Keep it off the public network; it takes no secret.
- A recheck of every verified domain's ownership record, `odudu domains recheck`, which the server also runs every hour. A domain whose record is gone for three passes fails, and a tenant that has it as its address returns to its path address. A resolver outage counts as nothing, and a failed domain verifies again once its record is back.
- `odudu seed domain --tenant <name> --host <host>`, with `--canonical` and `--assume-verified`, which marks a host verified without the DNS proof and refuses to run in production.
- Settings `ODUDU_DOMAIN_RECHECK_ENABLED`, `ODUDU_DOMAIN_RECHECK_INTERVAL_SECONDS` and `ODUDU_DOMAIN_RECHECK_FAILURES` for the recheck, and `ODUDU_RETENTION_PENDING_DOMAIN_SECONDS` (seven days) for how long a domain nobody proved is kept. `odudu reap` reports `tenant_issuer_retirements` and `tenant_domains` as well.
- The capabilities `view-domains` and `manage-domains`, and a built-in role for each.
- `odudu reap` reports a new table, `client_metadata_cache`, after `tenant_issuer_retirements`: the Client ID Metadata Documents the server fetched for a tenant, which are deleted once their cache lifetime (one minute to a day) has ended. A tenant keeps at most 1,000 of them; past that, a new one replaces the one unused longest that never completed a sign-in, and is refused if every one has. Nothing fills it until a tenant turns on client metadata documents, so the count is `0` for now.
- A tenant can let an app identify itself with a web address instead of registering first. Turn on the `cimd_enabled` setting (off by default; `odudu seed tenant --name <tenant> --set cimd_enabled=true`, or the settings API) and a `client_id` that is an `https` address is resolved to the Client ID Metadata Document served there. The consent page shows the document's name, the host and port of the address and every redirect address; a redirect address the document does not list is refused. The fetch is limited to five KiB and three seconds, follows no redirect, refuses private and local addresses, and is cached for the document's `Cache-Control` lifetime. A tenant's authorization server metadata states `client_id_metadata_document_supported` while the setting is on. With it off, such a `client_id` is refused like any unknown client. Such a client has no audience and no MCP scope until a tenant policy gives them.
- `odudu reap` reports another table, `cimd_clients`, after `client_metadata_cache`: a client kept from a metadata document is deleted when nobody has resolved its document for thirty days, unless it still holds a refresh token that can be used (or that lapsed within the longest access token's life). A tenant keeps at most 1,000 of them.
- A client that came from a metadata document shows `cimd` as its `registration_origin` in the admin API and the console, and is left out of a tenant export.
- A tenant can open client registration to MCP clients alone. The new `client_registration_policy` value `mcp` lets an agent register itself without a token, as a public client with `https` or loopback `http` redirect addresses, which may ask for `mcp:read` and never `mcp:write`, and whose only audience is the tenant's MCP address. A request for `mcp:read mcp:write` registers with `mcp:read` only, and the response's `scope` says what was kept; one whose scopes are all unavailable (only `mcp:write`, for example), or that names another audience, grant or authentication method, is refused with `invalid_client_metadata`. A tenant that holds 1,000 clients that registered themselves makes room by removing the oldest public one nobody used and refuses when there is none (a confidential one that registered itself is never removed that way), and one address may register ten clients an hour on a tenant, and the tenant sixty (`429` with `Retry-After` past either). It also refuses a key set and a logout address. `odudu reap` now deletes a public client that registered itself, under the `open` policy as well as `mcp`, once it is a week old and nobody approved it, signed in through it or holds a grant that has not yet been reaped; it reports them as `dynamic_clients`. A client with an approval (even one the person later withdrew), a recent grant, or a sign-in under way stays. A registration token presented to a tenant on `mcp` is ignored and not spent. Set it with `odudu seed tenant --set`, through the settings API, or in the console under Settings, Client registration, where the switch for client metadata documents (`cimd_enabled`) sits beside it; the tenant export carries both.
- On a tenant whose policy is `mcp`, a client that came from a metadata document is given the MCP address as its only audience and `mcp:read` as an optional scope by the policy, never by what its document says, and loses both the next time its document is resolved if the policy is changed. A document client that authenticates with a key is not given them. When the policy is turned off, no client that came through it is offered the MCP address or `mcp:read` at its next sign-in or refresh, so an existing refresh chain stops carrying them; disable or delete the client to end the chain at once. Neither kind of client is ever given `mcp:write`, even if an administrator assigns it.
- Two settings on each client limit token exchange, both off for every client: `token_exchange_allowed_for_public` lets a public client use the exchange grant, and `token_exchange_actor_from_other_client` lets a client present an actor token that was issued to another client. They are fields of the client in the admin API (changes are audited with their values, and so now are changes to `consent_required` and `token_exchange_impersonation_allowed`, which the trail left out before; a client's `ETag` follows them), they travel in a tenant export and import (a document from before them imports with both off), and `odudu seed client` sets them with `--token-exchange-allowed-for-public` and `--token-exchange-actor-from-other-client`, each needing `--grant-type urn:ietf:params:oauth:grant-type:token-exchange`. The console's client page shows them under Token exchange, beside impersonation. Neither is on for any built-in client, and the built-in admin client refuses a change to either.
- The admin API `POST` routes take an `Idempotency-Key` header, so a client that retries a request that may not have arrived cannot apply it twice. The first call with a key runs; a repeat within 24 hours is answered with the same status, body and `ETag` and is marked `Idempotent-Replayed: true`, without running again or writing a second audit row. A key belongs to one tenant, one route and the caller that first used it: the same key with another request, or from another caller, is refused with `422` (`about:blank#idempotency-key-reused`) and one still running with `409`. A repeat is answered from the record before its `If-Match` is read again. A refusal or failure is not kept, so a retry runs. A tenant holds at most 10,000 keys that have not expired, past which a new key is refused with `429`, and a response over 64 KiB is refused with `422` and undone. The stored response is a copy of the one sent, so it can hold subject data such as an email; it is kept 24 hours and then deleted by `odudu reap`, and erasing a subject does not purge it. A call is undone as a whole when the database work fails, but a side effect outside the database, such as the test mail, is not. The routes that answer with a secret shown once (creating a client, rotating its secret, minting a registration token, issuing a password, importing a tenant) refuse a key with `400` (`about:blank#idempotency-unsupported`) rather than keep the secret, and so does creating a tenant (`about:blank#idempotency-not-atomic`), which writes outside the transaction a record would share, and so do testing a tenant's mail relay and verifying a domain (`about:blank#idempotency-external-io`), which wait on another server while they run; repeat them without one. `PUT`, `PATCH` and `DELETE` ignore the header, being idempotent already, and the OpenAPI document names it, and the `400`, `409`, `422`, `429` and `503` it can bring, on each `POST` that takes one. A call undone by the ceiling or the size limit answers without the `ETag` or `Location` of the change that never happened. The console does not send it, so only direct callers use it. Calls with a key run a few at a time (fewer than half the database pool) and wait their turn for at most ten seconds, behind at most a hundred others; past either the call is refused with `503` (`about:blank#idempotency-busy`) and `Retry-After`, and nothing is applied. A database pool of one connection cannot run them and refuses them with `503` (`about:blank#idempotency-unavailable`).
- `odudu reap` reports another table, `idempotency_keys`, after `client_metadata_cache`: a key is deleted once its 24 hours have passed.
- Each tenant serves an MCP endpoint at `/tenants/<name>/mcp` on your base address, or at `/mcp` on a tenant's own domain (and only there: the path address of a tenant that has a domain does not serve it). An MCP client reaches 64 tools that read what the admin API reads (clients, people, roles, sessions, keys, domains, the audit trail and the rest, and for the system tenant alone the list of tenants, described below), as the person who signed in: a call is judged by the capabilities that person holds and by the token's scope, so `mcp:read` reads what they could read in the console and nothing more, and a tool they could not use is left out of the list. A confidential client with the `client_credentials` grant that you give the MCP address as an audience and `mcp:read` as a `client_credentials_scopes` entry reaches it too, as its service account, and sees only what the account's roles allow. The tools that change anything are described in the next entries. A client reaches it only with an access token whose audience is the MCP address, which it gets by naming that address as the `resource` of its sign-in request and of its token request, and which the tenant has to have allowed it: a client that registered itself under the `mcp` registration policy is given the MCP address as its only audience, a client that came from a metadata document is given it while that policy is on, and a client you created yourself needs the MCP address added to its `audiences` and `mcp:read` assigned. The `mcp:read` scope is then offered on the consent screen and the person approves it. The built-in `odudu-mcp` client is for local tools and the admin API: its tokens are refused here, and an ordinary client's token, whose audience is the tenant's address alone, is `401`. Ending the `mcp` policy ends the audience at each client's next sign-in or refresh. The endpoint refuses a token that is for another address, for another tenant, for the admin API (also when it names the MCP address beside it), that has expired or whose grant, session, client or person has since ended: `401` with a `WWW-Authenticate` header that names the protected resource metadata, and `403 insufficient_scope` for a valid token with no MCP scope. A tenant that does not exist or is disabled answers an empty `404`, as its metadata does. It answers `POST` only (`GET` and `DELETE` are `405`), serves the 2026-07-28 revision and the 2025-11-25 handshake without keeping a session, takes a body of at most 256 KiB, and refuses a `Host` that is not the tenant's address and an `Origin` that is not its own. Each person and client may make 60 requests a minute and four at once, a person 120 a minute across all their clients, and a tenant 600 a minute, counted over a sliding minute; one address (behind a proxy, the proxy) may make 600 a minute to the endpoints of all tenants before any token is looked at. Past a limit the answer is `429` with `Retry-After`. The counts are per server process, so several instances multiply them. A tool that has not answered in 20 seconds is given up on and recorded as failed. With no `ODUDU_PUBLIC_BASE_URL` set, only a loopback `Host` (and `Origin`) is accepted, so a name that merely points at the server cannot drive it from a browser. Every tool call writes one `agent.tool_call` audit row naming the tool and the admin route it reached, and never what it was called with.
- An MCP client holding `mcp:write` is offered tools to change what exists, `update_client_metadata` and `update_scope_metadata` first, which change the descriptive text of one client (its name, its description and their texts in other languages) or one scope (its description and its texts in other languages), and nothing else: a redirect address, a grant, a secret, whether a client is on, a role and a scope's consent text are not in the tools, and the admin API refuses them to an agent even when a tool is bypassed. A call names the `etag` that `get_client` or `get_scope` returned as `if_match`, so a change made in the meantime answers `412` and an agent reads again instead of overwriting; the person's own capability (`manage-clients` for a client, `manage-tenant` for a scope) still decides, the name of the built-in administration and MCP clients is refused to an agent, and each change is an audit row naming the agent's client and the person, with what the text was before and after, so it can be put back. A client has to be given `mcp:write` by you, and the person is then asked about it every time a sign-in would grant it, whatever the client's consent setting or an earlier approval (if the client holds `mcp:write` as an optional scope the box is not ticked for them; if as a default scope the screen names it and has no box; and a request that may not show a screen is refused with `consent_required`): it lasts ten minutes at most and has no refresh token, and a client that registered itself under the `mcp` policy, or came from a metadata document, can never have it. A text an agent reads (a name, a description, an audit detail) may tell it to change a description, and an agent that holds `mcp:write` for a person who may can then do so: that is the reversible risk of granting it. A write that runs past its 20-second deadline is answered `mcp:outcome_unknown`, not as a failure, because the change may still be made: it tells the agent to read the client or scope again before sending it twice, and the audit row for the call says `failed` with the reason `timeout_outcome_unknown`. An empty description can be sent, as the admin API accepts one.
- An MCP client holding `mcp:write` is also offered five tools for the structure of a tenant, for a person who holds `manage-tenant`: `create_role`, `create_group` and `create_scope` make a role, a group or a scope, and `update_role_description` and `update_group_description` change a description. What an agent makes grants nothing: a new role is held by nobody, is a default for no one and has nothing nested in it; a new group has no roles, no members and no parent; a new scope is assigned to no client, maps no role and has no consent text, and a scope's `display_order` can now be set, by `create_scope` and `update_scope_metadata`. A parent, a default for new subjects, a scope's consent text, the tokens it appears in and who is assigned it are not in the tools, and the admin API refuses them to an agent whatever a tool sends. A create needs an `idempotency_key` the agent chose and sends again on a retry, so one role is made however often the call is repeated, and a scope name has to be one token a client can ask for (no space, quote or backslash) and a group name holds no slash. Each token may make 20 changing calls and 10 creates, counted on the sign-in's grant, so calls made at once cannot pass the limit. Only a call that came through the MCP endpoint may create: `odudu mcp` does not offer the three create tools, and the admin API refuses a create from any agent token the endpoint did not sign (`403`, recorded as a refusal), because it is the endpoint that counts. Each of these now leaves its own audit row with what it set: the admin API records the fields a role, group or scope was created with (`role.create`, `group.create`, `scope.create`) and what an amendment of a role or group changed (`role.amend`, `group.amend`), which it did not before, for every caller.
- An MCP client holding `mcp:write` is also offered three tools for the words people read on the sign-in pages, for a person who holds `manage-tenant`. `update_tenant_text_settings` changes the tenant's display name, the languages its pages are offered in and the default language, and nothing else: none of the other settings can be set through it, and the admin API refuses a body that names one, or one beside these, as a whole. `set_message_override` sets the tenant's own wording for one message in one language, and `clear_message_override` puts the default wording back. **This wording is shown to people on the sign-in pages and in mail, where they type a password, as soon as it is saved**, so an agent that has read hostile text could mislead a person there: it is the text most worth reading in the audit trail. A change is reversed by sending the earlier text back, which the audit row now holds. The settings call names the `etag` that `get_settings` returned (which now carries it) as `if_match`; a message override is created without one (and refused with `412` where one exists) and replaced or cleared with the `etag` that `list_message_overrides` gave. A tenant still holds at most 500 overrides, and the display name is at most 256 characters once surrounding spaces are trimmed. A `set_message_override` without an etag creates a row, so it counts as one of the ten creates a sign-in allows; a replacement or a clear counts only among the twenty changes. Setting or clearing an override changes how many rows a tenant holds, so, as for a create, only a call that came through the MCP endpoint may do it: `odudu mcp` does not offer the override tools, a service account cannot use them, and the admin API refuses them (`403`, recorded as a refusal) to any agent token the endpoint did not sign; the settings tool is open to all three, because it only amends what exists.
- An MCP client holding `mcp:write` is also offered `update_theme_draft` and `update_client_theme_draft`, for a person who holds `manage-tenant` (the tenant's theme) or `manage-clients` (a client's), which save a draft of its colours and font, its stylesheet and its page templates. **A draft is not what people see:** nothing shows it until a person publishes it in the console, and no tool publishes, restores, discards or resets a theme, changes a built-in client's theme, or uploads an image. A call names the entity tag that `get_theme` or `get_client_theme` returned as `if_match` (none, when that read says there is no draft, to make the first one); the tool reads the draft itself and sends every part the agent did not name exactly as it is stored, so reading it for the agent never rewrites a stylesheet; each part it does name replaces that part whole, a draft passing 512 KiB is refused and nothing is saved, and a stylesheet or template the console would refuse comes back as the admin API's list of problems. A first draft counts as one of a sign-in's ten creates. A draft that is replaced is not kept: the audit event (`theme.draft_saved`, for a person's save too) now names the parts that changed with the length and a SHA-256 digest of each before and after, never the text, so both tools are hinted as destructive. The tool reads draft and published theme together, which must come to under 1 MiB. A first draft is answered with a warning if the published theme changed while it was saved, and a theme whose admin answer fits under 1 MiB but is too large for `get_theme` to return (over 256,000 bytes) still gives the draft's etag beside the refusal, so the draft can be updated. A theme whose admin answer is itself over 1 MiB is refused before any etag is available, and the tools cannot read or update it: it is edited in the console. Only the MCP endpoint offers them: `odudu mcp` does not, a service account cannot use them, and the admin API refuses them (`403`, recorded as a refusal) to an agent token the endpoint did not sign. The draft routes also refuse an agent for a built-in client (the admin console and the MCP client) whatever the body names.
- `odudu mcp` serves the same tools over standard input and output, for an AI tool that runs on your machine (Claude Code, Cursor, Claude Desktop). It calls your instance's admin API over HTTP, as you or as a service account, and needs no database or server settings: `odudu mcp --base-url https://id.example.com --tenant acme`. It offers the read tools; `--allow-writes` asks for `mcp:write` as well and adds the write tools that amend a description, a name or the tenant's display name and languages (the three that create something, the two that set or clear a message override and the two that save a theme draft are offered by the endpoint alone, because only the endpoint counts them). The address must be `https` unless it is a loopback address. A tenant with a domain of its own signs in at that address, which `--tenant-address` names; the admin API stays at `--base-url`. Each call it makes is recorded: the admin API writes one `agent.tool_call` audit row, before the call runs, for every agent call whose token the MCP endpoint did not sign, which covers a call made with a token issued straight to the agent and one made with an exchanged token, naming the route as the tool (`admin.get.clients`), and answers `503` without running it if the row cannot be written.
- Signing in for `odudu mcp` opens your browser, and no password is typed into the command. The sign-in is kept in your operating system's credential store (the macOS keychain, or `secret-tool` on Linux), or, where there is none, in a file under `~/.config/odudu/mcp` that only you can read; a file that group or others can read is refused. A run with `--allow-writes` asks you again each time, keeps nothing and never uses a stored sign-in. `odudu mcp --logout` forgets the one kept for an instance and tenant.
- A service account can run `odudu mcp` with no browser: `odudu mcp --keygen` prints an `ODUDU_MCP_KEY` line for the environment and the public key set to register for the client (`private_key_jwt`, the `client_credentials` grant, the audience `urn:odudu:params:admin-api` and the `mcp:read` scope). The client is named with `--client-id` or `ODUDU_MCP_CLIENT_ID`, and the key can come from `--key-file`.
- `odudu seed client --audience <resource>`, repeatable, gives a client the audiences it may ask for, such as a tenant's MCP address, so a client that is handed a fixed client id can be made without the console or the admin API; `odudu seed assign-scope` then gives it `mcp:read` or `mcp:write`. A list is held to the same limit as the admin API's.
- Every MCP connection now says which tenant it serves, so a client with several Odudu servers connected can tell them apart: the server's name is `odudu:<tenant>` with the title `Odudu (<tenant>)`, its instructions say it acts in that tenant only, and every tool description starts with `[<tenant>]`. The endpoint takes the tenant from the token and `odudu mcp` from `--tenant`. The `whoami` admin route, and the MCP tool of that name, also return `issuerTenantName`, the name of the caller's tenant, beside `issuerTenantId`.
- An MCP client signed in to the `system` tenant as a person who holds `manage-tenants` is offered two more tools, `list_tenants` and `count_tenants`, which list the instance's tenants (name, display name, whether enabled), one page at a time and filtered by name or display name prefix or by whether they are enabled, and count them. A client signed in to any other tenant is not offered them, and calling them anyway is refused with `401`; an owner without `manage-tenants` is refused with `403` and a `capability.refused` audit row. Neither tool takes a tenant argument or opens any tenant's content, and a tenant's display name, which its own administrators write, comes back under `data` like every other text. An agent of any other tenant is offered neither, and the rest of the tools are the same everywhere.
- An MCP client reaches six more small reads, each under the capability its admin route asks for: `get_tenant` (the tenant it acts in: name, display name, whether it is enabled; `manage-tenant`, and it takes no argument, so it can never open another tenant), `get_username_policy` (whether usernames can be changed; `view-users`), `get_passkey_impact` (how many subjects' passkeys would be hidden by moving the canonical address to the one named; `view-domains`), `get_scope_impact` (what deleting a scope would take with it) and `list_builtin_scopes` (which built-in scopes the tenant has; both `manage-tenant`), and `get_client_installation` (the issuer, discovery address and registered settings a relying party is configured with, never the secret; `manage-clients`). Text in their answers comes back under `data` like every other.
- An MCP client reaches eleven reads of how a tenant and its clients look. `get_theme` and `get_client_theme` return the draft and the published theme whole, with the stylesheet and every page template kept up to 131,072 characters instead of 1,000, still under `data` and stripped of control and bidirectional-override characters, and the draft's `ETag` beside them; a theme too large for one result is refused as `mcp:result_too_large`. `list_theme_versions` and `list_client_theme_versions` list the versions without their bodies, `get_theme_preview_info` and `get_client_theme_preview_info` say what a preview of a page kind would show, `get_stylesheet_hooks` lists what a stylesheet may name, `get_mail_branding` and `get_client_mail_branding` give the mail's colours and logo, `list_message_overrides` pages a locale's own wording and `get_message_catalogue` lists the messages it replaces. The tenant's are under `manage-tenant` and a client's under `manage-clients`, so an owner without `manage-clients` is not offered the client ones. The uploaded image bytes and the rendered previews are still not offered.

### Changed

- A tenant now defines at most 1,000 roles (a client's own included) and 10,000 groups, as it already defined at most 1,000 scopes. A create past the limit is refused with `409` and says `a tenant defines at most 1000 roles` (or `10000 groups`), for a person, a script and an AI agent alike; a tenant that already holds more keeps every one and is refused only a new one. The numbers are `ROLE_LIMIT` and `GROUP_LIMIT` in `@odudu/contracts`, and the admin API reference says them on `POST /roles` and `POST /groups`. A tenant import is held to the same limits and refused with the same words when its document defines more.
- Creating a role or a group no longer locks the tenant's row, which every sign-in locks too: creators of one kind in one tenant take an advisory lock, so a tenant loading thousands of groups does not make its sign-ins queue behind the count.
- An MCP write sent by name with a token that holds no write scope is refused before the allowance is read, so it takes no lock on the grant.
- `max_clients` now limits the clients an administrator or a registration token makes, the built-in ones included, and no longer counts a client that arrived on its own, so nobody who is not signed in can fill it and keep an administrator from making a client. Clients that registered themselves have a limit of 1,000 a tenant (the oldest one nobody approved, signed in through or granted anything is removed to make room, and the registration is refused when there is none), and clients from a metadata document one of 1,000 as before. A tenant import counts only the clients in the document that did not register themselves, and is refused when the document holds more than 1,000 that did. A restored `anonymous` client has no approval, so `odudu reap` removes it a week after the import unless it is used.
- The audit event for a settings change (`tenant.amend_settings`) now carries a detail: the registration policy, `cimd_enabled`, the display name and the supported and default languages, before and after, so a change to who may register clients or to wording people read can be read from the trail; no other setting is written into it. The audit events for setting and clearing a message override (`message_override.set`, `message_override.delete`) now carry the text before and after instead of its length, so a change to wording people read can be read, and undone, from the trail. A tenant's display name is now at most 256 characters, in the settings, in `PATCH /admin/tenants/{tenant}`, when a tenant is created or imported and in a tenant document; a longer one is refused with `400`. A tenant whose stored name is already longer keeps it and still exports; importing a document that holds one is refused. A message override's key with a NUL in it is now a `400`, not a `500`, and the wording an agent writes may hold no control or invisible character other than a line break and a tab (and no tab or line break in a name or the display name).
- The audit event for amending a scope (`scope.amend`) now carries a detail: what the description, the two token flags, the default assignment, the consent text, the texts in other languages and the display order were before and after, as a client's amendment already did, so a change can be read back and undone. It carried none before.
- A client that registered itself, or that came from a metadata document, is shown the consent screen on every sign-in until the person approves that exact client, even if its consent setting was turned off or its request names no scope the screen could record. Approving one client never approves another, whatever name it gives itself. Clients created by an administrator or with a registration token are unchanged.
- A tenant on a domain signs its administrators in to the console through the domain; the console itself stays on your base address. The admin API accepts a tenant's tokens while their issuer is its current address or one it left in the last hour, so a machine client has to fetch tokens from the canonical token endpoint, and tokens from the address left stop working when the hour ends. A console session opened before a switch carries on, because the console refreshes its token at the new address. Switching back returns sign-in to the path address, and tokens issued at the domain keep working for the hour. The system tenant is unaffected.
- A tenant has one address at a time. A passkey is tied to the address it was registered at: after a switch it is not offered at the other address, and a switch back brings it back. Password sign-in is not affected, and nothing is deleted.
- A client's redirect addresses, web origins and sign-out addresses do not change when its tenant switches address, and the apps that read a tenant's issuer have an hour to move to the new one. An API that checks a token's issuer locally must accept both for that hour.
- The built-in roles are ten, not eight. A tenant that exists before the upgrade gets the two new roles when you run `odudu console provision` once after it; until then its administrators are refused the domain routes and the console hides Domains.
- **Upgrade note.** Token exchange now refuses a public client unless its `token_exchange_allowed_for_public` is on, with `unauthorized_client` (a public client holds no secret, so reaching the grant proved nothing about who asked), and refuses an actor token issued to another client unless the requesting client's `token_exchange_actor_from_other_client` is on, as an `invalid_request` recorded as an `invalid_grant`. A client that relied on either stops working at the upgrade, and nothing backfills it. The server logs a warning at start naming how many public clients hold the grant with the setting off and the first twenty. To list them all, run `select t.name, c.client_id from client_oidc_config o join clients c on c.id = o.client_id join tenants t on t.id = c.tenant_id where c.type = 'public' and not o.token_exchange_allowed_for_public and o.grant_types @> array['urn:ietf:params:oauth:grant-type:token-exchange']` as the database owner. Set the field on each, with `PATCH` in the admin API, or register the client that way with `odudu seed client`. An actor token the requesting client was itself issued, and an exchange by a confidential client with no actor, are unchanged.
- A token exchange or a refresh that would turn a token holding `mcp:read` or `mcp:write` into one holding neither is refused with `invalid_scope`: such a token reaches the admin API as an agent, and one without the scope would have reached it as the person. An exchange of such a token that keeps a scope also keeps an `act` claim, the one it carried or the requesting client's. An exchange can no longer ask for more scope than the token it was handed holds, where it used to be bounded by the grant behind the token.
- A client has a service account only while it holds the `client_credentials` grant, not for every confidential client. Creating a client, registering one, importing a tenant or `odudu seed client` makes one only where the grant is on; adding the grant to a client later creates one, with no roles, or reuses the account an upgrade kept, with the roles it still holds; removing it deletes the account with every role, token grant and session it held, and revokes the tokens that were exchanged with the account as the actor, so a leaked secret can no longer sign in as the client. Odudu refuses a token already issued from then on (admin API, introspection), but a resource server that checks only the token's signature accepts it until it expires, at most the access-token lifetime. Past audit events by the account keep its id, and their `actor_name` resolves to nothing. Adding the grant back starts a new account with no roles. Removing the grant is refused when the account holds the tenant's last administrator role. A tenant export leaves `service_account_roles` empty for a client without the grant and names the omission, and an import ignores roles a backup lists for one.
- **Upgrade note.** The migration that ships with this change deletes the service account of a confidential client that does not hold the `client_credentials` grant, unless a token grant, role, group membership, consent, session or audit actor still names it. One it keeps is listed in the server's start-up log (`N confidential clients hold a service account without the client_credentials grant`, with the first twenty), and it is removed the next time that client's `grant_types` are set, for example by turning the grant on and off again in the console. A kept account keeps its roles, and turning the grant on makes them active again. Clients that hold the grant are unchanged. Drizzle runs every pending migration of an upgrade in one transaction, so the locks of all of them are held until it ends: migration 0124 adds two columns to `token_grants` and holds its lock to the end too (no row is rewritten), row security is lifted on `clients`, `client_oidc_config` and two more tables by migrations 0113, 0114, 0119, 0120 and 0122 only when the migrating role is neither a superuser nor `BYPASSRLS` (a supported install is one of them, so it takes no lock for that), and, whoever the owner is, the new columns and constraints on `clients`, `tenants` and `client_oidc_config` (migrations 0114, 0116, 0117, 0120 and 0122, two of which scan every `clients` row), the index builds, the aggregate over every consent that 0119 reads and the updates of 0120 and 0122 hold theirs to the end. Stop the server for the upgrade, as you would for a data migration on a very large installation. The migration reads audit events of the account's own tenant only, one indexed read per account, so its length follows the number of such accounts and does not grow with the audit table; an event filed under another tenant that names a deleted account keeps the actor's id and tenant and loses only the account's name.
- The audit event for a client change (`client.create`, `client.amend`) now carries `service_subject_id` among the values it records, so creating or removing a service account can be read from the trail.
- A client that asks for more than a client registered or identified by itself may hold, such as `mcp:read mcp:write` taken from the metadata's `scopes_supported`, is no longer refused. On a tenant whose registration policy is `mcp`, registration keeps `mcp:read` and the sign-in scopes and the response's `scope` lists them; at sign-in the request is asked about without `mcp:write`, and the token response's `scope` says what was granted. A request for `mcp:write` alone is still refused with `invalid_scope`.
- An AI agent holding `mcp:write` may now make at most 20 changing calls, and at most 10 creates among them, for each sign-in; a call over that is refused with `mcp:write_budget` (`429`) and recorded as a refused `agent.tool_call` event with the reason `write_budget`, and the person signs in again to give it a new allowance. The limit applies to calls made through the MCP endpoint; `odudu mcp` over stdio keeps a count of its own for each run, renewed by each new browser sign-in (a service account's key keeps the one it started with), and neither is a limit on a principal that calls the admin API with its own token, which the allowlist's fields still hold. Reads cost nothing, a call the admin API refuses with a `4xx` gives its place back, and a call that ran out of time or could not be read back keeps it, because the change may have been made. The count is kept on the sign-in's grant, so calls made at the same moment cannot between them pass it, and a new sign-in has its own, and a token exchanged from a sign-in's token shares that sign-in's count, so an exchange does not renew it. A reservation that takes more than a few seconds is answered `mcp:write_budget_unavailable` and the call is not made.
- **Upgrade note.** A migration adds three small columns to every token grant (`agent_writes` and `agent_creates`, both starting at 0, and `budget_grant_id`, empty); it rewrites no row and the server runs it with the others. The migration gives a grant an earlier exchange made its root by following the chain; one whose parent was deleted before the upgrade cannot be told from a sign-in's own grant and keeps a budget of its own, and an MCP write token lives ten minutes, so none that matters outlives the upgrade.
- The audit reasons list a new value, `write_budget`: an agent had made as many changes as one sign-in allows, so the call was not made.
- The admin API's allowlist for an agent's writes now names the method (PATCH, POST, PUT or DELETE), the route and whether the body is named fields or a whole record, and holds one entry for each of the twelve write tools. Which class each admin route is in, and so whether an agent may reach it, is written down in [MCP route classes](docs/protocols/mcp-route-classes.md); a route can no longer move to an MCP tool without its row changing.
- The three MCP guides say, in one table, and the consent and audit page, in a sentence, what an agent can and cannot do and why, class by class, with the count of the admin API's 152 routes in each: 59 reads and 2 instance reads, 13 content writes (12 with a tool), 32 access-changing, 7 credential and 27 destructive operations, 8 sensitive reads and 4 pages drawn for a browser. Access-changing, credential and destructive operations are not available to an agent yet, and a person makes them in the console.

### Fixed

- Moving a group under another rewrote the path of every group whose path began with the moved group's, read as a pattern, so a group named `a%`, `a_` or ending in a backslash could rewrite the paths of unrelated groups when it was moved. The moved group's own subtree is now found by following parents, and nothing else changes.
- `odudu seed role` and `odudu seed group` now refuse to pass a tenant's limit of 1,000 roles and 10,000 groups, with the same words as the admin API.
- A back-channel logout that is retried carries the time of the retry, with the lifetime it was minted with, so a receiver no longer refuses a retry for the age of the first attempt.
- A client's name or description, a scope's description or consent text, or a text in another language, that contained a NUL character was answered with a server error (`500`); it is now refused with `400` naming the field. Creating a scope, a group, a role or a subject with a NUL in its name, description, username or email was the same server error and is now the same `400`.
- Two upgrade migrations, `0119` (when a person first approved a client) and `0120` (which clients are public), found no row to update when the migrating role is neither SUPERUSER nor BYPASSRLS; they now lift forced row security for the statement and restore it, as the later ones do.
- Creating a group with a `/` in its name, and setting or clearing a message override whose key held a NUL character, were server errors (`500`) and are now `400`. A tenant's display name had no length limit before the limit of 256 characters.

### Security

- The consent screen of a client that registered itself says that nobody at the tenant set it up and names the origin this request sends the person back to, then the other origins it registered (five at most, with the count of the rest), as it already did for a client from a metadata document, so a name another application chose cannot stand alone on the screen. `offline_access` is named on it as ongoing access.
- The reads the MCP tools leave out for being personal data or credential metadata (a person's profile and credentials, registration tokens, the mail relay login, one client's claims for a person) are now refused to an agent's token at the admin API too, so `odudu mcp` or a service account holding an agent token cannot read them directly. The console's own sign-in is unaffected.
- A refresh of a client that registered itself or came from a metadata document reads the tenant's registration policy once, so turning the policy off while the token rotates no longer spends the old token and refuses the new one, which made the client's retry revoke its whole chain.
- A request is served as a tenant only through a verified domain row. A host with no verified row selects no tenant and is routed as before, so registering a name cannot blank it; a verified host that is not live gets one bare refusal on every path.
- `X-Forwarded-Host` is read only when `ODUDU_TRUST_PROXY` is on, and then from its last entry, the one your proxy appended, never one a client could have written ahead of it.
- Hosts are refused by their folded spelling, so a Unicode dot or a fullwidth letter does not walk past the refusal of your own host, `localhost` or an IP address.
- Verifying a domain is limited: a tenant looks a host up at most once every 30 seconds and makes ten lookups a minute. The limits are per process.
- A domain whose owner lost it stops serving the tenant's sign-in: the recheck fails it, and the tenant falls back to its path address.
- Mail links are written from the tenant's address, never from the request's `Host`.
- A public client that held the token-exchange grant could use it with any valid actor token, another client's included, because the token endpoint asks a public client for no secret. It is refused unless an administrator allows it, and an actor token must belong to the client presenting it unless that client is allowed otherwise.
- A token that carries `mcp:write` lives ten minutes at most and is never refreshed. The person is asked about it at every sign-in that would grant it, whatever the client's consent setting or an earlier approval, and a request that may not show a screen is refused. A client that registered itself, or came from a metadata document, can never hold it.
- An AI agent reaches the admin API only with a token marked as an agent's, which a token exchange or a refresh cannot shed. With `mcp:read` it can read, except the exports and downloads and the personal-data reads listed below. With `mcp:write` it can also change the descriptive text of a client, scope, role or group, the tenant's display name and languages and the wording of its sign-in pages, save a draft of a theme that only a person can publish, and create a role, group or scope that grants nothing, and only a person who holds the capability for that client or scope (`manage-clients`, `manage-tenant`) can have it done on their behalf: the token's scope allows the call and the person's capabilities still decide it. Every call it makes, allowed or refused, is an audit row naming the agent and the person, written before the call runs.
- An agent working through the MCP endpoint can no longer be used to change a great deal at once: the 20 changes and 10 creates a sign-in allows are counted in the database in one statement, so a burst of calls made together stops at the limit. A write sent to the admin API by an agent still needs the route in the allowlist, only the fields it names, and no body at all for a DELETE.
- The two reads that span tenants, the tenant list and its count, are offered only to an agent of the `system` tenant whose owner holds `manage-tenants`, and refused to every other agent token (`401`, or `403` without the capability). An agent holding a token of one tenant is refused at the routes of every other tenant, whatever capabilities its owner holds there.
- An agent cannot amend a built-in scope (`openid`, `offline_access`, `mcp:read`, `mcp:write` and the other standard ones), its description and display order included, as it cannot rename a built-in client; it still amends the scopes a person made.
- The write budget does not walk a chain of exchanges to find its counters: a grant made by an exchange names the grant it spends, and a grant whose root is gone, or that names none, is refused, so an error path or a long chain never renews an allowance.
- Nothing that changes who can sign in, what a token carries, a secret or the deletion of anything that grants or authenticates is reachable by an agent (a message override it set can be cleared, and nothing else is deleted): the admin API admits an agent's write by method, route and field from a short list, refuses every other field of a listed route and every unlisted route with `403`, and records the refusal. A write that adds or removes a row (a create, a message override set or cleared, a first theme draft) is admitted only to a token the MCP endpoint signed and counted, never to `odudu mcp`, a service account or a token a client holds itself.

- Sign-in pages, error pages and mail in one shared look, with their text in message catalogues.
- A language chosen for each page from `ui_locales` and the browser's `Accept-Language`.
- Sign-in with the authorization code flow and PKCE, refresh tokens, client credentials, token exchange and single sign-on.
- Many tenants on one server, each with its own people, clients, keys and settings.
- Passwords, passkeys, authenticator codes and recovery codes.
- An admin API and an admin console, and an audit trail of every change and sign-in.

### Changed

- Password rules follow NIST SP 800-63B-4.
- One setting now decides the lifetime and shape of every cookie the server sets.
- Built-in scopes can be deleted, by typing their name, and restored.
- The issuer in tokens, discovery and logout is the configured `ODUDU_PUBLIC_BASE_URL`, never a request's `Host` header.
- A password reset ends every session and token the person had.

### Security

- Base images are pinned by digest, and a test keeps them so.
- Registering with an address that is already taken no longer says that it is taken, when email verification is on.
- Cookies are `Secure` and `__Host-` prefixed under `ODUDU_TLS`, from one setting; before, the session cookie ignored it.
- Characters that change the direction of text are refused in names and usernames.
