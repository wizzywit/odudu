# Changelog

All notable changes to Odudu are written here, newest first. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/) as [RELEASING.md](RELEASING.md) describes.

## [Unreleased]

### Added

- Each tenant serves a "me" API where a signed-in person reads their own account with their own access token: `GET /tenants/<name>/me/profile`, `/me/credentials`, `/me/sessions` and `/me/consents` (at `/me/...` on a tenant's own domain). A token for it names the tenant's `/me` address as its audience and holds `me:read`. `me:read` and `me:write` are two new scopes every tenant defines, and a tenant that exists before the upgrade gets them when the server migrates; no client has either until you assign it, a request for either is refused with `invalid_scope` at any audience but the tenant's `/me` address, and a request for `me:write` carries `me:read` with it. No path or parameter names a person: the token's own subject is the only one read. A list takes `limit` and `cursor` and answers `items` and `next_cursor`; the credential list adds `recovery_codes_left`, and carries no secret, seed, key or hash. A token that holds `me:write` without `me:read` is refused with `insufficient_scope`. A read refuses a query member it does not know with `400`, `profile` included.
- A person can change their own account through the "me" API with a token that holds `me:write`: `PATCH /tenants/<name>/me/profile` amends their profile claims, `DELETE /me/sessions/<id>` ends one of their sessions and `DELETE /me/sessions` the others (a hundred at most in one request, which says whether any remain), `DELETE /me/consents/<client_id>` withdraws a consent and revokes the grants under it, and `PATCH` and `DELETE /me/credentials/<id>` rename and remove an authenticator. Each change leaves an audit row naming the person, with the fields changed and never their values. Every change needs a session that still stands, so a token whose session has ended, or that names none, is refused `401` `invalid_token` while reads keep answering. The audit trail gains `subject.credential_rename` and `email.changed`, and a session a person ends is recorded as `session.ended` with `via` set to `self`.
- A new email address is asked for through `PATCH /me/profile` and does not take effect until the person follows the link mailed to the new address. The answer is `202` whether or not another account holds the address, and then nothing is mailed. A server with no way to send mail answers `503` `mail_unavailable`.
- Changes that could lock a person out or hand their account over (a new address, a new username, ending all other sessions, withdrawing a consent, removing an authenticator) need a recent sign-in. An older one is answered `401` with the RFC 9470 challenge (`insufficient_user_authentication`, `max_age` and, for a person who holds a second factor, `acr_values`), and the application sends the person through `/authorize` again. The window is the tenant setting `session_freshness_seconds`: 300 seconds by default, 30 to 3600, in the console's Settings under Sessions.
- Removing an authenticator through the "me" API is refused with `409` when it is the last way to sign in (`last_sign_in_method`) or the last second factor of a tenant that requires one (`last_second_factor`).
- An application can send a signed-in person to Odudu to change one credential. The authorization request takes `action`, one of `update-password`, `configure-totp`, `configure-passkey` or `generate-recovery-codes`; the person sees the page Odudu already shows for that change, with a "Cancel and go back" control, and the redirect carries `action_status` (`success`, `cancelled` or `error`) beside `code`, `state` and `iss`. A sign-in older than the tenant's `session_freshness_seconds` is asked for again first. `action_status` is a hint, since a person who closes the tab sends nothing: the application reads the outcome from the credential list of the "me" API, which also counts the recovery codes left. A requested password change asks for the current password first, a requested authenticator replaces one the person already has, and a person who holds recovery codes is asked to confirm before they are replaced. The guide in the documentation is called Send a person to change a credential.
- What a client may start is its `allowed_actions` setting, empty for every client: a field of the client in the admin API (create, amend and read), a checklist under Application actions on the Advanced tab of the client in the console, a member of a tenant export and import, and `odudu seed client --allow-action <action>`, which assigns `me:read` to the client itself. A request that names an action the client is not allowed, an unknown name, the parameter twice or empty is refused with `invalid_request` at the client's redirect address. A client that may start an action has to hold `me:read`, which is how it reads the outcome: naming an action without it is refused with `allowed_actions_need_me_read`, and the scope cannot be unassigned from such a client or deleted while one holds it. Dynamic registration refuses `allowed_actions`, as it does `skip_logout_confirmation`.
- The audit trail records each action an application sends a person to: `action.requested` each time the page is shown, then `action.completed`, `action.cancelled` or `action.failed`, with the action in `detail` and the application as the actor client.
- A link an administrator mails can return the person to an application. `POST /admin/tenants/<name>/subjects/<id>/password-reset`, `verification` and `actions-email` take an optional `client_id`, and a `redirect_uri` when that client registers more than one; the last page of the link then offers a "Return to the application" link to that registered address with `action_status` (`success`, or `error` for a link that cannot be used), a hint that the "me" API confirms. The two older sends gain an optional body, and a request without one behaves as before; a body that names any other field is now refused with `400`, where a body was ignored before. A `client_id` that is not an enabled client of the tenant is refused with `400` `return-client-unknown`, an address the client does not register with `return-redirect-uri-unregistered`, and none named where the client registers several with `return-redirect-uri-required`. The page drops the link when the client was deleted, disabled or stopped registering the address after the mail was sent.
- A set of recovery codes can be replaced once an hour, on every page that makes one, because each set costs ten password hashes and a person with a valid password could otherwise ask for them without end. A person who asks sooner while they still have codes to spend is shown how many minutes to wait (`429`), and the audit trail records `recovery_codes.refused`. The first set, a set with no code left to spend and a set the sign-in is waiting for (a new authenticator, say) are never held back, so the bound can never keep a person from finishing a sign-in. The hour is counted from when the last set was made, which the server records on the person from this version on: sets made before the upgrade have no time, so each can be replaced once straight away.
- The credential list of the "me" API says when a person's recovery codes are running low: `recovery_codes_low` is `true` when they hold a set with fewer unspent codes than the tenant's `recovery_code_warn_below` setting, and `false` when they hold no set. The setting is 3 by default, 0 to 10, and 0 turns the warning off; it is in the console's Settings under Registration and recovery. Odudu serves no page of its own that a person lands on after signing in, so an application shows the warning from this field and sends the person to `generate-recovery-codes`; the sign-in itself never gains a step for it.
- A tenant chooses what its new authenticators are made with, under Authenticators in the console's Settings or through the settings API: `totp_algorithm` (`SHA1`, `SHA256` or `SHA512`), `totp_digits` (6 or 8), `totp_period` (30 or 60 seconds), `webauthn_user_verification` and `webauthn_resident_key` (`required`, `preferred` or `discouraged`) and `recovery_code_count` (8 to 16). Every setting starts at what Odudu has always done, so a tenant that changes nothing sees nothing change. A tenant export and import carry them. `recovery_code_warn_below` may not exceed `recovery_code_count`.
- An authenticator app, a passkey and a set of recovery codes keep what they were made with. A change applies to the next one made: an app already enrolled is checked by its own algorithm, digits and period and a passkey by its own user verification, so nobody is locked out by a change of policy. The enrolment page tells the person what their app must support when the parameters are not `SHA1`, 6 digits and 30 seconds, and the `otpauth://` address and QR code carry them.

### Changed

- An application that sends a person to `generate-recovery-codes` now asks before it makes a first set, as it already did before replacing one. Nothing is made while the question is on the screen, so reloading it changes nothing and cancelling it no longer follows a set that was made at once.
- A tenant's discovery document and its authorization server metadata list `me:read` and `me:write` in `scopes_supported`, with the tenant's other scopes. A tenant starts with twelve scopes where it started with ten, and the console's scope list and a tenant export show the two.

### Security

- A token that carries `act`, one issued to an agent acting for the person, may read the "me" API and is refused every write with `403` `agent_not_permitted`.
- An application cannot make an action look successful: the redirect's `action_status` is written by Odudu from the state of the request it kept, never from anything the browser or the client sends, and an action the client is not allowed is refused before any page is shown. Recovery codes are not replaced until the person confirms, the page that shows the new set has no way to cancel it, and a requested password change needs the current password, which counts against the tenant's lockout like a wrong password at sign-in.
- A person is told by mail when they change how they sign in. Setting up an authenticator app or a passkey, saving a new set of recovery codes, removing an authenticator through the "me" API and asking for a new email address each send a notice, in the tenant's theme and in the person's language (English and Arabic ship), saying what changed and when and what to do if it was not them. It carries no link, code or secret. The notice goes only to a verified address: for an address nobody verified the change is still allowed, nothing is mailed, and the audit row says `notice` is `skipped_unverified` (`skipped_none` where the person has no address, `sent` otherwise), on `otp.enrolled`, `passkey.enrolled`, `recovery_codes.issued`, `subject.credential_delete` and the `subject.profile_amend` that asks for an address. A request for a new address tells the address being left, since the new one already gets the link; a request for an address already in use, for the address the account has, or that is throttled queues no notice, and the audit row says `skipped` with the reason. Changes an administrator makes keep their own mails.
- A passkey assertion that lacks user verification, which a passkey made where the tenant did not require it can give, proves possession of the key and nothing else, so it signs in as one factor: the person is still asked for an authenticator app code where they have one or the tenant requires one, and a sign-in by the passkey alone has `acr` `1` and an `amr` with no `user`. Passkeys made with verification required are unchanged, and are still refused an assertion without it, whatever the tenant has chosen since. Passkey sign-in always asks the browser for `preferred` verification.
- A passkey the browser reports as not stored on the device is refused at enrolment under any `webauthn_resident_key` value, because passkey sign-in names no username and only a stored passkey can answer it. The person is told to add one that can be stored.

## [0.1.0] - 2026-11-07

The first stable release. It gathers everything from the release candidates and
adds the MCP server: each tenant serves an MCP endpoint that an AI assistant can
read from and, within strict limits, write through. Odudu has had no
independent security review.

### Added

- Every tenant has two new scopes, `mcp:read` and `mcp:write`, for the clients that will use its MCP endpoint, and a tenant that exists before the upgrade gets them when the server migrates. Neither is given to any client until you assign it. A request for either is refused with `invalid_scope` unless the resource is the tenant's MCP address (its address followed by `/mcp`) or the admin API, at the sign-in request and at the token endpoint for every grant, so a client registered for several audiences must name the MCP address as its `resource`. The consent screen says in plain words what each lets an application do, in English and Arabic, and `odudu seed restore-scopes` creates them again if one is deleted.
- Every tenant has a built-in public client, `odudu-mcp`, for local MCP tools to sign in through: PKCE is required, it holds no secret, and its access tokens are for the admin API. It asks for `mcp:read`, with `mcp:write` optional, and shows each person a consent screen. A tenant that exists before the upgrade gets it when the server migrates, unless the tenant already has a client of that name, which is left alone. Its redirect addresses are `http://127.0.0.1` and `http://[::1]`, and a public client registered with a loopback address and no port is accepted at any port, as RFC 8252 asks of an app that listens on a free one; `localhost`, other hosts and confidential clients are still matched exactly. You can disable `odudu-mcp` but not delete it, and the client ID is reserved. A tenant export carries it, and an import reproduces it.
- Each tenant publishes OAuth 2.0 authorization server metadata (RFC 8414), so a client that knows only a resource can find where to sign in without being told. It is at `/.well-known/oauth-authorization-server/tenants/<name>` on your base address, or at `/.well-known/oauth-authorization-server` on a tenant's own domain, and states the tenant's issuer and the same endpoints as its discovery document. It lists `mcp:read` and `mcp:write` among the scopes, `none` and `private_key_jwt` among the ways a client authenticates, and the signing algorithms `private_key_jwt` accepts. A tenant that is disabled or does not exist answers an empty `404`.
- Each tenant publishes OAuth 2.0 protected resource metadata (RFC 9728) for its MCP endpoint, so an MCP client given only that address can find where to sign in. It is at `/.well-known/oauth-protected-resource/tenants/<name>/mcp` on your base address, or at `/.well-known/oauth-protected-resource/mcp` on a tenant's own domain. It states the MCP address as the `resource`, the tenant's issuer as its authorization server (the same issuer its authorization server metadata states), and `mcp:read` and `mcp:write` as the scopes. A tenant that is disabled or does not exist answers an empty `404`.
- An access token that carries `mcp:write` lives ten minutes at most, even where the tenant or client sets a longer lifetime (a shorter one still applies), and is issued with no refresh token, so a client holding `mcp:write` signs the person in again to keep writing. `offline_access` asked for beside `mcp:write` is ignored without an error. `mcp:read` follows the tenant's lifetimes as before.
- A tenant can have a public address of its own, such as `login.acme.com`, instead of `/tenants/<name>` under your server's address. Its sign-in pages, the issuer its tokens carry, its cookies and the links in its mail follow that address, and a tenant that does nothing behaves exactly as before. The guide is [Custom domains](apps/docs/content/en/operating/custom-domains.md).
- A tenant proves it owns a host by publishing a DNS TXT record under `_odudu-challenge.<host>`, in the console's new Domains area or through `/admin/tenants/{tenant}/domains`. A tenant registers up to twenty domains and has one as its address; registering claims nothing, and the first tenant to prove a host keeps it.
- Switching a tenant to its domain, and back, from the base address. Sign-in cookies belong to one host, so people sign in again at the new address; sessions at the address left are not ended and resume if the tenant switches back. For one hour, the longest an access token lives, the address the tenant left keeps serving the token, user info, introspection, revocation, key, logout and discovery endpoints, and points sign-in to the new address. The console says how many people a switch hides passkeys from before you confirm it.
- `GET /internal/domain-check?domain=<host>` for your reverse proxy's on-demand TLS question (Caddy's `on_demand_tls { ask }`): `200` for a host Odudu serves, `404` for every other, with no body. Keep it off the public network; it takes no secret.
- A recheck of every verified domain's ownership record, `odudu domains recheck`, which the server also runs every hour. A domain whose record is gone for three passes fails, and a tenant that has it as its address returns to its path address. A resolver outage counts as nothing, and a failed domain verifies again once its record is back.
- `odudu seed domain --tenant <name> --host <host>`, with `--canonical` and `--assume-verified`, which marks a host verified without the DNS proof and refuses to run in production.
- Settings `ODUDU_DOMAIN_RECHECK_ENABLED`, `ODUDU_DOMAIN_RECHECK_INTERVAL_SECONDS` and `ODUDU_DOMAIN_RECHECK_FAILURES` for the recheck, and `ODUDU_RETENTION_PENDING_DOMAIN_SECONDS` (seven days) for how long a domain nobody proved is kept. `odudu reap` reports `tenant_issuer_retirements` and `tenant_domains` as well.
- The capabilities `view-domains` and `manage-domains`, and a built-in role for each.
- `odudu reap` reports a new table, `client_metadata_cache`, after `tenant_issuer_retirements`: the Client ID Metadata Documents the server fetched for a tenant, which are deleted once their cache lifetime (one minute to a day) has ended. A tenant keeps at most 1,000 of them; past that, a new one replaces the one unused longest that never completed a sign-in, and is refused if every one has. Nothing fills it until a tenant turns on client metadata documents, so the count is `0` for now.
- A tenant can let an app identify itself with a web address instead of registering first. Turn on the `cimd_enabled` setting (off by default; `odudu seed tenant --name <tenant> --set cimd_enabled=true`, or the settings API) and a `client_id` that is an `https` address is resolved to the Client ID Metadata Document served there. The consent page shows the document's name, the host and port of the address and every redirect address; a redirect address the document does not list is refused. The fetch is limited to five KiB and three seconds, follows no redirect, refuses private and local addresses, and is cached for the document's `Cache-Control` lifetime. A tenant's authorization server metadata states `client_id_metadata_document_supported` while the setting is on. With it off, such a `client_id` is refused like any unknown client. Such a client has no audience and no MCP scope until a tenant policy gives them.
- `odudu reap` reports another table, `cimd_clients`, after `client_metadata_cache`: a client kept from a metadata document is deleted when nobody has resolved its document for thirty days, unless it still holds a refresh token that can be used (or that lapsed within the longest access token's life). A tenant keeps at most 1,000 of them.
- A client that came from a metadata document shows `cimd` as its `registration_origin` in the admin API and the console, and is left out of a tenant export.
- A tenant can open client registration to MCP clients alone. The new `client_registration_policy` value `mcp` lets an agent register itself without a token, as a public client with `https` or loopback `http` redirect addresses, which may ask for `mcp:read` and never `mcp:write`, and whose only audience is the tenant's MCP address. A request for `mcp:read mcp:write` registers with `mcp:read` only, and the response's `scope` says what was kept; one whose scopes are all unavailable (only `mcp:write`, for example), or that names another audience, grant or authentication method, is refused with `invalid_client_metadata`. A tenant that holds 1,000 clients that registered themselves makes room by removing the oldest public one nobody used and refuses when there is none (a confidential one that registered itself is never removed that way), and one address may register ten clients an hour on a tenant, and the tenant sixty (`429` with `Retry-After` past either). It also refuses a key set and a logout address. `odudu reap` now deletes a public client that registered itself, under the `open` policy as well as `mcp`, once it is a week old and nobody approved it, signed in through it or holds a grant that has not yet been reaped; it reports them as `dynamic_clients`. A client with an approval (even one the person later withdrew), a recent grant, or a sign-in under way stays. A registration token presented to a tenant on `mcp` is ignored and not spent. Set it with `odudu seed tenant --set`, through the settings API, or in the console under Settings, Client registration, where the switch for client metadata documents (`cimd_enabled`) sits beside it; the tenant export carries both.
- On a tenant whose policy is `mcp`, a client that came from a metadata document is given the MCP address as its only audience and `mcp:read` as an optional scope by the policy, never by what its document says, and loses both the next time its document is resolved if the policy is changed. A document client that authenticates with a key is not given them. When the policy is turned off, no client that came through it is offered the MCP address or `mcp:read` at its next sign-in or refresh, so an existing refresh chain stops carrying them; disable or delete the client to end the chain at once. Neither kind of client is ever given `mcp:write`, even if an administrator assigns it.
- Two settings on each client limit token exchange, both off for every client: `token_exchange_allowed_for_public` lets a public client use the exchange grant, and `token_exchange_actor_from_other_client` lets a client present an actor token that was issued to another client. They are fields of the client in the admin API (changes are audited with their values, and so now are changes to `consent_required` and `token_exchange_impersonation_allowed`, which the trail left out before; a client's `ETag` follows them), they travel in a tenant export and import (a document from before them imports with both off), and `odudu seed client` sets them with `--token-exchange-allowed-for-public` and `--token-exchange-actor-from-other-client`, each needing `--grant-type urn:ietf:params:oauth:grant-type:token-exchange`. The console's client page shows them under Token exchange, beside impersonation. Neither is on for any built-in client, and the built-in admin client refuses a change to either.
- The admin API `POST` routes take an `Idempotency-Key` header, so a client that retries a request that may not have arrived cannot apply it twice. The first call with a key runs; a repeat within 24 hours is answered with the same status, body and `ETag` and is marked `Idempotent-Replayed: true`, without running again or writing a second audit row. A key belongs to one tenant, one route and the caller that first used it: the same key with another request, or from another caller, is refused with `422` (`about:blank#idempotency-key-reused`) and one still running with `409`. A repeat is answered from the record before its `If-Match` is read again. A refusal or failure is not kept, so a retry runs. A tenant holds at most 10,000 keys that have not expired, past which a new key is refused with `429`, and a response over 64 KiB is refused with `422` and undone. The stored response is a copy of the one sent, so it can hold subject data such as an email; it is kept 24 hours and then deleted by `odudu reap`, and erasing a subject does not purge it. A call is undone as a whole when the database work fails, but a side effect outside the database, such as the test mail, is not. The routes that answer with a secret shown once (creating a client, rotating its secret, minting a registration token, issuing a password, importing a tenant) refuse a key with `400` (`about:blank#idempotency-unsupported`) rather than keep the secret, and so does creating a tenant (`about:blank#idempotency-not-atomic`), which writes outside the transaction a record would share, and so do testing a tenant's mail relay and verifying a domain (`about:blank#idempotency-external-io`), which wait on another server while they run; repeat them without one. `PUT`, `PATCH` and `DELETE` ignore the header, being idempotent already, and the OpenAPI document names it, and the `400`, `409`, `422`, `429` and `503` it can bring, on each `POST` that takes one. A call undone by the ceiling or the size limit answers without the `ETag` or `Location` of the change that never happened. The console does not send it, so only direct callers use it. Calls with a key run a few at a time (fewer than half the database pool) and wait their turn for at most ten seconds, behind at most a hundred others; past either the call is refused with `503` (`about:blank#idempotency-busy`) and `Retry-After`, and nothing is applied. A database pool of one connection cannot run them and refuses them with `503` (`about:blank#idempotency-unavailable`).
- `odudu reap` reports another table, `idempotency_keys`, after `client_metadata_cache`: a key is deleted once its 24 hours have passed.
- Each tenant serves an MCP endpoint at `/tenants/<name>/mcp` on your base address, or at `/mcp` on a tenant's own domain (and only there: the path address of a tenant that has a domain does not serve it). An MCP client reaches 61 tools that read what the admin API reads (clients, people, roles, sessions, keys, domains, the audit trail and the rest, and for the system tenant alone the list of tenants, described below), as the person who signed in: a call is judged by the capabilities that person holds and by the token's scope, so `mcp:read` reads what they could read in the console and nothing more, and a tool they could not use is left out of the list. A confidential client with the `client_credentials` grant that you give the MCP address as an audience and `mcp:read` as a `client_credentials_scopes` entry reaches it too, as its service account, and sees only what the account's roles allow. The tools that change anything are described in the next entries. A client reaches it only with an access token whose audience is the MCP address, which it gets by naming that address as the `resource` of its sign-in request and of its token request, and which the tenant has to have allowed it: a client that registered itself under the `mcp` registration policy is given the MCP address as its only audience, a client that came from a metadata document is given it while that policy is on, and a client you created yourself needs the MCP address added to its `audiences` and `mcp:read` assigned. The `mcp:read` scope is then offered on the consent screen and the person approves it. The built-in `odudu-mcp` client is for local tools and the admin API: its tokens are refused here, and an ordinary client's token, whose audience is the tenant's address alone, is `401`. Ending the `mcp` policy ends the audience at each client's next sign-in or refresh. The endpoint refuses a token that is for another address, for another tenant, for the admin API (also when it names the MCP address beside it), that has expired or whose grant, session, client or person has since ended: `401` with a `WWW-Authenticate` header that names the protected resource metadata, and `403 insufficient_scope` for a valid token with no MCP scope. A tenant that does not exist or is disabled answers an empty `404`, as its metadata does. It answers `POST` only (`GET` and `DELETE` are `405`), serves the 2026-07-28 revision and the 2025-11-25 handshake without keeping a session, takes a body of at most 256 KiB, and refuses a `Host` that is not the tenant's address and an `Origin` that is not its own. Each person and client may make 60 requests a minute and four at once, a person 120 a minute across all their clients, and a tenant 600 a minute, counted over a sliding minute; one address (behind a proxy, the proxy) may make 600 a minute to the endpoints of all tenants before any token is looked at. Past a limit the answer is `429` with `Retry-After`. The counts are per server process, so several instances multiply them. A tool that has not answered in 20 seconds is given up on and recorded as failed. With no `ODUDU_PUBLIC_BASE_URL` set, only a loopback `Host` (and `Origin`) is accepted, so a name that merely points at the server cannot drive it from a browser. Every tool call writes one `agent.tool_call` audit row naming the tool and the admin route it reached, and never what it was called with.
- An MCP client holding `mcp:write` is offered tools to change what exists, `update_client_metadata` and `update_scope_metadata` first, which change the descriptive text of one client (its name, its description and their texts in other languages) or one scope (its description and its texts in other languages), and nothing else: a redirect address, a grant, a secret, whether a client is on, a role and a scope's consent text are not in the tools, and the admin API refuses them to an agent even when a tool is bypassed. A call names the `etag` that `get_client` or `get_scope` returned as `if_match`, so a change made in the meantime answers `412` and an agent reads again instead of overwriting; the person's own capability (`manage-clients` for a client, `manage-tenant` for a scope) still decides, the name of the built-in administration and MCP clients is refused to an agent, and each change is an audit row naming the agent's client and the person, with what the text was before and after, so it can be put back. A client has to be given `mcp:write` by you, and the person is then asked about it every time a sign-in would grant it, whatever the client's consent setting or an earlier approval (if the client holds `mcp:write` as an optional scope the box is not ticked for them; if as a default scope the screen names it and has no box; and a request that may not show a screen is refused with `consent_required`): it lasts ten minutes at most and has no refresh token, and a client that registered itself under the `mcp` policy, or came from a metadata document, can never have it. A text an agent reads (a name, a description, an audit detail) may tell it to change a description, and an agent that holds `mcp:write` for a person who may can then do so: that is the reversible risk of granting it. A write that runs past its 20-second deadline is answered `mcp:outcome_unknown`, not as a failure, because the change may still be made: it tells the agent to read the client or scope again before sending it twice, and the audit row for the call says `failed` with the reason `timeout_outcome_unknown`. An empty description can be sent, as the admin API accepts one.
- An MCP client holding `mcp:write` is also offered five tools for the structure of a tenant, for a person who holds `manage-tenant`: `create_role`, `create_group` and `create_scope` make a role, a group or a scope, and `update_role_description` and `update_group_description` change a description. What an agent makes grants nothing: a new role is held by nobody, is a default for no one and has nothing nested in it; a new group has no roles, no members and no parent; a new scope is assigned to no client, maps no role and has no consent text, and a scope's `display_order` can now be set, by `create_scope` and `update_scope_metadata`. A parent, a default for new subjects, a scope's consent text, the tokens it appears in and who is assigned it are not in the tools, and the admin API refuses them to an agent whatever a tool sends. A create needs an `idempotency_key` the agent chose and sends again on a retry, so one role is made however often the call is repeated, and a scope name has to be one token a client can ask for (no space, quote or backslash) and a group name holds no slash. Each token may make 20 changing calls and 10 creates, counted on the sign-in's grant, so calls made at once cannot pass the limit. Only a call that came through the MCP endpoint may create: `odudu mcp` does not offer the three create tools, and the admin API refuses a create from any agent token the endpoint did not sign (`403`, recorded as a refusal), because it is the endpoint that counts. Each of these now leaves its own audit row with what it set: the admin API records the fields a role, group or scope was created with (`role.create`, `group.create`, `scope.create`) and what an amendment of a role or group changed (`role.amend`, `group.amend`), which it did not before, for every caller.
- An MCP client holding `mcp:write` is also offered three tools for the words people read on the sign-in pages, for a person who holds `manage-tenant`. `update_tenant_text_settings` changes the tenant's display name, the languages its pages are offered in and the default language, and nothing else: none of the other settings can be set through it, and the admin API refuses a body that names one, or one beside these, as a whole. `set_message_override` sets the tenant's own wording for one message in one language, and `clear_message_override` puts the default wording back. **This wording is shown to people on the sign-in pages and in mail, where they type a password, as soon as it is saved**, so an agent that has read hostile text could mislead a person there: it is the text most worth reading in the audit trail. A change is reversed by sending the earlier text back, which the audit row now holds. The settings call names the `etag` that `get_settings` returned (which now carries it) as `if_match`; a message override is created without one (and refused with `412` where one exists) and replaced or cleared with the `etag` that `list_message_overrides` gave. A tenant still holds at most 500 overrides, and the display name is at most 256 characters once surrounding spaces are trimmed. A `set_message_override` without an etag creates a row, so it counts as one of the ten creates a sign-in allows; a replacement or a clear counts only among the twenty changes. Setting or clearing an override changes how many rows a tenant holds, so, as for a create, only a call that came through the MCP endpoint may do it: `odudu mcp` does not offer the override tools, a service account cannot use them, and the admin API refuses them (`403`, recorded as a refusal) to any agent token the endpoint did not sign; the settings tool is open to all three, because it only amends what exists.
- An MCP client holding `mcp:write` is also offered `update_theme_draft` and `update_client_theme_draft`, for a person who holds `manage-tenant` (the tenant's theme) or `manage-clients` (a client's), which save a draft of its colours and font, its stylesheet and its page templates. **A draft is not what people see:** nothing shows it until a person publishes it in the console, and no tool publishes, restores, discards or resets a theme, changes a built-in client's theme, or uploads an image. A call names the entity tag that `get_theme` or `get_client_theme` returned as `if_match` (none, when that read says there is no draft, to make the first one); the tool reads the draft itself and sends every part the agent did not name exactly as it is stored, so reading it for the agent never rewrites a stylesheet; each part it does name replaces that part whole, a draft passing 512 KiB is refused and nothing is saved, and a stylesheet or template the console would refuse comes back as the admin API's list of problems. A first draft counts as one of a sign-in's ten creates. A draft that is replaced is not kept: the audit event (`theme.draft_saved`, for a person's save too) now names the parts that changed with the length and a SHA-256 digest of each before and after, never the text, so both tools are hinted as destructive. The tool reads draft and published theme together, which must come to under 1 MiB. A first draft is answered with a warning if the published theme changed while it was saved, and a theme whose admin answer fits under 1 MiB but is too large for `get_theme` to return (over 256,000 bytes) still gives the draft's etag beside the refusal, so the draft can be updated. A theme whose admin answer is itself over 1 MiB is refused before any etag is available, and the tools cannot read or update it: it is edited in the console. Only the MCP endpoint offers them: `odudu mcp` does not, a service account cannot use them, and the admin API refuses them (`403`, recorded as a refusal) to an agent token the endpoint did not sign. The draft routes also refuse an agent for a built-in client (the admin console and the MCP client) whatever the body names.
- `odudu mcp` serves the same tools over standard input and output, for an AI tool that runs on your machine (Claude Code, Cursor, Claude Desktop). It calls your instance's admin API over HTTP, as you or as a service account, and needs no database or server settings: `odudu mcp --base-url https://id.example.com --tenant acme`. It offers the read tools; `--allow-writes` asks for `mcp:write` as well and adds the write tools that amend a description, a name or the tenant's display name and languages (the three that create something, the two that set or clear a message override and the two that save a theme draft are offered by the endpoint alone, because only the endpoint counts them). The address must be `https` unless it is a loopback address. A tenant with a domain of its own signs in at that address, which `--tenant-address` names; the admin API stays at `--base-url`. Each call it makes is recorded: the admin API writes one `agent.tool_call` audit row, before the call runs, for every agent call whose token the MCP endpoint did not sign, which covers a call made with a token issued straight to the agent and one made with an exchanged token, naming the route as the tool (`admin.get.clients`), and answers `503` without running it if the row cannot be written.
- Signing in for `odudu mcp` opens your browser, and no password is typed into the command. The sign-in is kept in your operating system's credential store (the macOS keychain, or `secret-tool` on Linux), or, where there is none, in a file under `~/.config/odudu/mcp` that only you can read; a file that group or others can read is refused. A run with `--allow-writes` asks you again each time, keeps nothing and never uses a stored sign-in. `odudu mcp --logout` forgets the one kept for an instance and tenant.
- A service account can run `odudu mcp` with no browser: `odudu mcp --keygen` prints an `ODUDU_MCP_KEY` line for the environment and the public key set to register for the client (`private_key_jwt`, the `client_credentials` grant, the audience `urn:odudu:params:admin-api` and the `mcp:read` scope). The client is named with `--client-id` or `ODUDU_MCP_CLIENT_ID`, and the key can come from `--key-file`.
- `odudu seed client --audience <resource>`, repeatable, gives a client the audiences it may ask for, such as a tenant's MCP address, so a client that is handed a fixed client id can be made without the console or the admin API; `odudu seed assign-scope` then gives it `mcp:read` or `mcp:write`. A list is held to the same limit as the admin API's.
- Every MCP connection now says which tenant it serves, so a client with several Odudu servers connected can tell them apart: the server's name is `odudu:<tenant>` with the title `Odudu (<tenant>)`, its instructions say it acts in that tenant only, and every tool description starts with `[<tenant>]`. The endpoint takes the tenant from the token and `odudu mcp` from `--tenant`. The `whoami` admin route, and the MCP tool of that name, also return `issuerTenantName`, the name of the caller's tenant, beside `issuerTenantId`.
- An MCP client signed in to the `system` tenant as a person who holds `manage-tenants` is offered two more tools, `list_tenants` and `count_tenants`, which list the instance's tenants (name, display name, whether enabled), one page at a time and filtered by name or display name prefix or by whether they are enabled, and count them. A client signed in to any other tenant is not offered them, and calling them anyway is refused with `401`; an owner without `manage-tenants` is refused with `403` and a `capability.refused` audit row. Neither tool takes a tenant argument or opens any tenant's content, and a tenant's display name, which its own administrators write, comes back under `data` like every other text. An agent of any other tenant is offered neither, and the rest of the tools are the same everywhere.
- An MCP client reaches six more small reads, each under the capability its admin route asks for: `get_tenant` (the tenant it acts in: name, display name, whether it is enabled; `manage-tenant`, and it takes no argument, so it can never open another tenant), `get_username_policy` (whether usernames can be changed; `view-users`), `get_passkey_impact` (how many subjects' passkeys would be hidden by moving the canonical address to the one named; `view-domains`), `get_scope_impact` (what deleting a scope would take with it) and `list_builtin_scopes` (which built-in scopes the tenant has; both `manage-tenant`), and `get_client_installation` (the issuer, discovery address and registered settings a relying party is configured with, never the secret; `manage-clients`). Text in their answers comes back under `data` like every other.
- An MCP client reaches eleven reads of how a tenant and its clients look. `get_theme` and `get_client_theme` return the draft and the published theme whole, with the stylesheet and every page template kept up to 131,072 characters instead of 1,000, still under `data` and stripped of control and bidirectional-override characters, and the draft's `ETag` beside them; a theme too large for one result is refused as `mcp:result_too_large`. `list_theme_versions` and `list_client_theme_versions` list the versions without their bodies, `get_theme_preview_info` and `get_client_theme_preview_info` say what a preview of a page kind would show, `get_stylesheet_hooks` lists what a stylesheet may name, `get_mail_branding` and `get_client_mail_branding` give the mail's colours and logo, `list_message_overrides` pages a locale's own wording and `get_message_catalogue` lists the messages it replaces. The tenant's are under `manage-tenant` and a client's under `manage-clients`, so an owner without `manage-clients` is not offered the client ones. The uploaded image bytes and the rendered previews are still not offered.

### Changed

- A tenant now defines at most 1,000 roles (a client's own included) and 10,000 groups, as it already defined at most 1,000 scopes. A create past the limit is refused with `409` and says `a tenant defines at most 1000 roles` (or `10000 groups`), for a person, a script and an AI agent alike; a tenant that already holds more keeps every one and is refused only a new one. The numbers are `ROLE_LIMIT` and `GROUP_LIMIT` in `@odudu/contracts`, and the admin API reference says them on `POST /roles` and `POST /groups`. A tenant import is held to the same limits and refused with the same words when its document defines more.
- Creating a role or a group no longer locks the tenant's row, which every sign-in locks too: creators of one kind in one tenant take an advisory lock, so a tenant loading thousands of groups does not make its sign-ins queue behind the count.
- An MCP write sent by name with a token that holds no write scope is refused before the allowance is read, so it takes no lock on the grant.
- `max_clients` now limits the clients an administrator or a registration token makes, the built-in ones included, and no longer counts a client that arrived on its own, so nobody who is not signed in can fill it and keep an administrator from making a client. Clients that registered themselves have a limit of 1,000 a tenant (the oldest one nobody approved, signed in through or granted anything is removed to make room, and the registration is refused when there is none), and clients from a metadata document one of 1,000 as before. A tenant import counts only the clients in the document that did not register themselves, and is refused when the document holds more than 1,000 that did. A restored `anonymous` client has no approval, so `odudu reap` removes it a week after the import unless it is used.
- The audit event for a settings change (`tenant.amend_settings`) now carries a detail: the registration policy, `cimd_enabled`, the display name and the supported and default languages, before and after, so a change to who may register clients or to wording people read can be read from the trail; no other setting is written into it. The audit events for setting and clearing a message override (`message_override.set`, `message_override.delete`) now carry the text before and after instead of its length, so a change to wording people read can be read, and undone, from the trail. A tenant's display name is now at most 256 characters, in the settings, in `PATCH /admin/tenants/{tenant}`, when a tenant is created or imported and in a tenant document; a longer one is refused with `400`. A tenant whose stored name is already longer keeps it and still exports; importing a document that holds one is refused. A message override's key with a NUL in it is now a `400`, not a `500`, and the wording an agent writes may hold no control or invisible character other than a line break and a tab (and no tab or line break in a name or the display name).
- The audit event for amending a scope (`scope.amend`) now carries a detail: what the description, the two token flags, the default assignment, the consent text, the texts in other languages and the display order were before and after, as a client's amendment already did, so a change can be read back and undone. It carried none before.
- A client that registered itself, or that came from a metadata document, is shown the consent screen on every sign-in until the person approves that exact client, even if its consent setting was turned off or its request names no scope the screen could record. Approving one client never approves another, whatever name it gives itself. Clients created by an administrator or with a registration token are unchanged.
- A tenant on a domain signs its administrators in to the console through the domain; the console itself stays on your base address. The admin API accepts a tenant's tokens while their issuer is its current address or one it left in the last hour, so a machine client has to fetch tokens from the canonical token endpoint, and tokens from the address left stop working when the hour ends. A console session opened before a switch carries on, because the console refreshes its token at the new address. Switching back returns sign-in to the path address, and tokens issued at the domain keep working for the hour. The system tenant is unaffected.
- A tenant has one address at a time. A passkey is tied to the address it was registered at: after a switch it is not offered at the other address, and a switch back brings it back. Password sign-in is not affected, and nothing is deleted.
- A client's redirect addresses, web origins and sign-out addresses do not change when its tenant switches address, and the apps that read a tenant's issuer have an hour to move to the new one. An API that checks a token's issuer locally must accept both for that hour.
- The built-in roles are ten, not eight. A tenant that exists before the upgrade gets the two new roles when you run `odudu console provision` once after it; until then its administrators are refused the domain routes and the console hides Domains.
- **Upgrade note.** Token exchange now refuses a public client unless its `token_exchange_allowed_for_public` is on, with `unauthorized_client` (a public client holds no secret, so reaching the grant proved nothing about who asked), and refuses an actor token issued to another client unless the requesting client's `token_exchange_actor_from_other_client` is on, as an `invalid_request` recorded as an `invalid_grant`. A client that relied on either stops working at the upgrade, and nothing backfills it. The server logs a warning at start naming how many public clients hold the grant with the setting off and the first twenty. To list them all, run `select t.name, c.client_id from client_oidc_config o join clients c on c.id = o.client_id join tenants t on t.id = c.tenant_id where c.type = 'public' and not o.token_exchange_allowed_for_public and o.grant_types @> array['urn:ietf:params:oauth:grant-type:token-exchange']` as the database owner. Set the field on each, with `PATCH` in the admin API, or register the client that way with `odudu seed client`. An actor token the requesting client was itself issued, and an exchange by a confidential client with no actor, are unchanged.
- A token exchange or a refresh that would turn a token holding `mcp:read` or `mcp:write` into one holding neither is refused with `invalid_scope`: such a token reaches the admin API as an agent, and one without the scope would have reached it as the person. An exchange of such a token that keeps a scope also keeps an `act` claim, the one it carried or the requesting client's. An exchange can no longer ask for more scope than the token it was handed holds, where it used to be bounded by the grant behind the token.
- A client has a service account only while it holds the `client_credentials` grant, not for every confidential client. Creating a client, registering one, importing a tenant or `odudu seed client` makes one only where the grant is on; adding the grant to a client later creates one, with no roles, or reuses the account an upgrade kept, with the roles it still holds; removing it deletes the account with every role, token grant and session it held, and revokes the tokens that were exchanged with the account as the actor, so a leaked secret can no longer sign in as the client. Odudu refuses a token already issued from then on (admin API, introspection), but a resource server that checks only the token's signature accepts it until it expires, at most the access-token lifetime. Past audit events by the account keep its id, and their `actor_name` resolves to nothing. Adding the grant back starts a new account with no roles. Removing the grant is refused when the account holds the tenant's last administrator role. A tenant export leaves `service_account_roles` empty for a client without the grant and names the omission, and an import ignores roles a backup lists for one.
- **Upgrade note.** The migration that ships with this change deletes the service account of a confidential client that does not hold the `client_credentials` grant, unless a token grant, role, group membership, consent, session or audit actor still names it. One it keeps is listed in the server's start-up log (`N confidential clients hold a service account without the client_credentials grant`, with the first twenty), and it is removed the next time that client's `grant_types` are set, for example by turning the grant on and off again in the console. A kept account keeps its roles, and turning the grant on makes them active again. Clients that hold the grant are unchanged. Drizzle runs every pending migration of an upgrade in one transaction, so the locks of all of them are held until it ends: migration 0124 adds two columns to `token_grants` and holds its lock to the end too (no row is rewritten), row security is lifted on `clients`, `client_oidc_config` and two more tables by migrations 0113, 0114, 0119, 0120 and 0122 only when the migrating role is neither a superuser nor `BYPASSRLS` (a supported install is one of them, so it takes no lock for that), and, whoever the owner is, the new columns and constraints on `clients`, `tenants` and `client_oidc_config` (migrations 0114, 0116, 0117, 0120 and 0122, two of which scan every `clients` row), the index builds, the aggregate over every consent that 0119 reads and the updates of 0120 and 0122 hold theirs to the end. Stop the server for the upgrade, as you would for a data migration on a very large installation. The migration reads audit events of the account's own tenant only, one indexed read per account, so its length follows the number of such accounts and does not grow with the audit table; an event filed under another tenant that names a deleted account keeps the actor's id and tenant and loses only the account's name.
- The audit event for a client change (`client.create`, `client.amend`) now carries `service_subject_id` among the values it records, so creating or removing a service account can be read from the trail.
- A client that asks for more than a client registered or identified by itself may hold, such as `mcp:read mcp:write` taken from the metadata's `scopes_supported`, is no longer refused. On a tenant whose registration policy is `mcp`, registration keeps `mcp:read` and the sign-in scopes and the response's `scope` lists them; at sign-in the request is asked about without `mcp:write`, and the token response's `scope` says what was granted. A request for `mcp:write` alone is still refused with `invalid_scope`.
- An AI agent holding `mcp:write` may now make at most 20 changing calls, and at most 10 creates among them, for each sign-in; a call over that is refused with `mcp:write_budget` (`429`) and recorded as a refused `agent.tool_call` event with the reason `write_budget`, and the person signs in again to give it a new allowance. The limit applies to calls made through the MCP endpoint; `odudu mcp` over stdio keeps a count of its own for each run, renewed by each new browser sign-in (a service account's key keeps the one it started with), and neither is a limit on a principal that calls the admin API with its own token, which the allowlist's fields still hold. Reads cost nothing, a call the admin API refuses with a `4xx` gives its place back, and a call that ran out of time or could not be read back keeps it, because the change may have been made. The count is kept on the sign-in's grant, so calls made at the same moment cannot between them pass it, and a new sign-in has its own, and a token exchanged from a sign-in's token shares that sign-in's count, so an exchange does not renew it. A reservation that takes more than a few seconds is answered `mcp:write_budget_unavailable` and the call is not made.
- **Upgrade note.** A migration adds three small columns to every token grant (`agent_writes` and `agent_creates`, both starting at 0, and `budget_grant_id`, empty); it rewrites no row and the server runs it with the others. The migration gives a grant an earlier exchange made its root by following the chain; one whose parent was deleted before the upgrade cannot be told from a sign-in's own grant and keeps a budget of its own, and an MCP write token lives ten minutes, so none that matters outlives the upgrade.
- The audit reasons list a new value, `write_budget`: an agent had made as many changes as one sign-in allows, so the call was not made.
- The admin API's allowlist for an agent's writes now names the method (PATCH, POST, PUT or DELETE), the route and whether the body is named fields or a whole record, and holds one entry for each of the twelve write tools. Which class each admin route is in, and so whether an agent may reach it, is written down in [MCP route classes](docs/protocols/mcp-route-classes.md); a route can no longer move to an MCP tool without its row changing.
- The three MCP guides say, in one table, and the consent and audit page, in a sentence, what an agent can and cannot do and why, class by class, with the count of the admin API's 152 routes in each: 59 reads and 2 instance reads, 13 content writes (12 with a tool), 32 access-changing, 7 credential and 27 destructive operations, 8 sensitive reads and 4 pages drawn for a browser. Access-changing, credential and destructive operations are not available to an agent yet, and a person makes them in the console.

### Fixed

- Moving a group under another rewrote the path of every group whose path began with the moved group's, read as a pattern, so a group named `a%`, `a_` or ending in a backslash could rewrite the paths of unrelated groups when it was moved. The moved group's own subtree is now found by following parents, and nothing else changes.
- `odudu seed role` and `odudu seed group` now refuse to pass a tenant's limit of 1,000 roles and 10,000 groups, with the same words as the admin API.
- A back-channel logout that is retried carries the time of the retry, with the lifetime it was minted with, so a receiver no longer refuses a retry for the age of the first attempt.
- A client's name or description, a scope's description or consent text, or a text in another language, that contained a NUL character was answered with a server error (`500`); it is now refused with `400` naming the field. Creating a scope, a group, a role or a subject with a NUL in its name, description, username or email was the same server error and is now the same `400`.
- Two upgrade migrations, `0119` (when a person first approved a client) and `0120` (which clients are public), found no row to update when the migrating role is neither SUPERUSER nor BYPASSRLS; they now lift forced row security for the statement and restore it, as the later ones do.
- Creating a group with a `/` in its name, and setting or clearing a message override whose key held a NUL character, were server errors (`500`) and are now `400`. A tenant's display name had no length limit before the limit of 256 characters.

### Security

- The consent screen of a client that registered itself says that nobody at the tenant set it up and names the origin this request sends the person back to, then the other origins it registered (five at most, with the count of the rest), as it already did for a client from a metadata document, so a name another application chose cannot stand alone on the screen. `offline_access` is named on it as ongoing access.
- The reads the MCP tools leave out for being personal data or credential metadata (a person's profile and credentials, registration tokens, the mail relay login, one client's claims for a person) are now refused to an agent's token at the admin API too, so `odudu mcp` or a service account holding an agent token cannot read them directly. The console's own sign-in is unaffected.
- A refresh of a client that registered itself or came from a metadata document reads the tenant's registration policy once, so turning the policy off while the token rotates no longer spends the old token and refuses the new one, which made the client's retry revoke its whole chain.
- A request is served as a tenant only through a verified domain row. A host with no verified row selects no tenant and is routed as before, so registering a name cannot blank it; a verified host that is not live gets one bare refusal on every path.
- `X-Forwarded-Host` is read only when `ODUDU_TRUST_PROXY` is on, and then from its last entry, the one your proxy appended, never one a client could have written ahead of it.
- Hosts are refused by their folded spelling, so a Unicode dot or a fullwidth letter does not walk past the refusal of your own host, `localhost` or an IP address.
- Verifying a domain is limited: a tenant looks a host up at most once every 30 seconds and makes ten lookups a minute. The limits are per process.
- A domain whose owner lost it stops serving the tenant's sign-in: the recheck fails it, and the tenant falls back to its path address.
- Mail links are written from the tenant's address, never from the request's `Host`.
- A public client that held the token-exchange grant could use it with any valid actor token, another client's included, because the token endpoint asks a public client for no secret. It is refused unless an administrator allows it, and an actor token must belong to the client presenting it unless that client is allowed otherwise.
- A token that carries `mcp:write` lives ten minutes at most and is never refreshed. The person is asked about it at every sign-in that would grant it, whatever the client's consent setting or an earlier approval, and a request that may not show a screen is refused. A client that registered itself, or came from a metadata document, can never hold it.
- An AI agent reaches the admin API only with a token marked as an agent's, which a token exchange or a refresh cannot shed. With `mcp:read` it can read, except the exports and downloads and the personal-data reads listed below. With `mcp:write` it can also change the descriptive text of a client, scope, role or group, the tenant's display name and languages and the wording of its sign-in pages, save a draft of a theme that only a person can publish, and create a role, group or scope that grants nothing, and only a person who holds the capability for that client or scope (`manage-clients`, `manage-tenant`) can have it done on their behalf: the token's scope allows the call and the person's capabilities still decide it. Every call it makes, allowed or refused, is an audit row naming the agent and the person, written before the call runs.
- An agent working through the MCP endpoint can no longer be used to change a great deal at once: the 20 changes and 10 creates a sign-in allows are counted in the database in one statement, so a burst of calls made together stops at the limit. A write sent to the admin API by an agent still needs the route in the allowlist, only the fields it names, and no body at all for a DELETE.
- The two reads that span tenants, the tenant list and its count, are offered only to an agent of the `system` tenant whose owner holds `manage-tenants`, and refused to every other agent token (`401`, or `403` without the capability). An agent holding a token of one tenant is refused at the routes of every other tenant, whatever capabilities its owner holds there.
- An agent cannot amend a built-in scope (`openid`, `offline_access`, `mcp:read`, `mcp:write` and the other standard ones), its description and display order included, as it cannot rename a built-in client; it still amends the scopes a person made.
- The write budget does not walk a chain of exchanges to find its counters: a grant made by an exchange names the grant it spends, and a grant whose root is gone, or that names none, is refused, so an error path or a long chain never renews an allowance.
- Nothing that changes who can sign in, what a token carries, a secret or the deletion of anything that grants or authenticates is reachable by an agent (a message override it set can be cleared, and nothing else is deleted): the admin API admits an agent's write by method, route and field from a short list, refuses every other field of a listed route and every unlisted route with `403`, and records the refusal. A write that adds or removes a row (a create, a message override set or cleared, a first theme draft) is admitted only to a token the MCP endpoint signed and counted, never to `odudu mcp`, a service account or a token a client holds itself.

## [0.1.0-rc.1] - 2026-10-23

The first release candidate. Odudu is not production ready: it has had no security review.

### Added

- A container image on `ghcr.io/wizzywit/odudu`, for amd64 and arm64, signed, with a list of its contents and a record of how it was built.
- A quick start in one command: `docker compose up -d` starts Postgres and Odudu, makes the database roles and the first administrator, and prints a one-time password.
- The `odudu` command in the image: `odudu init`, `odudu help` and `odudu --version`.
- The documentation, served by the server at `/docs/` and published as a site: a quick start, guides, concepts, a tour of the console, operating and reference pages.
- Four small example apps that sign in with Odudu: a web app, a single-page app, an API and a machine-to-machine client.
- A sign-up button: an app sends `prompt=create` to open the registration page, and discovery lists `prompt_values_supported`.
- A hand-tested guide to signing in to WordPress.
- Sign-in pages, error pages and mail in one shared look, with their text in message catalogues.
- A language chosen for each page from `ui_locales` and the browser's `Accept-Language`.
- Sign-in with the authorization code flow and PKCE, refresh tokens, client credentials, token exchange and single sign-on.
- Many tenants on one server, each with its own people, clients, keys and settings.
- Passwords, passkeys, authenticator codes and recovery codes.
- An admin API and an admin console, and an audit trail of every change and sign-in.

### Changed

- Password rules follow NIST SP 800-63B-4.
- One setting now decides the lifetime and shape of every cookie the server sets.
- Built-in scopes can be deleted, by typing their name, and restored.
- The issuer in tokens, discovery and logout is the configured `ODUDU_PUBLIC_BASE_URL`, never a request's `Host` header.
- A password reset ends every session and token the person had.

### Security

- Base images are pinned by digest, and a test keeps them so.
- Registering with an address that is already taken no longer says that it is taken, when email verification is on.
- Cookies are `Secure` and `__Host-` prefixed under `ODUDU_TLS`, from one setting; before, the session cookie ignored it.
- Characters that change the direction of text are refused in names and usernames.
